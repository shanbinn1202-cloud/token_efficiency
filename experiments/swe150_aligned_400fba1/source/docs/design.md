## 5. Page selection for the query policies

This section is the catalogue of the page-selection policies (`--policy`): each policy's rule, the protocols it serves, its options and what does not combine; the paragraphs below give each rule in full. Which policies ran on the GPU, and how, is in [docs/status.md](status.md); their limits are in [docs/known-limits.md](known-limits.md). On the Gemma 4 profile see section 4.14 for what it serves.

`--token-gather markers` or `separators` is an option of `goal_query` and `observation_query`, not a policy: single history tokens kept beside the selected pages inside the same budget, their K/V gathered at restore into whole 16-token blocks (`mswea-xml`, Qwen, 16-token pages; refused with the plug-ins and with `--release-idle-pages`; [policy-registry section 6](policy-registry.md#6-token-level-selection-option-a-marker-pages-option-b-token-gather), [docs/token-gather/DESIGN.md](token-gather/DESIGN.md)).

`goal_query` and `observation_query` run the Online Selector V2 contract of the dram-backed-kv PoC (`scripts/serve_online_selector_v2.py`, upstream commit `a70701e`). The server pins it at startup as its **selection contract**: a JSON object in `startup.json` and `ready.json` (`selection_contract`; the `runtime.jsonl` rows name its digest in `query.selection.contract_sha256`) that fixes P, the switch threshold, the budget, the recent quota, the projection and each policy's own pin. The page size P is a parameter of that contract. At the default P = 784, vLLM restores full-attention KV in 784-token pages, so the PoC's 16-token budgets are converted to whole pages, and each page is represented by its final 16-token sub-page. At P = 16 (`--page-tokens 16`, section 4.6) the pages, budgets and vectors are the PoC's 16-token ones.

Terms used below:
- **Session:** one agent's multi-turn conversation on one task, with its own KV history (section 4.4). With the XML protocol a server starts with its frozen tasks, one session each (section 4.1).
- **Eligible (candidate) pages:** the sealed pages of the history before the newest observation.
- **Gated-DeltaNet (GDN):** Qwen3.6-27B's linear-attention layers, 48 of its 64 layers. Their recurrent state (153,944,064 bytes) carries the whole history; pages and their selection belong to the 16 full-attention layers. vLLM keeps the states in its Mamba pool (section 8).
- **Live tail:** the session's last page while it is not full, so not yet sealed; every turn attends it.
- **Cover:** a page covers a class of tokens when it holds any token of that class.
- **Rebuild:** a request that does not continue its session starts it again from the whole request: re-rendered from text, the previous pages released, the selector and Goal reset (section 6.1; `stage_b.rebuild` in `runtime.jsonl`). The one exception is the Goal of `goal_query` (and of the plug-in `goal_query_markers`) after a dropped reply (the previous request plus one user message, a format-error retry; goal-rollback-1116): it goes on from the turn whose reply was dropped (running.md section 6.1). `local_turn` counts the session's requests since its start or last rebuild; `turn` counts them all.

Every request after the first of a session runs the PoC's two-phase turn (the PoC's V0 schedule), for every policy:

1. **Phase 1 (observation).** The new observation is prefilled on the pages that stayed resident after the previous turn (its active pages plus the pages sealed while serving it) and on the live tail page, continuing the Gated-DeltaNet state of the previous turn. It yields the vectors of the pages it closes and the observation query: the hidden state at the observation's last token.
2. **Goal.** For `goal_query`, the maintained Goal is built from the previous reply and the latest observation. Its query text runs once as a separate cold forward and is cached by its retrieval-goal hash, as upstream.
3. **Selection** among the pages before the observation (below).
4. **Phase 2 (generation).** The generation header and the decode run on the selected pages plus the observation's KV from phase 1.

Every token is computed exactly once. A page sealed during a turn keeps the vector of that single computation. The first request of a session is one plain prefill.

The selection:

1. Keeps every page active on turn 0 and while the sealed history is at most **8192 tokens** (`reason` `cold_start` / `below_switch_threshold`).
2. Otherwise sets the capacity to `min(n, max(1, mandatory pages, floor(0.40 × history tokens) // P))` pages, where n is the number of candidate pages (the sealed pages before the observation) and the history is n × P tokens. `--active-token-budget N` replaces the ratio with an absolute budget; `--active-ratio R` changes the ratio.
3. Always keeps the **mandatory** pages: every page touched by the initial system + task prompt.
4. Adds **recent** pages: non-mandatory pages from the two previous turns, newest first, at most ⌈1,024 / P⌉ pages (the PoC's 64 × 16 = 1,024 tokens): 2 pages at P = 784, 64 at P = 16.
5. Fills the rest with the pages whose vectors have the highest cosine to the query, using the upstream `PrefillPageEmbeddingSelectorV2`.

Vectors: the last-token hidden state before the model's final norm (the PoC's last decoder layer), projected with the PoC's seeded 128-d Rademacher matrix (seed 20260904, SHA-256 `20c2e1cf…87aa` for hidden size 5120), L2-normalised and int8-quantised per vector. The Goal query is the PoC's `<retrieval_query>` JSON text of the maintained Goal; `--goal-query-variant candidate_entity_cap8` keeps only the last 8 files, symbols and tests in that text. The maintained Goal uses entity-drift 3 and, with `--goal-rewriter-model`, the PoC's persistent Qwen3-0.6B rewriter (the default engine). `--goal-rewriter-engine vllm` serves the same model from a vLLM child instead (section 4.10); outside the README's stable command it is experimental ([docs/known-limits.md](known-limits.md) 3.2). A failed rewrite falls back to deterministic fields for that turn, as upstream, and is recorded; `goals.jsonl` keeps the text of every Goal, Goal query and rewriter exchange (section 8).

`observation_query` does not use the Goal rewriter, because its ranking depends only on the observation vector: the server never starts the rewriter for it, builds its Goal from deterministic fields (evidence only), refuses a startup config that pins one, and records a given `--goal-rewriter-model` as unused in `startup.json` and the dry run (`goal_rewriter`).

**Random-fill control.** `--policy random_fill` is `observation_query` with only step 5 changed: the same threshold, capacity, mandatory and recent pages, the same phase 1 and deterministic Goal (evidence only), no Goal rewriter (a given `--goal-rewriter-model` is recorded as unused, a config that pins one is refused) and no Goal forward. The candidates left after the mandatory and recent pages are put in a random order and the first ones fill the capacity; no query vector, projection or score is used. The order is SplitMix64 with Fisher-Yates (nothing is hashed), keyed by the seed pinned at startup (`--fill-seed`, default 42, the `random_fill` key of the selection contract), the session index and the session's request ordinal. On every active turn `query.selection.fill` records the seed, the session index, the ordinal (`turn`) and the counts of eligible and drawn pages, and `retrieved_pages` lists the drawn pages in draw order. If `goal_query` and `observation_query` do no better than this control, their ranking carries no useful information. Unlike `random50`, it keeps the query policies' mandatory and recent pages and budget.

**AKV rule (akv-rule).** `--policy akv_rule` reproduces the tool-response rolling-drop policy of AKV (Fu et al., "Cache Engineering for Agents", arXiv 2610.28577): the paper retains the cache of all reasoning and of the latest 12 tool responses (sections 3.2 and 5.1) and drops older tool-response cache once the tool responses exceed those 12 (appendix A.4.2), with no token threshold. akv_rule attends the mandatory pages (the initial system + task prompt, which the paper never drops), every page holding a token of any agent reply (the reply spans of 60c5d21's `recent_tools`: the generation header, the reasoning, `</think>`, the content and the closing boundary; cover) and the pages of the latest 12 tool responses, the current turn's observation counted as the newest of them (it is the live tail, always attended), so the latest 11 sealed observation spans are kept whole; nothing else. A page is dropped only when every one of its tokens lies in an older tool response; the history of a rebuilt first request, which no span splits by role, is kept (the paper never drops reasoning). There is no budget: the capacity is the rule's selection, so the contract's `active_ratio` and `active_token_budget` are both null (serve.py refuses `--active-token-budget` and `--active-ratio` for akv_rule) and no token threshold (`switch_threshold_tokens` 0: the rule applies from local turn 1 and keeps every page until the 13th tool response arrives, when the oldest sealed one is dropped). The fill is the kept pages newest first, then the dropped ones; the native admission gate counts every page as a possible restore for akv_rule (`capacity.selected_max`). Its contract alone carries the `akv_rule` key (`{rule: replies_and_latest_tool_responses_v1, latest_tool_responses: 12}`); every other contract keeps its bytes and digest. On every active turn `query.selection.window` records, besides the window fields above, `selected_page_count` and `selected_tokens`, `reply_pages`, `kept_tool_responses` (min(11, sealed tool responses); the current one is the 12th) and `dropped_tool_responses`, `dropped_pages`, and the first kept sealed tool response's page and token position (`first_tool_page`, `first_tool_position`). Known differences from AKV: (1) positions: retained pages keep their original positions (AKV's `repos`, which re-encodes positions in logical token order, is not implemented); (2) dropped pages stay in DRAM and the rule never selects them again (AKV prefers evicting dropped cache); (3) Qwen3.6's GDN layers keep a state of the whole history, the dropped tool responses included, so the drop applies to its full-attention layers only (the paper's models, MiniMax-M2.7, GPT-OSS-120B and MiroThinker-1.7-Mini, are MoE transformers with no such state described); (4) the server applies the rule itself, where AKV's agent harness issues the cache operations (message indices) with each request; (5) granularity: P-token pages by cover (16 with `--page-tokens 16`, 784 at the default), so a dropped tool response's tokens on a page shared with a kept token stay attended (AKV drops whole messages); (6) "the latest 12" is read as including the newest tool response, which the paper does not state explicitly. Tests: `test_akv_rule.py`.

**Recent-window policies (recent-fill).** `--policy recent_fill` and `--policy recent_tools` are `random_fill` with a fixed fill order instead of a random one: the same threshold, capacity, mandatory and recent pages, the same phase 1 (the worker still computes and sends the page vectors) and deterministic Goal (evidence only), no Goal rewriter and no Goal forward; no query vector, projection or score is used, and nothing is hashed per page. `recent_fill` fills the candidates (the sealed pages that are neither mandatory nor recent) newest first by position. The recent pages are the newest ones, so its selection is the mandatory pages plus the contiguous window from its first page to the newest sealed page: the latest tool responses and the replies between them, as many whole turns as the budget holds. `recent_tools` classifies every candidate page by cover (a page holding any token of a class, as for the mandatory pages), in this precedence: a CALL page holds any tool-call token, else a TOOL page holds any tool-response token (an observation span), else it is a REASONING page; it fills the CALL pages newest first, then the TOOL pages newest first, then the REASONING pages newest first. A reply runs from the end of a turn's observation span (the first turn: its stable end) to the next turn's stable end: the generation header, the generated tokens and the closing boundary. Its tool call is everything after the first `</think>` past the generation header (the content, through the boundary); its reasoning is the generation header, `<think>` ... `</think>`. With thinking off, or for a reply without `</think>`, the call is the whole reply after the generation header. The split is computed on the transcript's own token stream: with `--enable-thinking` the XML protocol keeps the reasoning in its history (section 6.8); `--thinking-history strip` (chat-text) refuses `recent_tools` and `akv_rule` at launch, because a stripped history holds each past reply inside the next observation span, where its tool call and reasoning cannot be told from tool responses (until review-fixes-1110 the combination was accepted, `recent_tools` then ordered exactly as `recent_fill` and `akv_rule` dropped pages of old replies); the kv-session transcript has no encoder, so its replies are all call. The history of a first request that carries more than the initial messages (a rebuild) lies in no observation or reply span and is windowed with the tool responses (TOOL). Each contract carries its own key (`recent_fill` or `recent_tools`: `{order}`, no option); every other contract keeps its bytes and digest. On every active turn `query.selection.window` records the first selected page after the mandatory ones and its token position (`first_page`, `first_position`), how many whole turns (a tool response and the reply after it) and whole tool responses of the sealed history are attended (`covered_turns` of `history_turns`, `covered_tool_responses` of `history_tool_responses`: N; the current observation is always attended besides), and for `recent_tools` the CALL pages kept (`calls_kept` of `call_pages`, `calls_truncated`), the TOOL pages kept (`tools_kept` of `tool_pages`), the REASONING pages kept (`reasoning_kept` of `reasoning_pages`) and the first selected TOOL page and its position (`first_tool_page`, `first_tool_position`). `retrieved_pages` lists the filled pages in fill order. Tests: `test_recent_fill.py`.

**Plug-in policies and token gather.** `ledger_query`, `goal_query_markers` and `observation_query_markers` are query plug-ins of the policy registry (`source-overlay/page_policies/`): on every active turn Selector V2 computes the partition and the cosine order exactly as for its base policy, and the plug-in's hook protects, excludes or groups candidate pages before the cosine fill takes the rest of the budget ([docs/policy-registry.md](policy-registry.md) sections 8 and 9: the rules, pins and records). `--token-gather` keeps single tokens of the history beside the selected pages; the selection of pages is unchanged ([docs/token-gather/DESIGN.md](token-gather/DESIGN.md)). The token gather does not combine with a plug-in.

Known differences from the PoC, and between the two layouts:
- At the default 784-token pages every budget is a whole number of pages and the live tail is one partly filled page. At 16-token pages the budgets, the recent quota and the live tail (under 16 tokens) are the PoC's.
- Mandatory pages cover every page the system + task prompt touches. The PoC keeps only pages lying fully inside it, which at 784-token pages could drop the end of the task; at 16-token pages the two differ by at most one page.
- In the decoupled layout the worker computes the int8 page vectors in one batch on the GPU; at the default layout they are computed per vector on the CPU. The two paths can differ: on 600 synthetic 5,120-wide rows (x86 CPU torch) about 0.35 % of the vectors, about 2 of 600, differed by 1 in one element, which can reorder near-ties. The test (`tests/test_decouple_wp3_vectors.py`) bounds that share below 2 % and every difference at 1 (`docs/exp-decouple-pages/DESIGN.md`, Integration item 4).
- `random50` keeps its fixed floor(n/2) draw. At 16-token pages it is seeded from a 16-token block hash, so its draws are not comparable with those at 784-token pages.

## 8. Evidence per server

Each `--output` directory contains:

| File | Content |
| --- | --- |
| `startup.json`, `launch.json`, `chat_template.jinja` | Frozen task/config hashes, exact server command, pinned template |
| `ready.json`, `worker-attached.json` | READY identity (READY: section 4.1; with the selection contract, the pre-norm vector space and the `epoch`, the identity token of this server run that the native files, `goals.jsonl` and the cleanup receipts repeat) and worker attachment receipt |
| `runtime.jsonl` | One row per turn: response `id`, internal request ID, token/order hashes, `candidate_page_count`, `selected_logical_pages`, `prepare`/`restore` H2D bytes, joined purge/drain, latency. `stage_b` holds the geometry of the two-phase turn of section 5 (Stage B): the computed start C (the session's tokens already computed before this request), the candidate end, the observation span, the phase-1 range, the phase-2 start, `retain`/`restore`/`release`, the computed end C′ = prompt + generated − 1, the sealed end and `rebuild`. Rows of the Selector V2 policies (every policy but `full` and `random50`) add `query.selection` (`reason`, `capacity_pages`, `mandatory_pages`, `recent_pages`, `retrieved_pages`, contract and projection hashes; `fill` for `random_fill`, `window` for `recent_fill`, `recent_tools` and `akv_rule`, `hook` for the plug-ins) and `query.goal` (variant, rewriter attempt/success/fallback, cache hit, cold forward); `goal_query` rows add `query.goal_text` (below) |
| `goals.jsonl` | `goal_query` only: per request, the text behind its Goal hashes and the Goal rewriter's input and output (below) |
| `native-<sha256(request id)>.json` | Native plan (`selected`, `retain`/`restore`/`release`; `run_pages`, the phase-1 pages handed to phase 2; the tail flags `tail_candidate`, the tail page completed in phase 1, and `tail_live`, the tail page continued in phase 2; `phase1`, the id and digests of phase 1's block lease), worker frames (`prepare`, `phase1`, `phase1_drain`, `reserve`, `allocation_update`, `complete`) and drain receipt (`drain`: `drained`, the carry's computed end and the pages in DRAM after every copy joined) |
| `failures.jsonl` | Contract/runtime failures with the exception `chain` and `traceback` (absent on success: written only when a request fails) |
| `engine-cleanup.json`, `parent-cleanup.json` | Shutdown receipts |

The decoupled layout adds fields; the default layout writes none of them (`docs/exp-decouple-pages/WP4.md`, section 4):
- `ready.json`: `kv_layout` (P = `page_tokens`, the attention page; M = `mamba_tokens`, the tokens of one Mamba block, after which the Gated-DeltaNet state crosses to a new block; K = `mamba_slots`, the state slots of the Mamba pool), `num_blocks_by_pool` and `free_blocks_by_pool` (attention pool first, Mamba pool second); `worker-attached.json`: the same as `kv_pools`.
- Every `runtime.jsonl` row and native file: `kv_pools.free_blocks_by_pool` after that request's drain.
- `engine-cleanup.json`: `kv_pools` once every session closed. After a clean run both pools are back at the readiness baseline (every block but each pool's null block free), which the validated runs checked.
- Sealed page records name their tokens by `token_span` [pP, (p+1)P] instead of `token_sha256`, and page vectors use the `compact_int8_v1` form `[[128 int8], scale]`.

A session-pool server (section 4.4) also writes `sessions.jsonl`, one row per session open and close (`schema` `remote-ra-session-event-v1`, the session id, index and task id, `open_sessions`, the pools' free blocks, and for a close its receipt); `ready.json` adds `session_pool` (`max_running_sessions`, `registered`); every `runtime.jsonl` row adds `open_wait_s`; `engine-cleanup.json` lists under `sessions` the sessions still open at shutdown and adds `session_pool` (which sessions the harness closed, which closed without opening, which were open at shutdown and which never opened). A server without the option writes none of these.

vLLM's KV connector keeps a pinned CPU pool that this runtime never stores to or loads from (section 4.9). A server with `--connector-pool-gib` records `connector_pool_bytes` in `startup.json` only. The speed defaults set it to 1 GiB (section 4.15), so every server started without `--no-speed-defaults` or `--no-connector-pool-gib` records it (1,073,741,824).

A server with an admission flag (section 4.10) records the pinned `admission` record in `startup.json`, `worker-attached.json` and `ready.json`. With `--gdn-device-handoff`, every `runtime.jsonl` row adds `restore.d2d_bytes`. With `--goal-overlap`, every native file adds `goal_overlap_ms`; one whose turn ran a Goal forward also adds `goal_forward_ms` and the worker frame `goal_forward`, which holds that forward's drain, and its `runtime.jsonl` row is unchanged. A server without the flags writes none of these. A server with `--goal-rewriter-batch N` records `goal_rewriter_batch` and its token cap `goal_rewriter_batch_tokens` in `startup.json` and `ready.json` and adds `batch_id` and `batch_size` to every `goals.jsonl` exchange.

A server with `--language-model-only` (section 4.12) records `language_model_only` in `startup.json` and its `effective_server_config`, the worker's text-only record in `worker-attached.json`, and both in `ready.json`. A server without the flag writes none of these.

A server with `--deferred-completion-io` (section 4.11) records `deferred_completion_io` in `startup.json` and `ready.json`; its native files and `goals.jsonl` are byte for byte what the engine thread writes without it, written later (before the frontend reads them).

A kv-session server (section 6.6) adds `kv_session` to every `runtime.jsonl` row. A chat-text server (section 6.7) adds `chat_text` to every `runtime.jsonl` row (`client_session`, `kind` session/main/aside, `key_sha256`, `session_id` (the X-Session-ID or null), `slot`, `slot_turn`, `client_turn`, `binding` bind/rebind, `rebind_reason`, `rebuild`, the requested and effective `max_tokens`, `prompt_tokens`, `completion_tokens`, `finish_reason`, `busy_wait_s`) and writes `chat_sessions.jsonl` (`schema` `remote-ra-chat-text-session-v1`: one row per bind, rebind and close, with the slot, the reason, the idle time and the close receipt's turns). A chat-text `goal_query` server (provisional Goal inputs, section 6.7) records `chat_text_goal` in `startup.json`; its `chat_text` rows add `goal_inputs` (`definition`, `request` `main`, `summary_call`, `answers_call`, `questions_call` or `short_summary_call`, the `requirement` and `observation` rule names, `rewriter` `allowed` or `skipped`), and its `goals.jsonl` rows add `inputs` (the same, each input's `span` in the request's messages, the message index and the start and end in its content, its length in characters, `goal_source` `maintained`, `session_last` or `requirement_only`, and `goal_restarted` on a summary hand-off). A server with `--release-idle-pages` (section 4.13) writes `capacity.jsonl`, adds `idle_release` to every native file and `runtime.jsonl` row and its totals to `engine-cleanup.json`, and records `release_idle_pages` in `startup.json`, `worker-attached.json` and `ready.json`. Other servers write none of these.

With thinking on (`--enable-thinking`, section 6.8) every `runtime.jsonl` row adds `thinking`: the reasoning and content token counts, `closed`, and `history`, how the request met the session (`fresh`, `append`, `rollback` on the XML protocol since keep-rebuild-1116, `rebuild_reasoning_dropped`, `rebuild_reasoning_differs`, `rebuild`); a `rollback` or XML rebuild row adds `kept_tokens` and `reencoded_replies`. A session close of a session pool returns a close receipt (the `POST /v1/sessions/close` response and its `sessions.jsonl` row) whose `released` record itemizes the blocks freed: `released.blocks` = `resident_pages` + `tail` + `gather_blocks` (`gather_blocks` 0 without `--token-gather`; gather-receipt-1115).

**Goal text (`goal_query` only).** `goals.jsonl` (`schema` `remote-ra-goal-text-v1`) has one row per request that reached its native terminal, completed or cancelled, with the text behind the Goal hashes of `runtime.jsonl`:
- `request_id`, `session_id`, `session_index`, `turn`, `local_turn`, `epoch`, `terminal_state`: as in the request's native file (`epoch` is the server run's token of `ready.json`).
- `goal`: `text` is the Goal the selector used, the canonical JSON of its selector payload (schema version, root goal, retrieval Goal, policy hint); `sha256` is the row's `query.goal_hash`.
- `query`: `text` is the `<retrieval_query>` text of the Goal query (`variant`, section 5); `sha256` is `query.goal.payload_sha256`.
- `decision`: gate and applied decision, triggers, changed fields, rewriter attempt and success, `fallback_reason`.
- `carry` (only on a rebuild that dropped the previous reply, goal-rollback-1116): whether the Goal went on from the dropped reply's turn; the same record as the row's `query.goal.carry` (running.md section 6.1).
- `rewrites`: one entry per call of the Qwen3-0.6B rewriter while the Goal was built: `request` (the exact JSON payload sent), `response` (the raw line the rewriter process answered with; `null` when none arrived) and `error` (`Type: message` of a failed call, equal to `fallback_reason`). A successful line holds the candidate the rewriter parsed from its generation. When the rewriter cannot parse its own generation, its line holds only the error and the token counts: the vendored rewriter script does not return the generated text. A request refused before the call (over its size bounds) has no entry. Each entry also records the call's times, measured with the server's `time.perf_counter`, and the child's own counts:
  - `wait_ms`: from the call until the rewriter took it. The rewriter serves one call at a time under its lock, so this is the time spent behind other sessions' calls.
  - `start_ms`: a start of the rewriter process inside the call; 0 unless the process had exited or an earlier call had timed out (the rewriter then closes it).
  - `call_ms`: from the send to the answer line, or to the failure when none arrived (a timeout runs to the 120-s limit).
  - `input_tokens`, `output_tokens`, `generation_latency_ms`: copied from the answer line (the child's prompt and generated token counts and its `generate` time); `null` when the line has none, for example after a timeout.
  - `batch_id`, `batch_size` (only with `--goal-rewriter-batch N`, section 4.10): the server's batch ordinal and the number of calls sent together. On such a server `wait_ms` is the time queued until the batch formed, `start_ms` a child start and the batch line, `call_ms` the batch's send to its answer, and `generation_latency_ms` the batch's `generate` time; the token counts are the call's own. A call whose `generate` failed (in job 3404230, the out-of-memory and cuDNN errors of section 4.10) has `null` token counts and `generation_latency_ms`.

The request's native file and its `runtime.jsonl` row name the row as `goal_text` and `query.goal_text`, `{"file": "goals.jsonl", "sha256": …}`, the SHA-256 of the row's bytes without the newline. A verifier checks every `goal_query` row of `runtime.jsonl`: one line of `goals.jsonl` has that SHA-256 and the row's `request_id`; the SHA-256 of `goal.text` (UTF-8) is `query.goal_hash`; the SHA-256 of `query.text` is `query.goal.payload_sha256`. On the GPU the file took about 11.1–11.3 KB per turn, mostly the root goal repeated in `goal.text`: 23,443,474 bytes over 2,109 rows in job 3461703 and 26,002,489 bytes over 2,303 rows in job 3428631 (SWE-bench `goal_query` servers). At 16 sessions × 70 turns that is about 12.4–12.6 MB per server. Recording changes no Goal, selection or rewriter call and checks nothing per request; at startup the server checks that the Goal text hashes to the GoalRecord version hash. The other policies write neither the file nor the reference.

**Goal timing (`goal_query`, sessions decoding together).** When the Goal is built on a Goal thread (section 4.10), the native file records `goal_async_ms` (from parking the admission to resuming it) and `goal_construct_ms` (the construction's wall time). With `--goal-overlap`, `goal_async_ms` is the time parked at the Goal after phase 1 (0 when the Goal was already built then), and `goal_overlap_ms` is the time from the Goal's start to that point. If the construction called the rewriter, the native file adds `goal_rewrite_wait_ms` and `goal_rewrite_call_ms`, the sums of its calls' `wait_ms` and `call_ms`; `goal_construct_ms` covers both. A construction without a call adds neither. A server of another policy writes neither these fields nor the per-call times above, on Qwen or Gemma 4 (`test_gemma_goal_rewriter.py`); a Gemma 4 `goal_query` server with the rewriter (section 4.14) writes them through the same code as a Qwen one, which is not tested separately.

**One session (`goal_query` with the rewriter).** A one-session server has no Goal thread to park at: the Goal is built during the synchronous admission and the server writes none of the timing fields above. Since review-fixes-1110 the construction runs on a thread of its own while the engine thread waits for it and answers the manager's heartbeat (`goal_async.InlineGoals`), so a rewriter call that runs to its 120-s timeout ends in the fallback above (`fallback_reason`). Before, the engine thread built the Goal itself and could not answer the 90-s heartbeat, and the server was killed first. Goals, selections and evidence are unchanged. CPU-tested only (`test_inline_goal_heartbeat.py`).

A clean shutdown requires all of the following (`examples/slurm/server_checks.py cleanup` checks the receipts):
- `parent.cleanup_sha256 == SHA256(raw engine-cleanup.json)`;
- `joined == true` in both receipts;
- matching `epoch`/`session_id`;
- `engine.runtime_manifest == ready.runtime_manifest`, `engine.pending_operations == 0`;
- `parent.child_exitcode == 0`, `parent.natural_exit == true`;
- the APIServer process actually exited 0.

Reading the transfer numbers:
- `restore.h2d_bytes` counts every host-to-device copy during the turn's model execution, including the hybrid model's recurrent (Gated-DeltaNet) state, not only attention pages. For Qwen3.6-27B one recurrent state is 153,944,064 bytes in either layout, one 784-token attention page is 51,380,224 bytes and one 16-token attention page 1,048,576 bytes.
- In short histories that fit in GPU KV, no attention page is restored from CPU, so all policies show the same restore bytes.
- `prepare.h2d_bytes` is the phase-1 cost (restoring the recurrent state carried from the previous turn); `restore.h2d_bytes` counts the rest of the turn.
- With `--gdn-device-handoff` (section 4.10) the recurrent state moves on the device: on a continuing turn `restore.h2d_bytes` counts the restored attention pages only, and `restore.d2d_bytes` counts the state copies (one, plus one per Mamba-block crossing); `prepare.h2d_bytes` is still the carry.
- Compare policies only on histories that actually evict pages to CPU, and report these components separately.

These files can contain prompts and tool output. Keep them out of public source releases. Joined transfers establish mechanism behavior, not task quality or speedup. Historical labels inside receipts such as `NOT_SYSTEM_VALID` or `cuda_qualified=false` are deliberately conservative capability strings. Judge a run by its READY, per-turn native evidence, cleanup and task evaluation.
