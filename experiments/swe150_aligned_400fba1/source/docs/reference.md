### 4.6 Decoupled KV layout and 16-token pages

**Why pages are 784 tokens by default.** Qwen3.6-27B is a hybrid model: 16 full-attention layers (4 KV heads × 256, bf16: 4,096 bytes per token per layer) and 48 Gated-DeltaNet layers, each with a 3,207,168-byte recurrent and convolution state (vLLM calls these Mamba layers). vLLM 0.24 keeps both kinds in one block pool with one page size. `_align_hybrid_block_size` in `vllm/platforms/interface.py` raises the attention block size until one attention page holds at least one Mamba page, 16 × ⌈3,207,168 / (16 × 4,096)⌉ = 784 tokens, and pads the Mamba page to 784 × 4,096 = 3,211,264 bytes. A runtime page is one attention block, so pages are 784 tokens, and the PoC's 16-token budgets have to be rounded to whole pages (section 5).

**What the decoupled layout changes.** It gives the two kinds separate block pools with independent block sizes (`docs/exp-decouple-pages/DESIGN.md`, decisions D2-D4):
- **Attention pool:** blocks of P tokens. One block is still one page: P × 65,536 bytes over the 16 attention layers, 1 MiB at P = 16.
- **Mamba pool:** unpadded Gated-DeltaNet states. The 48 layers form 3 Mamba groups of 16; one block holds one group's states (16 × 3,207,168 = 51,314,688 bytes), and one slot is one block per group. The pool holds K = 2S + 1 slots for S sessions (a running and a crossing slot per session plus a spare) and a null block: 1 + 3K blocks. It is reserved first out of `--kv-cache-gib`; the attention pool gets the rest, ⌊(KV bytes − (1 + 3K) × 51,314,688) / (P × 65,536)⌋ blocks.
- **Mamba align block:** M = P × ⌈784 / P⌉, which is 784 at P = 16. The Gated-DeltaNet state therefore crosses blocks, is captured and is restored exactly as at 784-token pages (153,944,064 bytes per state).

Group structure, kernels and the Mamba `align` mode stay as they are.

**Flags.** `--page-tokens 16`, `32` or `64` always uses the decoupled layout; `--kv-layout decoupled` also selects it at 784 tokens, a validation mode that splits only the pools. `--page-tokens 16 --kv-layout decoupled` (the form the GPU runs used) is the same as `--page-tokens 16` alone and names the layout explicitly. `serve.py` then appends `--block-size P --mamba-block-size M --additional-config {"remote_ra_kv_layout":{"mamba_slots":K,"mamba_tokens":M,"page_tokens":P}}` to the vLLM command and records `kv_layout` and `page_tokens` = P in `startup.json`. Without either flag the layout adds no vLLM argument, startup key or pin: with `--no-speed-defaults` the vLLM command, the startup config and its pins are byte-identical to those of `902690a` (CPU tests against the earlier code; without it the speed defaults of section 4.15 apply).

**Startup log.** A decoupled server logs these lines (job 3313802: 24 GiB, 5 sessions) and neither vLLM's `Setting attention block size to 784 tokens` nor its Mamba padding line:

```text
Decoupled KV layout: attention block 16 tokens, Mamba block 784 tokens, 11 Mamba slots, unpadded Mamba page.
Decoupled KV cache pools: 22912 attention blocks, 34 Mamba blocks
GPU KV cache size: 366,592 tokens
```

`ready.json` records the layout and both pool sizes (section 8). Pool sizes of the validated runs are in the table of section 4.4.

**Host memory.** In the decoupled layout the worker keeps the attention pages it copies to the host in a pinned page arena. Its capacity is S × (⌈L / P⌉ + 1) pages of P × 65,536 bytes for a context limit of L tokens (`--dram-arena-gib` sets one smaller capacity, section 4.9), allocated on demand in 256 MiB chunks: up to about 4 GiB per session at P = 16 and L = 65,536 (`arena_pages` in `remote_ra_live_v2/worker_composition.py`, `PageArena` in `remote_ra_growing_worker/tensors.py`). This comes on top of the connector's pinned CPU pool (1 GiB by default, vLLM's 32 GiB with `--no-connector-pool-gib`; sections 4.9 and 4.15).

**Selection at P = 16.** The Selector V2 contract takes the page size as a parameter, so at P = 16 it is the PoC's own contract: capacity `max(1, mandatory pages, floor(0.40 × history tokens) // 16)` pages, a recent quota of 64 pages (1,024 tokens), a live tail under 16 tokens and one vector per 16-token page (section 5). The worker compacts the page vectors to int8 on the GPU in one batch per forward (`compact_int8_v1` in the selection contract) instead of one at a time on the CPU.

**Attention backend: `--triton-attn` (opt-in).** vLLM 0.24 runs Qwen's 16 full-attention layers on FlashAttention 3 on a GH200. `--triton-attn` (the decoupled layout at P = 16, 32 or 64 only) passes `--attention-backend TRITON_ATTN` instead, the backend of the group's baselines; the Gated-DeltaNet layers keep their own backend and the Triton kernels of `--gdn-prefill-backend triton`. Nothing else changes: the runner rewrites vLLM's common attention metadata (the physical sequence lengths, the compact block tables and slot mapping) before either backend's metadata builder reads it, the worker takes its KV views from the loaded backend's cache shape (both `(blocks, 2, P, 4, 256)` per layer), and both backends run behind the same attention and KV-update ops, so the CUDA-graph modes and the FULL graphs' sequence-length binding are the same (section 4.8). At 784-token blocks FlashAttention uses 49 kernel blocks of 16 and TRITON_ATTN one of 784, so the switch is refused there (the shared pool and `--kv-layout decoupled` at 784). It pins `attention_backend` in `startup.json` and its `effective_server_config`; the frontend compares vLLM's parsed backend, the engine its resolved one, and the worker its resolved one and every full-attention group's loaded backend, once at startup; the worker's record goes to `worker-attached.json` and `ready.json` (whose `source_closure.backends` names and hashes the loaded backend module either way). Without the switch nothing changes, and a Qwen vLLM that resolved TRITON_ATTN anyway is refused. Outputs are not expected to be bit-identical to FlashAttention's. Give the stock vLLM control the same `--attention-backend TRITON_ATTN`. The Gemma 4 profile always runs TRITON_ATTN (section 4.14); there the switch changes nothing. Tests: `test_triton_attn.py`.

**In-place Mamba-block crossing: `--gdn-inplace-crossing` (opt-in; CPU-tested only, not GPU-validated).** In vLLM's `align` mode a request that crosses a multiple of M gets a second Mamba block, its state is copied into it, and the old block is freed one engine step later; that is why the Mamba pool holds K = 2S + 1 slots and why the capacity gate counts a running and a crossing slot per request. With `--gdn-inplace-crossing` (the decoupled layout only, Qwen) vLLM's `MambaManager` moves the request's one running block to the new row index instead: nothing is allocated or freed, the old index becomes null, and the worker's crossing copy reads and writes that same block. Each running request then holds one Gated-DeltaNet slot, so the pool holds K = S + 1 (the + 1 is phase 1's probe next to its Goal slot) and the attention pool gets the rest: at 25 GiB and P = 16, 2,349 / 3,523 / 4,698 more attention blocks (+2.29 / +3.44 / +4.59 GiB) at 16 / 24 / 32 sessions. The capacity gate counts one running slot in phase 2 (two with `--gdn-device-handoff`'s held probe) and no crossing slot in the running requests' headroom; phase 1 is unchanged. The worker no longer captures the state at M-aligned ends (the slot never moves; a moved slot fails closed), so each crossing saves the second block, the 154 MB host capture and the 154 MB restore (with the hand-off, the device-to-device copy into the new block). The crossing still runs vLLM's own copy of the running state into the block at the new index, which is now the same block: a full device self-copy of the Gated-DeltaNet state (about 154 MB read and 154 MB written), as costly as that copy is without the flag. Before that copy, the worker checks that each request's row still names its running block at its previous index (vLLM's worker rows only grow), so a replaced row fails closed instead of copying the null block over the state; a continuing turn's `restore.h2d_bytes` is the restored Pages plus one carry, a turn 0's the Pages alone (with the hand-off `restore.d2d_bytes` is the hand-off's copy alone). The flag pins `"inplace_crossing": true` in the `kv_layout` record of `startup.json` and in vLLM's `--additional-config`, which `ready.json` (the worker's layout echo) repeats; the dry run and `launch.json` add `gdn_inplace_crossing` with K. Off (the default) nothing changes: no key, K = 2S + 1, the same allocations (checked against `a6d3ef7`'s KV manager) and records. Refused on the shared 784-token pool, on the Gemma 4 profile (it has no Gated-DeltaNet state), with speculative decoding, and wherever a Mamba block would be prefix-cached (the runtime never caches one: every request it owns allocates with `skip_cache`, and the HTTP runtime refuses requests it does not own; a Mamba manager with the flag never hashes a block, skipping that request's Mamba caching rather than stopping the engine, and a crossing refuses a cached or shared running block). It composes with `--async-scheduling` (a voided step of a stopped request moves the block it already holds; the carry is unchanged) and `--gdn-device-handoff`. The Mamba pool can now make the gate wait, which it never did at 2S + 1: with the hand-off a request in its first phase-2 step holds its probe next to its running slot, and with `--admission-overlap` every admission in flight reserves its phase-2 peak, so overlapped admissions wait on the Mamba pool earlier than without the flag (a `CAPACITY_WAIT` naming the Mamba pool; nothing is overcommitted). For example at 4 sessions, with two admissions in flight holding their probes and nothing decoding, a third waits with the flag (5 slots) and is admitted without it (9). Tests: `test_gdn_inplace.py` (the real `MambaManager`, the gate at 16 / 24 / 32 sessions, end to end on one and three sessions, async and with the hand-off). It needs its own GPU test (token-exact against the server without it) before any benchmark uses it. With up to 32 sessions (integrate-1116; CPU only): at 32 sessions K = S + 1 = 33; at 262,144 tokens with 4,096-token replies the launcher then takes every K up to 32 at 24 and 25 GiB (without the flag 25 GiB takes K ≤ 25 and 24 GiB K ≤ 20, `running.md` section 4.4); on the fakes, `goal_query` at 24 sessions waits once for the Mamba pool without the flag and never with it, and 32 sessions decode in one batch with a format-error rollback (a rebuild at local turn 0) in every fourth session (`test_inplace_32.py`).

### 4.8 CUDA graphs

`--cuda-graphs off` (the default with `--no-speed-defaults`; without it `full` is the default, section 4.15) is the eager server above: the vLLM command, `startup.json`, its pins and the evidence are byte-identical to those of a `--no-speed-defaults` launch without the flag (CPU tests against `b37044f`, `test_cudagraph.py`).

`--cuda-graphs piecewise`, `full` or `full-decode` replaces `--enforce-eager` in the vLLM command with a pinned `--compilation-config` (the scheduling is not changed by it: synchronous, unless the server is started with `--async-scheduling`, which a CUDA-graph server takes too; section 4.15):

| Mode | `--compilation-config` | What vLLM 0.24 captures |
| --- | --- | --- |
| `piecewise` | `{"cudagraph_mode":"PIECEWISE","mode":"VLLM_COMPILE"}` | the compiled pieces between FlashAttention, the KV-cache update and the Gated-DeltaNet core, which run eagerly every step and read that step's selective sequence lengths, slot mapping, block tables and Mamba state indices |
| `full` | `{"cudagraph_mode":"FULL_AND_PIECEWISE","mode":"VLLM_COMPILE"}` (stock vLLM's default) | whole uniform-decode steps, attention included; mixed steps stay piecewise. The runner binds every full-attention group to its physical sequence-length buffer at capture and at replay |
| `full-decode` | `{"cudagraph_mode":"FULL_DECODE_ONLY","mode":"NONE"}` | whole uniform-decode steps of the eager kernels, without torch.compile; prefill, mixed steps and phase 1 run eagerly as with `off`. The same binding as `full` |

- **Pins and checks.** `startup.json` records `cuda_graphs` and the effective config `enforce_eager: false` plus the compilation config. At startup the frontend compares vLLM's parsed arguments, and the worker checks the resolved configuration (compilation mode, CUDA-graph mode, capture sizes and, when compiled, the three ops kept outside the graphs) and refuses any difference; with the flag off it refuses a runner that captured graphs.
- **Evidence.** `worker-attached.json` gains a `cuda_graphs` record (mode, resolved configuration, capture sizes); nothing is checked per request or step.
- **With several sessions.** vLLM sizes the captured batches from `max_num_seqs`: one per startup task, or K with `--max-running-sessions K` (section [4.4](running.md#44-several-sessions-on-one-server)). The sizes are 1, 2, 4 and multiples of 8 up to 2 × `max_num_seqs` (1, 2, 4, 8, 16, 24, 32 at 16 sessions), so every decode step of up to 16 running sessions has a graph (CPU test `test_int_flags.py`, vLLM 0.24's own sizing code). Above 16 (`MAX_SESSIONS` 32, not GPU-validated): up to 40 at K = 20, 48 at K = 24 and 64 at K = 32 (CPU test `test_ms32.py`). vLLM 0.24's dispatcher (`vllm/v1/cudagraph_dispatcher.py`) captures FULL uniform-decode graphs only for the sizes up to `max_num_seqs`: at K = 24 and 32, K itself is a size, so every decode step of up to K requests replays a FULL graph in `full`; at K = 20 (as at 12) a step of 17 to 20 requests is padded to 24 and replays the piecewise graph. The extra sizes are small graphs in vLLM's shared graph pool (stock vLLM captures up to 512 in 0.13 GiB).
- **Phase 1** (and the Goal forward) runs without a CUDA graph and unpadded: compiled code in `piecewise` and `full`, the eager kernels in `full-decode`. Decode steps (and, except in `full-decode`, small mixed steps) use the graphs. With `--phase1-in-step` (section 4.10) a phase 1 that joins a decode step runs with that step: with the piecewise graphs in `piecewise` and `full`, eagerly in `full-decode`. With `--phase1-graph-tokens T` (section 4.10; opt-in, `piecewise` and `full` only) vLLM also captures piecewise graphs up to T tokens, and a separate phase-1 or Goal-forward pass of up to T tokens is padded and replays one.
- **Results.** torch.compile (`piecewise`, `full`) replaces vLLM's custom kernels with compiled ones and changes bf16 numerics, so greedy outputs can differ from the eager server. `full-decode` keeps the eager kernels; it changes only what capture itself changes: FlashAttention's split limit for batches up to the largest capture size, and padding to a capture size. Prompt and transcript token exactness does not depend on the mode. With torch.compile, startup takes about a minute longer on a cold compile cache (stock vLLM 0.24.0 on one GH200: +58 s; capture 4 s, 0.13 GiB).
- **Comparing.** Graph-mode outputs, and with them the query policies' page choices, can differ from the eager server's, so compare a CUDA-graph server with stock vLLM in the same mode. Even in eager mode, batched runs are not token-identical from run to run (section 4.4).
- **Gemma 4** (section 4.14) takes the same modes on its window layout, with its global group bound.

**On the GPU.** Job results: [docs/status.md](status.md); limits: [docs/known-limits.md](known-limits.md) (2.3); the GPU runs this section described until 2026-11-16: [frozen notes, 4.8](history/reference-gpu-notes.md#from-section-48-cuda-graphs).

### 4.9 Context limit and reply bound

Three launcher options size a server for longer agent runs. Without them the vLLM command, `startup.json`, its pins, the evidence and the page selections are byte-identical to `8c5f4d0` (CPU tests). `--max-model-len 262144` is a later third context choice; adding it left the defaults and the 131072 profile unchanged (CPU tests, `test_ctx_256k.py`).

| Option | Default | Other choice | What it pins |
| --- | --- | --- | --- |
| `--max-tokens` | 1536 (the PoC's reply bound) | 4096 | `startup.json` `max_tokens` |
| `--max-model-len` | 65536 | 131072 or 262144 | vLLM's `--max-model-len` and `effective_server_config.max_model_len` |
| `--dram-arena-gib N` | room for every running session at the context limit | one pinned page arena of N GiB for all sessions, decoupled layout only | `startup.json` `dram_arena_pages` |

- **KV cache size (`--kv-cache-gib N`).** The GPU KV cache these limits must fit: 8 GiB by default, or 16, 24, 25 or 32 on the Qwen profile; the Gemma 4 profile takes 24, 25, 28 or 32 (section 4.14). The refusals and capacity tables below say which sizes take a given context limit and session count.
- **Choosing the limit.** A longer limit needs more GPU KV and pinned host memory for the same sessions (the refusals below), so use the shortest one that holds the agent's histories, prompt plus reply: with 4096-token replies, prompts of up to 61,440 tokens at 65536, 126,976 at 131072 and 258,048 at 262144. 262144 is the model's native context; there is no longer choice.
- **Reply bound.** A server setting, not part of the agent protocol: the frontend's live controller and the engine hold the pinned value; the Mini-SWE-Agent XML route fixes it on every request and the engine refuses any other value before allocation. The server still decodes greedily and ignores the client's sampling fields. The capacity gate reserves every request's pages up to ⌈(prompt + max_tokens) / P⌉, and the launcher's margin is one reply, ⌈max_tokens / P⌉ + 1 blocks (97 at 1536, 257 at 4096 with 16-token pages). vLLM caps a reply at the context limit minus the prompt, so a prompt holds at most the context limit minus the reply bound (61,440 tokens at 65,536 with 4096-token replies; 126,976 at 131,072; 258,048 at 262,144).
- **Startup checks, once.** The frontend compares vLLM's parsed `--max-model-len` with the pin; the engine checks its resolved `max_model_len` and sends the worker a context record (`max_model_len`, `max_tokens`) in its startup record when either is not the default; the worker checks the record against its runner and echoes it in `worker-attached.json`; the engine and the frontend compare the echo, and `ready.json` adds `context`. A 262144-token server also sets its request caps (below) once, in the frontend and in the engine. Nothing is checked per request or step. The page catalog bound, the attention and Gated-DeltaNet rows and the pinned page arena follow vLLM's `max_model_len` (at P = 16 and 131072 tokens a catalog of 8,192 pages and an arena of 8,193 pages per session; at 262144, 16,384 and 16,385).
- **Launcher refusals.** One session's turn at the context limit must fit the attention pool (decoupled layouts: ⌈L / P⌉ + 1 + ⌈16,384 / P⌉ + ⌈max_tokens / P⌉ + 1 blocks plus the 1 % watermark) or the shared 784-token pool (⌈L / 784⌉ + 1 + 6 + ⌈max_tokens / 784⌉ + 1 blocks plus the watermark, what vLLM's own startup check demands); at 131072 tokens this refuses `--kv-cache-gib 8` in every layout. The worst-case pinned host memory (the connector's CPU pool, one 154 MB Gated-DeltaNet carry per running session (two with `--gdn-device-handoff`) and a host copy of every attention page of every running session at the limit) must stay within 128 GiB (`PINNED_HOST_GIB` in `serve.py`; the validated jobs requested 200 GiB). The figures of this item and of the 262144 item below are those of vLLM's 32 GiB pool (`--no-connector-pool-gib`); the default 1 GiB pool needs 31 GiB less (next item). At 65536 tokens up to 16 running sessions need at most 99.4 GiB (101.7 GiB with `--gdn-device-handoff`) and pass. A chat-text pool may run up to 24 (`MAX_CHAT_TEXT_RUNNING` in `remote_ra_live_v2/sessions.py`); at 65536 tokens and P = 16 the budget holds 23 of them (22 with `--gdn-device-handoff` or at 784-token pages): 20 need 115.1 GiB, 24 need 131.7 GiB. At 131072 tokens 11 running sessions fit (121.8 GiB at P = 16) and 16 need 162.5 GiB, so 16 sessions need `--dram-arena-gib` (88 GiB gives 122.3 GiB). A capture beyond a capped arena fails that request (`DRAM_ARENA_EXHAUSTED`); nothing is spilled or evicted. 16 sessions at an average of 90,000 tokens hold 87.9 GiB of pages. When `--dram-arena-gib` itself is too large for the budget, the refusal names the largest arena that fits (93 GiB for 16 sessions, 91 GiB with `--gdn-device-handoff`).
- **Connector CPU pool (`--connector-pool-gib N`; 1 by default, section 4.15, `--no-connector-pool-gib` for vLLM's 32 GiB; on every benchmark server).** The connector's CPU pool above belongs to vLLM's `OffloadingConnector`, which `serve.py` always configures (`--kv-transfer-config`); vLLM pins and zeroes it when the worker starts, whatever `--kv-cache-gib` is. This runtime never moves data through it. At startup it isolates the connector (`remote_ra_http/connector.py`): every prefix lookup returns 0 tokens, any load from the pool is refused, finished requests store nothing, and the connector never gets a transfer job. Pages copied to the host and restored from it use the runtime's own pinned memory instead: the page arena of section 4.6 (in the shared pool, one pinned copy per captured page) and the Gated-DeltaNet carries. The connector itself stays, because the runtime's isolation and checks hook into it.
  - `--connector-pool-gib N` (N from 1 to 31; 1 by default, section 4.15) gives the pool N GiB instead of 32, and the budget counts N GiB. One GiB still holds 20 blocks of 784 tokens, or 1,024 of 16 tokens, and saves about 31 GiB of pinned host memory per server at every `--kv-cache-gib`. At 65536 tokens up to 16 running sessions then need at most 68.4 GiB instead of 99.4 GiB (70.7 instead of 101.7 with `--gdn-device-handoff`), and a chat-text pool of 24 at most 105.5 GiB, so every configuration passes; at 131072 tokens 15 running sessions fit without `--dram-arena-gib`, and 16 take an arena of at most 124 GiB (122 GiB with `--gdn-device-handoff`); at 262144 tokens 7 fit without an arena. This matters for a job that requests only one GH200's share of the node's host memory.
  - `startup.json` records `connector_pool_bytes`, and vLLM gets `cpu_bytes_to_use` = N GiB. The engine checks that its vLLM configuration has the pinned value, and the worker checks that the allocated pool holds at least one block per KV tensor and at most N GiB, once each at startup (`remote_ra_live_v2/connector_guard.py`). With `--no-connector-pool-gib` (or `--no-speed-defaults`) the vLLM command, the startup config and the launcher's refusals are those of the former 32-GiB server. CPU tests: `test_connector_pool.py`.
- **Token and frame caps** (measured on the CPU with the pinned tokenizer, test `test_align_ctx.TokenFrameCapTests`): Mini-SWE-Agent requests of 126,976 tokens with SWE-like observations (code listings, padded `pytest -v` output, FITS header cards, at most 10,000 characters each) need 3.3 to 5.3 source bytes per token, under 0.66 MiB of the 1 MiB source limit (the test's bound), under 0.3 MB of the 1 MiB core request limit (131,072 ids are at most 0.66 MB) and under 1.5 MB of the 4 MiB frame limit; 126,976 tokens are within the 131,072-token bound. The source limit binds above 8.26 bytes per token at 126,976 tokens (16.4 at 64,000): banner-only logs (one 80-column rule per token, about 19 bytes per token) are refused before admission, at either context. These are the caps at 65536 and 131072, unchanged; a 262144-token server doubles them (next item).
- **262144 tokens.** `--max-model-len 262144` is the model's native context (`max_position_embeddings` 262144 with the default rope): no YaRN, no override and no new pin. Anything longer would need YaRN, which changes outputs at every length. As with 131072, only vLLM's `--max-model-len` and `effective_server_config.max_model_len` change, and the page catalog (16,384 pages at P = 16), the rows and the arena follow vLLM's `max_model_len`. One request's byte and token caps scale with the pinned limit (table below). On the CPU with the pinned tokenizer (test `test_ctx_256k.TokenFrameCapTests256`), 258,048-token requests (262,144 minus a 4096-token reply) need 3.3 (code listings, README text) to 5.2 (FITS header cards) source bytes per token: 0.84 to 1.35 MB of source, so the padded and FITS histories exceed the former 1 MiB. They need at most 0.61 MB of core request and 2.9 MB of frame. The 2 MiB source cap binds above 8.13 bytes per token, so banner-only logs are still refused before admission.
  - Launcher refusals at 262144 tokens. One session's turn needs 16,385 + 1,024 + 257 blocks plus the watermark (17,824 at 16 GiB with 4096-token replies), so `--kv-cache-gib 8` and `16` are refused in every layout and at every session count; 24, 25 and 32 pass at 1 to 16 sessions. The shared 784-token pool needs 352 blocks with 4096-token replies (333 usable at 16 GiB, 500 at 24 GiB).
  - Pinned host memory at 262144 tokens: at most 5 running sessions fit without an arena (113.0 GiB at P = 16). 6 need 129.1 GiB and 16 need 290.5 GiB; a session pool counts its K running sessions. 16 sessions need `--dram-arena-gib` between 17 GiB (one session at the limit, 16,385 pages) and 93 GiB (91 GiB with `--gdn-device-handoff`). 93 GiB holds 95,232 tokens per session on average, 88 GiB 90,112. 16 sessions all at 262,144 tokens cannot fit: their pages alone are 256 GiB.
  - Not changed yet: the 300-s admission wait and 360-s lease; phase 1 still takes at most 16,384 tokens per appended message; the per-request work outside the GPU that grows with the prompt (prompt hashes, JSON snapshots, detokenization, evidence rows with every prompt id); arena fairness (`DRAM_ARENA_EXHAUSTED` fails whichever session captures next); the capacity of a 262K rebuild under the strict rule (17,409 blocks).
- **Lifetime request bound.** max(1,024, 256 × T) for T registered tasks: the per-session bound of 256 requests (the frontend's turn bound, the engine's turn ordinal and generation bound) summed over the tasks, so it never refuses a request a session could still make. 32 tasks of 120-step agents make at most 3,840 requests against 8,192; a `CAPACITY_WAIT` retry takes no lifetime record. Per-session limits stay at 256 requests, so a step limit above 256 is refused by `run_agents.sh`.

### 4.10 Admission optimizations (opt-in)

An admission is the engine's work on a new turn before it decodes: phase 1, for `goal_query` the Goal, the selection and the reservation (section 5). By default admissions run one at a time in arrival order, phase 1 runs as a separate forward pass while the running requests wait, and the Gated-DeltaNet state goes from phase 1 to phase 2 through pinned host memory. Four launcher flags change this, each off by default (the letters are the admission designs that the code comments name):

| Flag | Default | What it does | What it pins at startup |
| --- | --- | --- | --- |
| `--gdn-device-handoff` (e) | off | hands the Gated-DeltaNet state from phase 1 to phase 2 on the device instead of through host copies | `startup.json` `admission.gdn_device_handoff` = `true` |
| `--phase1-in-step` (b) | off | runs an admission's phase 1 inside the next decode step instead of a separate pass | `admission.phase1_in_step` = `true` |
| `--admission-overlap K` (f) | 1 (off) | keeps up to K admissions in flight, 2 ≤ K ≤ the sessions running together | `admission.admission_overlap` = `{"permits": K, "admission_seconds": 300 + 120(K − 1), "lease_seconds": 360 + 120(K − 1)}` |
| `--goal-overlap` | off | `goal_query` with `--goal-rewriter-model`: runs a turn's phase 1 while its Goal is built, then the Goal forward as its own pass | `admission.goal_overlap` = `true` |
| `--phase1-graph-tokens T` (d) | 0 (off) | Qwen with `--cuda-graphs piecewise` or `full`: vLLM also captures piecewise CUDA graphs up to T tokens, and a separate phase-1 or Goal-forward pass of up to T tokens runs with them instead of without a graph (not GPU-validated; its item below) | `phase1_graphs` = `{"capture_sizes": [...], "tokens": T}` and the compilation config's `cudagraph_capture_sizes` (not in `admission`) |

`startup.json` has an `admission` record only when a flag is on; with all of them off the startup config, the evidence and the vLLM command gain nothing. `--phase1-graph-tokens` pins its own record, `phase1_graphs`, next to `cuda_graphs` (its item below). The engine and the worker check the record once at startup, the worker echoes it in `worker-attached.json` and `ready.json` records it; nothing is checked per request or step (`remote_ra_live_v2/admission_flags.py`; CPU tests `test_gdn_handoff.py`, `test_adm_phase1_step.py`, `test_adm_overlap.py`, `test_goal_overlap.py`). `examples/slurm/serve_gh200.sh` passes none of these flags (nor `--cuda-graphs`), so its server runs the speed defaults of section 4.15 (CUDA graphs `full` and the decode fast paths).

- **`--gdn-device-handoff`.** Phase 1 keeps its probe slot on the GPU, and phase 2's first step copies it device to device into the phase-2 slot; Mamba-block crossings copy on the device too. The committed carry is the only host copy: at the end of a turn it is copied to the host asynchronously, into whichever of the session's two pinned carry buffers does not hold the committed carry, and joined by the drain; phase 1 restores it from there (`remote_ra_live_v2/gdn_handoff.py`). A continuing turn's phase 2 holds three Gated-DeltaNet slots (running, crossing and the held probe slot), and the capacity gate counts three. The launcher's pinned-host budget (section 4.9) counts the second carry buffer: 153.9 MB more per running session (2.3 GiB at 16 sessions; 16 sessions at 131,072 tokens with `--dram-arena-gib 88` need 124.6 GiB instead of 122.3). The transient pinned bounce copies of indexed restores, freed when the restore is joined, are not counted. Every `runtime.jsonl` row adds `restore.d2d_bytes` (section 8).
- **`--phase1-in-step`.** The admission parks its phase 1, and the engine adds it to the next decode step as one more row next to the running requests (a mixed step); the admission resumes once that step has collected it (`remote_ra_live_v2/phase1_step.py`). Phase 1 keeps the separate pass when nothing else runs (`probe_only`), when its tokens do not fit what the step leaves of the 16,384-token step budget, or when no batch row is free for two steps (`fallback`); a phase 1 that carries `goal_query`'s Goal forward also stays a separate pass, and a server that runs one session at a time (`max_num_seqs` 1) always takes it. Phase 1 is never chunked. With CUDA graphs, a step that carries a phase 1 runs with the piecewise graphs (`piecewise`, `full`) or eagerly (`full-decode`). Native files record `phase1_mode` and the time parked.
- **`--admission-overlap K`.** Up to K admissions are in flight at once: the frontend's admission lock becomes a first-come-first-served semaphore with K permits, and every session gets its own Goal thread and its own copy of the Goal constructor, so while one admission waits for its Goal (a rewriter call) or its in-step phase 1, the others proceed (`remote_ra_live_v2/admission_overlap.py`). The Goal rewriter is still one process that serves one request at a time, and phase 1 still runs for one admission at a time. How long each rewriter call waited for that process and how long it took are recorded per call in `goals.jsonl` (`wait_ms`, `call_ms`) and per request in the native file (`goal_rewrite_wait_ms`, `goal_rewrite_call_ms`, next to `goal_construct_ms`; section 8). Without the flag only one Goal is built at a time, so `wait_ms` stays near 0 and the queueing is the admission wait in front of the engine. The frontend's wait for an admission's acknowledgement and the engine lease grow with K and are pinned at startup: 300 + 120(K − 1) s and 60 s more (2,100 s and 2,160 s at K = 16; 300 s and 360 s without the flag). Nothing is preempted: every admission in flight holds a capacity reservation until it is accepted, and an admission that does not fit next to the running requests and the other reservations is refused with `CAPACITY_WAIT` and retried, as in section 4.4. With all three flags an admission reserves the larger of its two peaks; in the Mamba pool that is 9 blocks for phase 2 (three Gated-DeltaNet slots; 6 without `--gdn-device-handoff`) against 3 for phase 1 (6 with a Goal forward), so about 3 admissions fit at once at 5 sessions (11 slots, 33 blocks) and about 11 at 16 sessions (33 slots, 100 blocks); the others retry. Each refusal writes an `engine_rejected` line with a `traceback` field to the server log (section 6.3): expected, not a crash.
- **`--goal-overlap` (the Gemma 4 profile takes it too, section 4.14).** For `goal_query` with `--goal-rewriter-model`, on a server whose sessions decode together; with one session at a time it changes nothing.
  - **Order.** A turn starts its Goal on its Goal thread where it did before, but does not wait for it. Its phase 1 runs meanwhile: in place, or inside a decode step with `--phase1-in-step`, now also on turns that need a Goal forward. The admission then waits for the Goal only if it is not built yet. If the turn needs a Goal forward (the cold forward of the Goal query text that gives the query vector), that forward runs as its own short probe-only pass, and the selection follows.
  - **Same result.** The Goal is built as before. The Goal forward always ran on its own blocks, from position 0, with no history KV, none of the new tokens and no Gated-DeltaNet state. Run separately it gives the same Goal vector, so the Page scores and the selection are the same.
  - **Gain and cost.** A turn whose Goal takes longer than its phase 1 is admitted about the phase-1 time earlier: the saving is at most the smaller of `goal_construct_ms` and `goal_overlap_ms` (the overlap window, from a Goal's start to its join). A turn with a Goal forward costs one more probe-only pass. Measured windows: [frozen notes, 4.10](history/reference-gpu-notes.md#from-section-410-admission-optimizations).
  - **Leases.** With `--admission-overlap K`, a phase 1 no longer waits for an admission that has drained its own phase 1 and waits for its Goal; it waits only for a lease that is not drained.
  - **Evidence.** Native files add `goal_overlap_ms`, and on a turn with a Goal forward `goal_forward_ms` and the worker frame `goal_forward`, which holds its drain (a `phase1_drain` frame for it follows only a failed Goal forward). `runtime.jsonl` rows are those of a server without the flag (section 8).
  - **No new hashing.** The Goal forward's lease and reply are neither signed nor digested: the worker checks them field by field against the turn's phase-1 lease. Its SHA-256 and HMAC calls are those of a server without the flag (the CPU test counts them).
  - **Sources and tests.** `remote_ra_live_v2/goal_overlap.py`; the design and the equivalence argument are in `docs/goal-overlap/DESIGN.md` (the Gemma 4 profile: its section 9). The CPU tests (`test_goal_overlap.py`; Gemma: `test_gemma_goal_overlap.py`) check that every turn's Goal, Goal vector, selection and tokens equal the flag-off server's, with and without the other three flags.
  - **With thinking on (integrate-1031 and keep-overlap).** It composes with `--thinking-history strip` (chat-text, Qwen): the overlap changes when phase 1 runs, not what it computes, and the drained phase-1 record keeps the phase-1 Gated-DeltaNet state that the strip completion commits at the cut (section 6.9). `test_goal_overlap_thinking.py` runs Terminus 2 `goal_query` sessions with summaries under pool pressure on a strip server with the flag, alone and with `--admission-overlap 4`: every strip check holds, every Goal that needs a forward runs it as its own pass after phase 1's drain, and every turn's Goal, Goal hash and selection equal those of the same run without the flag. It composes with `--enable-thinking` alone too (stage 1's keep mode, chat-text and mswea-xml; keep-overlap): the keep mode changes only the transcripts, the replies and their evidence, the engine and the worker run the thinking-off path, and the Goal's input is built at the same point from the same previous reply (its content). `test_goal_overlap_thinking.py` runs the same Terminus 2 sessions on a keep server whose clients send each reasoning back, alone and with `--admission-overlap 4`, and three mswea-xml (SWE-bench) sessions together on a `goal_query` server with parked Goals, one sending every reasoning back, one dropping one and one changing one (each a rebuild): every prompt is the template's render with the reasoning kept, the turns append where the reasoning came back and rebuild elsewhere, and every turn's Goal, Goal vector, selection, prompt and output tokens equal those of the same run without the flag. Mutations (the Goal forward skipped, a stale Goal at the forward, an append rule that ignores the reasoning, the XML marker stop not armed after `</think>`, a Goal that reads the reasoning) fail it.
- **`--phase1-graph-tokens T` (option (d); off by default, 0; the Qwen profile with `--cuda-graphs piecewise` or `full`; not GPU-validated: job 3569412 ran it at `b6f6b9f`, a partial pass ([docs/status.md](status.md); its findings: [History](history.md#integrate-1112-2026-11-12))).** Without it a separate phase-1 pass, and a Goal forward, runs without a CUDA graph (section 4.8), and so does every step above vLLM's largest capture size, 2 × `max_num_seqs` tokens (32 at 16 sessions). In the Qwen runs of jobs 3539242 and 3461703 (SWE-bench, the `recent_fill` and `observation_query` servers) and 3461661 (Terminal-Bench, `observation_query`), the phase-1 RPC of a continuing turn took 91–104 ms at the median of every token bin up to 512 tokens (0–128, 128–256, 256–512) and 106–110 ms at 512–1,024, and a least-squares line over the turns of up to 4,096 tokens rises by 51–84 ms per 1,000 tokens: of a 200-token pass, about 10–17 ms follow its tokens (`phase1_ns` and `forward_tokens` of the jobs' native files; the step profile below is to time the rest).
  - **What changes.** vLLM's capture sizes are pinned: its own sizes for the running sequences (the list it derives without the option, so decode steps and the FULL decode graphs are unchanged), then 64, 96, 128, 192, 256, 320, 384, 448, 512, 640, 768, 896, 1024, 1280, 1536, 1792 and 2048 up to T (one of 64, 128, 256, 512, 1024 and 2048); above 256 tokens a pass is padded by less than 25 %. A separate phase-1 or Goal-forward pass is dispatched to the piecewise graph of the next captured size when its tokens fit, and runs without a graph above T; it never replays a FULL graph. Every other step keeps vLLM's dispatch with the larger sizes, so a mixed step of up to T tokens runs piecewise too: with `--phase1-in-step` a decode step that carries a phase 1, and any step with a prefill chunk. The probe's hooks run outside the captured pieces and read only its own rows and positions, never the padding.
  - **Results.** Padding changes the shapes of the compiled pieces' matrix products, so phase 1's KV, Gated-DeltaNet state and vectors, the rows of a mixed step that is now padded, and with them a near-tie in a selection or a reply, can differ in the last bits from the unpadded pass without a graph, as for the graph modes of section 4.8: compare policies at the same setting. The plumbing is exact: on the CPU fakes, whose padded rows hold NaN, every reply, selection, carry and Page vector equals the server's without the option.
  - **Pins and checks.** `startup.json` records `phase1_graphs` = `{"capture_sizes": [...], "tokens": T}`, and the compilation config (in the vLLM command's `--compilation-config` too) records `cudagraph_capture_sizes`. The frontend compares vLLM's parsed sizes; the engine sends the record to the worker and requires its echo; the worker requires vLLM's resolved capture sizes to be exactly the pinned ones, records `probe_forward: "piecewise"` and `phase1_graph_tokens` in its `cuda_graphs` record and echoes `phase1_graphs` in `worker-attached.json`; `ready.json` records it. Nothing is checked per request or step; the runner reads one more attribute per step. With 0 the vLLM command, the startup config, its pins and the evidence are those of a launch without the option, and the runner dispatches every step as at `ba4d1ba` (identity probe; CPU tests).
  - **Combinations.** On the Qwen profile the launcher refuses it only with `--cuda-graphs off` and `full-decode` (no piecewise graphs). The CPU tests run it end to end with phase 1 in place, with `goal_query`'s Goal forward inside phase 1, with `--phase1-in-step`, with `--gdn-device-handoff` and with `--async-scheduling`: under async a separate pass runs after the batch in flight is drained, as without the option, and every turn's tokens, selections, Page vectors and carries equal the synchronous server's without the option. `--goal-overlap` (its Goal forward is such a pass too) and the thinking options are accepted but not tested end to end with it. The Gemma 4 profile refuses it (v1: neither built nor tested on the window layout; its phase-1 passes took 101 s of the 2,710-s run of job 3462014, 3.7 %).
  - **To check on the GPU.** That vLLM keeps the pinned sizes and captures FULL graphs for the decode sizes only (its dispatcher is not part of the overlay; the CPU tests model it); the startup time and the graph memory (each extra size is one more piecewise capture, and the graph pool comes out of the GPU memory left next to the pinned KV cache, `--kv-cache-gib`, and the Goal rewriter); the phase-1 times by token bin, with the option and without it; vectors and selections against the server without it on identical prompts.
  - **Step profile.** With `REMOTE_RA_STEP_PROFILE=1` each separate phase-1 or Goal-forward pass also gets a record of its own, with the graph mode vLLM chose and its token bin (section 4.11).
  - **Sources and tests.** `remote_ra_live_v2/phase1_graphs.py`, `cuda_graphs.py` (`probe_piecewise`), `hooks.py`, the runner's dispatch (`vllm/v1/worker/gpu_model_runner.py`), `serve.py`; `test_phase1_graphs.py` (the sizes against vLLM's own sizing code, the pins and refusals, the dispatch against the `ba4d1ba` runner's and a model of vLLM's dispatcher, and three sessions on the fakes with padded steps: in place, `goal_query`, `--phase1-in-step`, `--gdn-device-handoff` and `--async-scheduling`).
- **`--goal-rewriter-batch N` (off by default; `goal_query` with `--goal-rewriter-model` and `--admission-overlap K`, 2 ≤ N ≤ 16, N ≤ K; the Gemma 4 profile takes it too, with its own default token cap, section 4.14).** With `--admission-overlap 16` the sessions' Goal rewriter calls queue for the one rewriter process: in the unbatched 16-session SWE-bench job 3404696 a rewriter call queued 98.2 s and a Goal with a rewriter call took 108.8 s at the median. With this flag the calls that queue are sent together, up to N at a time, to a child that runs them as one batched greedy `generate` (`remote_ra_live_v2/goal_rewriter_batch.py`, `goal_rewriter_child.py`):
  - **Unchanged:** when the rewriter is called, what it is sent (the upstream request line, byte for byte), the prompt, the JSON schema and its constraint, `max_new_tokens`, the parsing and validation of each answer (the upstream `PersistentCommandGoalRewriter.rewrite` code runs for every call) and the fallbacks. Each call gets its own answer; a child error or a refused candidate concerns that call only. A batch of one is the upstream `generate`.
  - **Changed:** the model call. The prompts are left-padded into one `generate`, and each row is constrained by its own request's lm-format-enforcer prefix function. **Batched greedy decoding is not bit-identical to one request at a time:** padding and the batch dimension change the order of floating-point reductions, so a near-tie can flip a token, and a rewritten Goal (or its fallback) can differ from the unbatched server's. Compare policies only between servers with the same setting. The child also builds lm-format-enforcer's tokenizer data once instead of for every request (the same allowed tokens; a self-check at the child's start compares a fresh and a cached build, else the per-request build stays).
  - **Timeouts and failures:** the pinned 120-s timeout runs from the send of the call's batch, so the time queued before it is not charged, as before. A timeout, a child exit or an unreadable answer fails every call of that batch with the upstream error (each falls back), and the next batch restarts the child. A CUDA out-of-memory error runs the batch in halves, down to single requests; any other failure of a batched `generate` runs its requests one by one through the upstream code. Each retry starts only after the failed `generate`'s exception is gone, with the CUDA cache emptied before each attempt, and a request that fails alone keeps no traceback (earlier code ran the retries inside the exception handler, whose traceback still held the failed `generate`'s tensors: job 3404230, [frozen notes, 4.10](history/reference-gpu-notes.md#from-section-410-admission-optimizations)). A single call's failure is the upstream fallback.
  - **Token cap (`--goal-rewriter-batch-tokens T`, default 16,384; for the Gemma 4 profile by `--kv-cache-gib`, section 4.14; 0: none).** Each call's thread counts its prompt tokens before it queues, with the pinned checkpoint's tokenizer and the child's own prompt construction. A batch takes the queued calls in order while its size times its longest prompt stays within T, and stops at the first call that does not fit; a call over T alone (or one that could not be counted) runs as a batch of one, as unbatched. No call jumps the queue. The default leaves 1 GiB of the GPU free next to the 27B server, by job 3404230: CUDA can allocate 97,362 MiB (95.08 GiB, by the child's own out-of-memory report; nvidia-smi shows 97,871 MiB), the server process held 90,102 MiB (87.99 GiB) and the rest of the child 2,519 MiB (the weights, 1,137 MiB; the CUDA context, kernels and workspaces, 1,382 MiB), which leaves 4,741 MiB, 3,717 MiB for one batch after the margin. By Qwen3-0.6B's sizes (28 layers, 8 KV heads of 128, bf16) a padded prompt token needs 112 KiB of KV cache and at most 40 KiB of one layer's activations, a generated token 112 KiB, and a padded batch of B prompts of L tokens at most 3 B L² bytes of attention mask: the widest batch of 16,384 padded tokens (worst as 2 × 8,192, with 384 new tokens per row) needs 2,900 MiB, 3,770 MiB with the 1.3× allocator slack the two runs suggest. The cap that fits is 20,400 without slack and 16,100 with it; 16,384 lies between. A local replay of job 3404230's batches under the cap estimated that it keeps most of the batching's saving of child time (an estimate; its output was not archived).
  - **What it pins:** `startup.json` and `ready.json` record `goal_rewriter_batch: N` and `goal_rewriter_batch_tokens: T`, and the engine checks once, at startup, that its rewriter runs batched with N and T. Each `goals.jsonl` exchange of a batched server adds `batch_id` and `batch_size` (section 8). Without the flag the startup config, the rewriter command and the evidence are unchanged.
  - **GPU memory:** Qwen3-0.6B needs about 112 KiB of KV cache per prompt token, so a batch of 16 prompts of 4–6K tokens needs 7–10 GiB next to the 27B server. Start with N = 4 and read the prompt sizes (`input_tokens`) in `goals.jsonl`. After every batched `generate` the child empties the CUDA cache, so that the batch's peak is not kept reserved between batches, where neither cuDNN, the driver nor the 27B server can use it (rewriter-batch-fix; in job 3404230 the cache was kept).
  - **CPU tests (`test_goal_rewriter_batch.py`):** a fake model that follows Transformers' batched greedy `generate` and a fake enforcer. Each batched answer equals the upstream answer of that request alone, and sixteen sessions' Goals equal the unbatched ones (N = 16 and N = 4). The tests also cover the out-of-memory and failure paths, a timeout, a mismatched answer, a cancelled admission and shutdown, and, on a fake GPU whose tensors stay allocated while a frame or a traceback holds them and whose cached blocks cuDNN cannot use, the four failure modes of job 3404230 (each test failed before the fix).
- **`--goal-rewriter-engine vllm` (off by default: `hf`; `goal_query` with `--goal-rewriter-model` and `--admission-overlap K ≥ 2`, not with `--goal-rewriter-batch`; both model profiles; experimental outside the README's stable command, where it is validated (job 3576565, [known limit 3.2](known-limits.md#32-the-vllm-goal-rewriter-is-validated-only-inside-the-stable-command)); [docs/rewriter-vllm/DESIGN.md](rewriter-vllm/DESIGN.md)).** The rewriter's calls go to one child that runs Qwen3-0.6B in a small vLLM `AsyncLLM` engine with continuous batching, so several calls are in flight at once instead of one Hugging Face `generate` at a time (`remote_ra_live_v2/goal_rewriter_vllm.py`, `goal_rewriter_vllm_child.py`):
  - **Unchanged:** when the rewriter is called, what it is sent (the upstream request line), the prompt (the vendored script's own construction and the Hugging Face tokenizer's ids, so `input_tokens` is the same count), the JSON schema, greedy decoding, `max_new_tokens`, the decode, the parsing and validation (the upstream `PersistentCommandGoalRewriter.rewrite` code runs for every call), the fallbacks, the 120-s call timeout, the answer line and every `goals.jsonl` field.

### 4.11 Decode fast path (on by default)

On by default (section 4.15): `--no-decode-fastpath` turns all three stages off, `--no-decode-fastpath2` the second and third, `--no-decode-fastpath3` the third, `--no-deferred-completion-io` the deferred completion files. The text below describes each switch as given.

In the decode check of job 3366128 ([frozen notes, 4.11](history/reference-gpu-notes.md#from-section-411-decode-fast-path)), with 16 requests running on SWE-like histories and 16-token pages, this runtime without the fast path decoded 1.8 times slower than stock vLLM: 53.8 ms against 29.2 ms per token (both with synchronous scheduling). The cause is host work in each decode step that grows with the number of running requests times the Pages per request.

- Each running request's per-step `allocation_update` RPC counted its own blocks by scanning every allocation claim of every running request (`remote_ra_http/evidence.py`).
- A long request holds 49 times as many Pages at 16 tokens as at 784 tokens, so the scan grew with the smaller page.
- In the `full` SWE-bench run (job 3357655) these calls took 245.9 s, 13.8 % of the run (321,338 calls, 0.765 ms each).

`--decode-fastpath` (on by default and recommended for every policy, section 4.15; `--no-decode-fastpath` turns it off) produces the same values with less work:

- A per-request count of claimed blocks replaces the scan (`remote_ra_live_v2/decode_fastpath.py`).
- The step lease type-checks only the attention leases added since the last step.
- The step positions are read from the device once per step instead of once or twice per request.
- The worker drains the device once per step instead of once per request.
- The action-marker stop decodes only the new token unless that token contains `>`. This is exact because the marker is ASCII and ends in `>`.

**What the flag pins.**

- With the flag, `startup.json` records `decode_fastpath: true`. The worker echoes it in its evidence, `ready.json` records it, and it is checked once at startup.
- Without the flag, the startup config, the evidence and the vLLM command gain nothing, and the code paths are the previous ones.

**CPU tests (`test_decode_fastpath.py`).**

- The claim counts equal the scan under random changes.
- Leases, positions, refusals and marker decisions are identical, including with the pinned Qwen3.6 tokenizer.
- On the multi-session fakes (16- and 784-token pages, `full` and `observation_query`), the RPC payloads, evidence files, attended Pages and replies are identical with the flag on and off.

**Step profile.** `REMOTE_RA_STEP_PROFILE=1` (an environment variable, off by default) writes one `REMOTE_RA_STEP {json}` line per decode step to the server log.

- Each line holds the host time of each part of the step, and the forward pass timed with CUDA events (no added synchronization).
- `tools/step_profile.py` summarizes the lines.
- It is a diagnostic, not part of the evidence.
- An admission's own work stays out of the steps, but each separate phase-1 or Goal-forward pass is also kept as a record of its own, in each line's `probes` (phase1-graphs): grouped by kind (phase 1, phase 1 with a Goal forward, a Goal forward alone), the CUDA-graph mode vLLM chose for it and a token bin, with per pass the RPC, the runner pass of each forward (state update, inputs, graph dispatch, metadata, the hooks with the carry restore, the forward, the rows and vectors with the state capture), the cleanup and drain, the Page-vector compaction, the receipt, the forward's device time, and the next step's re-add of the rows the pass took out of the batch. With `--phase1-in-step` a step's probe row adds `worker.before.probe` and `worker.after.probe`. `tools/step_profile.py` prints them per label (`--probe-csv` writes the long form). The step records need the synchronous engine loop: with `--async-scheduling` vLLM steps through its batch queue, the install line names that fault and no step is recorded, but these probe records are still written, one line per `REMOTE_RA_STEP_PROFILE_EVERY` passes (default 50) when the next pass starts; the last passes before shutdown are not flushed.
- Every step is also counted under the CUDA-graph mode vLLM's dispatch chose for it, in each line's `dispatch` (phase1-graphs): FULL, PIECEWISE or NONE, with the tokens scheduled in the step, their padded size, and the step and forward times. The iterations whose input pass handled a Cancel or CloseSession command are tagged `cancel` or `close`; `admit` is left to real admissions (before, all three were tagged `admit`). `tools/step_profile.py` prints the steps by tag and mode (`--dispatch-csv` writes them), so the first step after an admission reads against a plain decode step with the same number of requests.

**Torch profile.** `REMOTE_RA_TORCH_PROFILE=<absolute directory>` (an environment variable, off by default) makes `serve.py` pass vLLM's own `--profiler-config {"profiler":"torch","torch_profiler_dir":<directory>}`, so the server has vLLM's `/start_profile` and `/stop_profile` routes, and a trace window is opened and closed through them as on stock vLLM (`VLLM_CUSTOM_SCOPES_FOR_PROFILING=1` adds vLLM's named ranges).

- The startup config, its pins and the server's environment are unchanged, and `--language-model-only` stays the last argument; unset, the vLLM command is unchanged.
- It cannot be combined with `REMOTE_RA_STEP_PROFILE=1` (one profiler at a time).
- It is a diagnostic, not part of the evidence. CPU-tested only (`test_torch_profile.py`).

**Second stage: `--decode-fastpath2` (on by default, section 4.15; needs `--decode-fastpath`).** With 16 requests running, job 3366128 still decoded 6 to 7 ms per token slower than stock vLLM (36.1 against 29.2 ms, both with synchronous scheduling), and its step profile put about 5.5 ms of the 9.2 ms host time per step (the mean over every step with 16 running; 10.2 ms in the W2 round) in this runtime. `--decode-fastpath2` (on by default; `--no-decode-fastpath2` turns it off) removes more of that work and produces the same values:

- One `allocation_batch` worker RPC per decode step carries the allocation updates of every scheduled request, instead of one `allocation_update` RPC per request. An update whose rows did not change since the worker last accepted them is sent without rows (`remote_ra_live_v2/decode_fastpath2.py`, `engine_boundary.py`). The worker applies each entry as before, so every native file keeps one `allocation_update` frame per request per step, with the same fields.
- Less host work per request and step: the native allocation arguments are bound without `inspect`, unchanged rows, leases and tuples are reused instead of rebuilt, a request's active KV bytes are counted per KV group, and the action-marker stop remembers per token id whether the token contains `>`.
- The per-request work after the forward pass (lease close, Page compaction, Gated-DeltaNet capture) runs after vLLM has queued the logits computation, so the two overlap.

**What the flag pins.** With the flag, `startup.json` records `decode_fastpath2: true` (refused without `decode_fastpath: true`). The engine sends it to the worker once at startup; `worker-attached.json` and `ready.json` record it. Without the flag, nothing is added and the code paths are those of `--decode-fastpath` alone.

**Gemma 4** (section 4.14) takes both switches; on its window layout they add the incremental observation of the sliding windows and incremental sliding rows.

**CPU tests (`test_decode_fastpath2.py`).** On the multi-session fakes (784- and 16-token pages, `full` and `observation_query`; `goal_query` with the GDN hand-off and with in-step phase 1), the replies, plans, attended Pages, computed positions, evidence files and per-request frames equal those of `--decode-fastpath` alone, and the batches, expanded entry by entry, equal its `allocation_update` RPCs.

**Third stage: `--decode-fastpath3` (on by default, section 4.15; needs `--decode-fastpath2`).** With both fast paths on, most of the host work this runtime still adds to a decode step before the forward is a fixed cost per running request: the worker's step (observation, claims, materialize, positions, the step lease), the FullAttention row check and the per-request allocation path. `--decode-fastpath3` (on by default; `--no-decode-fastpath3` turns it off) cuts part of it and produces the same values:

- A request whose step appends no FullAttention block and keeps its Mamba rows at the same slot index (15 of 16 steps at 16-token pages) keeps its last step's Mamba leases, key tuples and (empty) claim differences, after the same list, device-row and Mamba checks (`remote_ra_live_v2/decode_fastpath3.py`, `allocation_owner.py`). The device row is compared by its bytes, the same answer as `np.array_equal` for one integer dtype (`allocation_owner.py`, `worker_rows.py`).
- Such a request skips `materialize` when it would only mark the step, and skips its IO-attribution scope when nothing in it can issue IO. Its step lease is built without re-checking Mamba slots that were checked when they were accepted (`qwen.py`).
- The step's position columns are read from the GPU in one copy instead of two.
- On the worker, an allocation update sent without rows is applied and measured directly, with the same frame; the engine binds the modules it imports per request once (`engine_boundary.py`).

**What the flag pins.** With the flag, `startup.json` records `decode_fastpath3: true` (refused without `decode_fastpath2: true`). The engine sends it to the worker once at startup; `worker-attached.json` and `ready.json` record it. Without it nothing is added and the code paths are those of `--decode-fastpath2`.

**CPU tests (`test_decode_fastpath3.py`).**

- The byte compare equals `np.array_equal`, and the one-copy position read equals the two reads, on random inputs.
- The owner's steady observation and materialize equal the full per-step path on randomized step sequences (Page and Mamba crossings, row moves, finishes with block reuse, corruptions): the same results, refusals and state.
- The new step lease equals the old one on random lease sequences, refusals included.
- On the multi-session fakes (784- and 16-token pages, `full` and `observation_query`; `goal_query` with the GDN hand-off and with in-step phase 1; also with vLLM-shaped block tables and MRoPE positions, where the steady paths run), the replies, plans, attended Pages, computed positions, evidence files, per-request frames and RPCs equal those of `--decode-fastpath2` alone. The longer cases run with `REMOTE_RA_SLOW_TESTS=1`.
- CPU micro-benchmark (x86 fakes, 16 requests at 20K tokens, 16-token pages, median of 7 runs): a decode step, all host work including the fakes' own forward, takes 6.15 ms with `--decode-fastpath2` alone and 5.25 ms with `--decode-fastpath3` (the per-step mean; 5.44 and 4.70 ms at the median step).

**Gemma 4** (section 4.14) takes the third switch too (gemma-fastpath3). The cuts above that do not rest on Mamba rows apply unchanged: the rowless allocation entries, the byte compare of the global group's device row, the skipped `materialize` and IO scope, the per-call imports bound once. The window layout adds its own, with the same values (`remote_ra_live_v2/window_rows.py`, `window_owner.py`, `window_lifecycle.py`):

- The engine checked every kept block of every sliding window in every step (5 × 65 blocks per request at W = 1,024 and P = 16) and walked each sliding row from its start to reach the window (O(context)). The window pool now records the blocks whose reference count or incarnation it changes (`get_new_blocks`, `touch` and `free_blocks`, the only places vLLM 0.24 changes them), and a request's windows are checked block by block only when that record names one of their kept blocks since their last check. The window's entries of a row are read as a slice.
- A step whose rows did not change (14 of 16 decode steps) keeps the last observation's leases, key tuples and (empty) differences after the same full-attention, window and runner-row checks, and its `materialize` only marks the step.
- The step lease of an unchanged window is built without re-checking its slots, and a moved window's slots are checked in C-level passes; the backend does not re-check the generation of a lease tuple it already checked at that generation.

**CPU tests (`test_gemma_fastpath3.py`).** The engine's record path against the full check over randomized steps on vLLM's KV manager (other requests' blocks coming and going, double frees, a freed block given to another request, touched blocks, replaced row entries, record restarts); the steady owner, the lease and the backend against their full paths on random sequences, refusals included; and the window end-to-end fakes with `--decode-fastpath2` against `--decode-fastpath3` (three sessions, eager and with the CUDA-graph record, every policy with `REMOTE_RA_SLOW_TESTS=1`, one session, sixteen sessions with `--release-idle-pages` under pool pressure, `goal_query`): identical RPCs, evidence files, frames, positions, attended Pages, plans, replies, sliding reads, per-step leases and claims. CPU micro-benchmark at Gemma's geometry (x86 fakes: one global and five sliding groups, W = 1,024, 16-token pages, median of 7 runs, the same measure as above): 16 requests at 20K tokens 6.51 → 4.13 ms per decode step (5.11 → 2.88 ms at the median step), 16 at 2K tokens 5.26 → 3.70 ms, one request at 20K tokens 0.50 → 0.37 ms (not re-verified: the benchmark's output was never archived).

**Completion I/O off the decode path: `--deferred-completion-io` (on by default, section 4.15).** vLLM emits a request's last token only after `update_from_output` has run this runtime's completion: the worker `complete` RPC (the sealed Pages into the arena, the Gated-DeltaNet carry, its receipt), the transcript commit and the native terminal, which reads and checks the startup config again, copies the drain receipt, encodes 2 to 5 MB of JSON and writes it with an fsync. In job 3410181 (one request at a time, histories of 2K to 257K tokens) each request's decode time carried a fixed 103 to 108 ms more than stock vLLM's (`goal_query`, `observation_query`), about 40 ms of it the worker's `complete` frame; with 16 requests running, all of them wait for it. On the Gemma 4 profile (job 3410750: one session, `full`, CUDA graphs `full` and both decode fast paths) the completion made 10 of 699 decode intervals 75 to 300 ms long (replies of 64.5 tokens on average): by the server's inter-token-latency histogram about 1.7 ms per token (1.3 to 2.1) of the 3.8 ms per token by which it decoded slower than stock vLLM (29.30 against 25.49 ms). `--deferred-completion-io` (on by default; `--no-deferred-completion-io` turns it off) keeps on the engine thread only what reads engine state and writes the same files on one writer thread after the step's outputs (`remote_ra_live_v2/deferred_completion.py`):

- **Engine thread.** The native record is built by the same code (`terminal_value` in `remote_ra_http/evidence.py`). The containers other owners may still hold (the drain receipt, the plan, the query receipt, the idle-release record) are copied with pickle at that moment; `goal_query`'s `goals.jsonl` row is encoded and named there; the startup config is not read again (the output directory and the layout were read at startup). The request's worker frames and prompt list belong to the record alone.
- **Writer thread.** `post_step` hands it the staged jobs once the step's outputs are in the output queue, and it writes them in order with the calls of before: the row with `open('ab')`, the native file with `open('xb')`, one write, a flush and an fsync each. The bytes are those of `encoded(value)`: the JSON is assembled from pieces of about 2,048 values (the same encoder and options on sub-values), and the writer sleeps 0.1 ms after every 0.5 ms of work. CPython's JSON encoder holds the GIL for a whole call, so a plain thread that encodes each record at once would hold up the engine thread for tens of milliseconds at a time (CPU benchmark below).
- **Who waits for the files.** The frontend reads a native file only after the engine has acknowledged its Cancel (state complete). While the request's files are being written that acknowledgement waits, and the engine thread sends it at its next input pass. A session's next admission (with its readmission or rebuild), the release of its Pages for another admission and its close first wait for its writes. A cancellation, an expiry, a disconnect or a second terminal of a request waits for every write and then writes synchronously, so `goals.jsonl` keeps its order. Shutdown waits for and stops the writer before the request drain (`remote_ra_http/shutdown.py`); an interpreter exit without shutdown still writes what is pending.
- **Failures.** A failed write fails its request's acknowledgement (the request fails, as when the engine thread wrote), is reported as `COMPLETION_WRITE_FAILED` (a `failure-*.json` and the server log) and stops the writer: every later completion, admission and the shutdown raise it, and nothing more is written.

**What the flag pins.** `startup.json` records `deferred_completion_io: true` and `ready.json` records it. It is the engine's alone: no worker startup record, no vLLM argument. Both model profiles take it (the Gemma 4 profile since gemma-deferred-io: below and section 4.14). Without the flag the startup config, the evidence and the vLLM command gain nothing and the code paths are the previous ones.

**On the Gemma 4 profile's window layout.** The moved code is the one both profiles share. What the window layout adds to a completion stays on the engine thread, where it was, around the native terminal: the worker's `complete` RPC commits the window carry and releases the request's sliding leases; before vLLM frees the request the engine pins the next window (`WindowPins.pin_after`) and frees phase 1's leftover blocks (`WindowPhase1Coordinator.release`); after it, vLLM's free returns the request's other sliding blocks to pool 1, and `WindowPins.after_free` checks that the pinned window keeps the session's pin alone. The record is built by the same code, and both pools' free blocks (global Pages and sliding blocks) are read at the same point as without the flag. The native file's one reader on the XML, kv-session and chat-text protocols is the frontend's, after the held acknowledgement; a session's close (a chat-text idle close or eviction too: the same CloseSession frame), its next admission (with a readmission or a rebuild) and an idle release wait for its writes, as for Qwen. No other Gemma code path reads a native file or `goals.jsonl` while the server runs.

**Step profile.** With `REMOTE_RA_STEP_PROFILE=1`, `sched.complete` is split into `sched.complete.drain` (the worker's `rpc.complete`, the engine's copy of its receipt `rpc.complete.copy`, a query policy's vector publication `sched.complete.publish`, and the engine's checks), `sched.complete.after` (with the transcript commit `sched.complete.transcript`) and `sched.complete.terminal` (`.config`, `.copy`, `.goal`, and `.save` with its JSON `.encode`; with the flag, `.snapshot`), and with the flag every line carries the writer's totals (`completion_writer`: jobs, bytes, encode, write and queue time, held acknowledgements). Without the variable nothing changes.

**CPU tests (`test_deferred_completion.py`).**

- The launcher on every base of `test_integrate_flags.py` (both layouts, the three protocols, CUDA graphs, the admission flags) with the decode fast paths, `--language-model-only`, `--release-idle-pages` and next to `--goal-rewriter-batch`: only the switch's key is added; `config.load`, `ready.json`, `compose_engine` (the writer only when pinned, the same worker record) and the shutdown order.
- The bytes equal `encoded(value)` on random values (other key types, tuples, subclasses, floats, deep nesting, small pieces), on records shaped like native files and on every native file of job 3410181 (108 files, checked separately); later changes to the receipt, the plan or the query do not reach the file.
- The writer: the same calls and bytes as the synchronous path, the order, the joins, held acknowledgements, a write failure, cancellations and retries, close and interpreter exit.
- End to end: three mswea-xml sessions decoding together (`full`, `goal_query`; with the three decode fast paths; `observation_query`, `random50` and 784-token pages with `REMOTE_RA_SLOW_TESTS=1`) and sixteen sessions under pool pressure with `--release-idle-pages` and the three fast paths write byte-identical evidence files, send the same RPCs and commit the same replies with the flag on and off. ### 4.12 Text only: `--language-model-only` (on by default)

On by default (section 4.15); `--no-language-model-only` loads the vision tower (Qwen only). The text below describes the switch as given.

Qwen3.6-27B is a multimodal checkpoint, but this runtime serves text only. Without this flag, vLLM 0.24.0 still loads the vision tower and profiles its encoder cache with a dummy image. Before the server reports ready, it also warms up the multimodal processor with fake image and video inputs sized to the context limit (job 3357655 logged `Multi-modal warmup completed in 13.884s`). For under a second this warmup takes tens of GiB of host memory, enough to get a server killed before READY in a job that requests only one GH200's share of the node's host memory.

`serve.py --language-model-only` (on by default, section 4.15; `--no-language-model-only` turns it off on Qwen) passes vLLM's own `--language-model-only`, which sets every multimodal limit to 0. In the pinned vLLM 0.24.0 sources this means:

- The vision tower is replaced by a placeholder and is never built or loaded (`_mark_tower_model` in `vllm/model_executor/models/interfaces.py`; `qwen3_5.py` builds `visual` inside it).
- The renderer creates no multimodal processor, so neither multimodal warmup runs (`vllm/renderers/base.py`), and no encoder cache is set up or profiled.
- The language model's weights are the same. The KV cache is still `--kv-cache-memory-bytes`, so its blocks and pools and the launcher's KV and host-memory checks are unchanged. The tower's weights (about 0.9 GiB in BF16, computed from the vision config, not measured) stay free on the GPU.
- One computation changes. In text-only mode vLLM runs the QK-norm, RoPE and output-gate split of the 16 full-attention layers as one fused kernel instead of separate operations (`Qwen3NextAttention` in `qwen3_next.py`). The arithmetic is the same (every step the runtime checks that the three mRoPE rows equal the logical positions), but outputs need not be bit-identical to those of a server without the flag. The runner also passes token ids to the model instead of the embeddings it looked up itself; that change is exact (the model does the same lookup).

**Pass the same flag to the stock vLLM control**, so that both sides load the same model and run the same kernels, and compare only servers that agree on it. The stock command in [docs/SWEBENCH_BENCHMARK.md](SWEBENCH_BENCHMARK.md) passes it; `examples/slurm/serve_gh200.sh` does not pass it, so its server takes the default (on, section 4.15).

**What the flag pins.**

- `startup.json` records `language_model_only: true`, and its `effective_server_config` holds `language_model_only: true`; the frontend compares vLLM's parsed argument with it.
- The engine checks its resolved multimodal configuration. The worker checks that vLLM resolved the image and video limits to 0 and holds no vision-tower tensor, and echoes `{"mm_limits": {"image": 0, "video": 0}, "vision_tower_tensors": 0}` in `worker-attached.json`; `ready.json` records it. Each check runs once, at startup (`remote_ra_live_v2/language_model_only.py`).
- Without the flag, the vLLM command, the startup config and the evidence gain nothing, and the frontend, the engine and the worker refuse a vLLM that runs language-model-only anyway.

**CPU tests (`test_language_model_only.py`):** the launcher, the startup checks, the worker evidence and `ready.json`; with the flag, the multi-session fakes produce the same RPC payloads, evidence files and tokens.

### 4.13 Releasing idle sessions' pages (opt-in)

Between turns a session pins its resident pages on the GPU (the previous turn's selected pages plus the pages sealed in it) and its live tail page; its Gated-DeltaNet carry is on the host, and every sealed page also has a host copy in the pinned page arena. With 16 sessions at a 32,768-token budget and 16-token pages, an idle session pins about 2,300 pages and the 16 together about 37,000, more than a 25 or 32 GiB KV pool holds (the capacity rule of section 4.9). Without this option the capacity gate then waits for a running request to finish. Once every session is idle nothing can free a block, and every next turn waits for good (earlier code admitted the first of them because nothing ran, and it failed for lack of blocks).

`--release-idle-pages` (off by default; decoupled layout only) lets the capacity gate release pages instead (`remote_ra_live_v2/idle_release.py`):

- **Victims.** When a turn does not fit, the gate covers its attention-pool shortfall by releasing whole idle sessions' resident pages, least recently used first. Idle means open, with no request admitted or running, and not the session being admitted. A session whose next request has reached the server but still waits for admission is idle: its released pages come back before that request's phase 1 (otherwise a pool pinned by sessions whose next requests all wait could never free a block). The live tail page is never released. If the idle sessions together cannot cover the shortfall, nothing is released and the turn waits with `CAPACITY_WAIT`, as before. A turn the gate admits because nothing runs first releases what it needs; with `--admission-overlap K` the same holds when, in addition, no admission is in flight (earlier code: the ledger gate admitted such a turn without the release).
- **Readmission.** The released pages come back from their host copies before the session's next phase 1, which attends to them. That turn then runs exactly as if they had never left; the gate counts the readmitted pages in both of its peaks.
- **No waiting inside an admission.** A release and a readmission are synchronous engine operations between steps. A refusal is the usual immediate `CAPACITY_WAIT`, so the frontend's 300-s acknowledgement wait covers only an admitted turn's own work.
- **What it pins.** `startup.json` records `release_idle_pages: true`. The engine sends it to the worker once in its startup record; the worker checks it and only then accepts the release and readmission operations; `worker-attached.json` and `ready.json` record it. Without the option nothing is added and the code paths are the previous ones.
- **Evidence.** `capacity.jsonl` in the output directory has one row per release and per readmission (`schema` `remote-ra-capacity-event-v1`: the session, its pages and blocks, both pools' free blocks before and after, the admitting request and its shortfall). Every native file and `runtime.jsonl` row adds `idle_release` (the sessions released to admit that request, its readmitted pages), and `engine-cleanup.json` adds the totals.

**CPU tests (`test_idle_release.py`).** 16 sessions on the batched engine and worker fakes at 16-token pages, `observation_query` with `--active-token-budget 32768`, 12 turns each with observations of about 3,600 tokens (prompts up to 39,845 tokens, 2,048 selected pages on the last turns):

| Attention pool | Without the option | With it |
| --- | --- | --- |
| 25,600 blocks (the 16 sessions' idle pins exceed it) | a turn waits for good (`CAPACITY_WAIT` with nothing running; earlier code admitted it, and it failed) | all 192 turns, with releases and readmissions of idle sessions' pages |
| 48,000 blocks | all 192 turns | all 192 turns, nothing released |

With the option, every session's prompts, selections, attended pages and replies equal those of the 48,000-block run. A shorter case (900 against 9,000 blocks) runs in the normal pass with `observation_query` and in the slow pass (section 2.3) with `full` too; the 32,768-token case takes about 5 minutes and runs in the slow pass. Not measured: the readmission's host-to-device time on the GPU, and how often a session is released again before its next turn under a real workload (least recently used is, under round-robin turns, the session that runs next).

**On the GPU.** Job results: [docs/status.md](status.md); limits: [docs/known-limits.md](known-limits.md) (2.4); the GPU runs this section described until 2026-11-16: [frozen notes, 4.13](history/reference-gpu-notes.md#from-section-413-releasing-idle-sessions-pages).

**Model and selection.**
- 60 decoder layers: 50 sliding-window layers (window 1,024 tokens, 16 KV heads × 256) and 10 global full-attention layers (5, 11, …, 59; 4 KV heads × 512, K and V both cached).
- Pages, budgets, mandatory and recent Pages, vectors and restores apply to the global layers only: 81,920 bytes per token, so a 16-token Page is 1.25 MiB (Qwen: 1 MiB).
- The sliding layers always attend to the exact last 1,023 tokens plus the current one, as in stock vLLM. Their window is not counted in `--active-token-budget`.
- The selection query is the hidden state before the final norm at layer 59 (the last layer, a global one), projected with the same seeded matrix: SHA-256 `852b42e4…a1dfb7` for hidden size 5,376.

**Windows across turns.**
- Each session keeps its sliding window on the GPU between turns: at the end of a turn the engine pins, per sliding group, the blocks the next query reads (at most ⌈1,024 / P⌉ + 1).
- The next turn's phase 1 computes the new tokens on that window plus fresh blocks. Phase 2 starts from the window phase 1 ended in, behind null blocks, so vLLM never allocates the blocks before the window; the older blocks are freed then.
- The worker checks both rows and keeps the window after the computed end as the session's carry; there is no Gated-DeltaNet state. A rebuild or a closed session frees its window.

**Chunked phase 1.** A phase 1 longer than one native forward (8,192 tokens; Mini-SWE-Agent's 10,000-character cap allows about 10.2K tokens of digit-dense output) runs as forwards of at most 4,096 tokens on one lease (`model_profile.GEMMA4_PHASE1_CHUNK_TOKENS`); a phase 1 of at most 8,192 tokens is one forward, as before.

**Serving configuration: CUDA graphs and the decode fast paths.** A Gemma server takes `--cuda-graphs piecewise`, `full` or `full-decode`, `--decode-fastpath`, `--decode-fastpath2` and `--decode-fastpath3` with the pins and the startup checks of sections 4.8 and 4.11; without them its vLLM command, startup config and evidence are unchanged. Together they give Gemma the serving configuration of Qwen: `--cuda-graphs full --decode-fastpath --decode-fastpath2 --decode-fastpath3` (the benchmark settings use the three). They combine with every policy, `--admission-overlap K` and `--release-idle-pages` (CPU: `test_gemma_flags`).
- **CUDA graphs.** The global group is the window layout's only FullAttentionSpec group (vLLM's SlidingWindowSpec is not one). With FULL graphs the runner binds it to the physical seq-len buffer at capture and at replay, and it keeps the physical slot mapping; the five sliding groups keep vLLM's logical seq lens, positions and slot mapping. Every buffer a captured graph reads is one of the runner's persistent buffers, rewritten in place before each replay (CPU test: the overlay runner's metadata build on the six groups gives each group the same buffers at capture and at replay). The compiled modes need attention and the KV-cache update as splitting ops (there is no GDN op). Phase 1, its chunks and the Goal forward run eagerly. At 16 sessions the capture sizes are 1, 2, 4, 8, 16, 24 and 32. torch.compile (`piecewise`, `full`) changes bf16 numerics as for Qwen: compare with stock vLLM on `TRITON_ATTN` in the same mode.
- **`--decode-fastpath`.** Qwen's fast paths plus the window owner's incremental observation: a step extends the last observation when the full one would accept the same rows. The full-attention leases grow by the appended blocks, each sliding group's leases by the blocks that entered its window minus those that left it, and the claims and allocation sets move by these differences; the leases of a window that did not move are neither rebuilt nor checked again.
- **`--decode-fastpath2`.** Qwen's one `allocation_batch` RPC per step and the after-forward work behind the logits, plus incremental sliding rows (`remote_ra_live_v2/window_rows.py`): the engine follows each sliding window instead of rebuilding whole rows, a changed request's update carries per KV group only the window's first index, the row's length and the appended (block, incarnation) pairs, an unchanged one carries no rows, and the worker keeps its sliding rows compact. At 131,072 tokens a changed update carried about 41K pairs (five sliding rows of 8,192 entries and the global row); it now carries the appended ones. A request's first update is still whole.
- **`--decode-fastpath3`** (gemma-fastpath3, needs `--decode-fastpath2`). Qwen's cuts that do not rest on Mamba rows, plus the window layout's own (section 4.11): the window pool records the blocks whose reference count or incarnation it changes, so the engine checks a request's windows block by block only when one of their kept blocks changed; an unchanged step keeps its observation, leases and key tuples after the same checks; a moved window's slots are checked at C speed. CPU tests: `test_gemma_fastpath3`.
- **vLLM's runner rows.** vLLM's runner only appends a request's new block ids; EngineCore nulls the blocks that left a window in its own rows only. The worker therefore checks a runner's sliding row against EngineCore's on the live window, which holds every read of the step, not the whole row. The stage-1 check compared whole rows and would have refused a real runner at the first window slide; the CPU fakes now keep their rows (and numpy block tables) as vLLM 0.24's runner does.

The new messages open at `<|turn>` (`input_ids[boundary_tokens]`, after a text reply's `<turn|>` and `\n`: boundary 2) or right after `<|tool_response>` (`input_ids[boundary_tokens − 1]`): a reply with a tool call stops on `<|tool_response>` (id 50), which is also the first token of the tail that carries its responses, so its boundary is 1. ### 4.15 Speed defaults

The switches every benchmark server passes (A.3 and the Gemma parts of [docs/SWEBENCH_BENCHMARK.md](SWEBENCH_BENCHMARK.md), [docs/TERMINALBENCH_BENCHMARK.md](TERMINALBENCH_BENCHMARK.md) and [docs/MEMORYAGENTBENCH_BENCHMARK.md](MEMORYAGENTBENCH_BENCHMARK.md)) are on by default:

| Option | Default | Off | Notes |
| --- | --- | --- | --- |
| `--cuda-graphs` | `full` | `--cuda-graphs off` (eager) | Section 4.8; `piecewise` and `full-decode` as before |
| `--decode-fastpath` / `--decode-fastpath2` / `--decode-fastpath3` | on / on / on | `--no-decode-fastpath`, `--no-decode-fastpath2`, `--no-decode-fastpath3` | Section 4.11; each stage needs the one before |
| `--deferred-completion-io` | on | `--no-deferred-completion-io` | Section 4.11 |
| `--language-model-only` | on | `--no-language-model-only` | Section 4.12; the Gemma 4 profile requires the flag and refuses the off switch |
| `--connector-pool-gib` | `1` | `--no-connector-pool-gib` | Section 4.9; off is the profile's own pool: vLLM's 32 GiB for Qwen, 1 GiB for Gemma 4 |
| `--max-tokens` with `--enable-thinking` | `4096` | `--max-tokens 1536` | Sections 4.9 and 6.8: the baselines' bound, the reasoning included; thinking off keeps 1536, so the thinking-off servers keep their meaning |

- **Rules.** A switch on the command line wins over its default. A stage whose prerequisite is off is off: `--no-decode-fastpath` turns the second and third stages off too, `--no-decode-fastpath2` the third. A switch with its own off switch is refused, and so is every combination the launcher refused before when it is asked for explicitly (for example `--decode-fastpath2 --no-decode-fastpath`). Over the CPU tests' grid of launches (both profiles, the three protocols, four policies: `full`, `observation_query`, `goal_query` and `random_fill`, both layouts, with and without thinking, the admission and Goal-rewriter options, `--triton-attn`, `--release-idle-pages` and `--async-scheduling`) the defaults turn no accepted launch into a refused one.
- **Still opt-in.** `--release-idle-pages` (section 4.13; `full` at 16 sessions in 25 GiB needs it, [known limit 2.4](known-limits.md#24-full-at-16-sessions-in-25-gib-needs---release-idle-pages)), `--admission-overlap K`, `--goal-rewriter-batch N`, `--goal-overlap`, `--gdn-device-handoff`, `--phase1-in-step` and `--triton-attn`.
- **`--async-scheduling` is not a speed default** (integrate-1103): it stays opt-in ([docs/async-sched/IMPLEMENTATION.md](async-sched/IMPLEMENTATION.md)). On the GPU: [docs/status.md](status.md) (Qwen and Gemma 4; Gemma 4: [known limit 5.3](known-limits.md#53-gemma-4-with---async-scheduling-is-a-partial-pass)); the earlier text: [frozen notes, 4.15](history/reference-gpu-notes.md#from-section-415-speed-defaults). The current configuration passes it ([docs/status.md](status.md#current-configuration)). Without it vLLM gets `--no-async-scheduling`, with the defaults and with `--no-speed-defaults` alike, and the `speed_defaults` record never names it. With the defaults its prerequisite `--decode-fastpath2` is on, so `--async-scheduling` alone starts the same server as every speed switch given with it; with `--no-speed-defaults` it needs `--decode-fastpath --decode-fastpath2`, as on the former command line. `--no-decode-fastpath` or `--no-decode-fastpath2` with it is refused, and so are `--gdn-device-handoff` and `--phase1-in-step`, defaults or not. The same holds on both model profiles: the Gemma 4 profile takes it since async-gemma ([docs/async-sched/GEMMA.md](async-sched/GEMMA.md)).
- **`--no-speed-defaults`** gives every speed option left out its former default (off): the eager server without the fast paths, the completion files written on the engine thread, the vision tower loaded, the profile's own connector pool and, with `--enable-thinking`, the 1,536-token reply bound. That is the former command line, byte for byte: dry run, vLLM command, `startup.json` and `launch.json`. Switches given with it still apply.
- **What is recorded.** Only the command line changes; the launcher's `prepare()` keeps the former defaults. A launch whose options come from the defaults gets the vLLM command, `startup.json` and evidence of the same launch with the switches given explicitly. The dry run and `launch.json` add a `speed_defaults` record with each speed option's value and source (`default`, `switch`, or why it is off). A launch where no default applied (every option given, or `--no-speed-defaults`) has no record.
- **Commands.** The benchmark docs' server commands give every speed option explicitly, so their meaning does not change. The Qwen MemoryAgentBench servers, whose runs of record used the first fast path alone, add `--no-decode-fastpath2 --no-deferred-completion-io`. A server command of these pages written without the switches starts the server with them; add `--no-speed-defaults` for the eager server that the earlier sections describe ([docs/running.md](running.md) 4.1 to 4.5, sections 4.6 and 4.7). Compare a CUDA-graph server with stock vLLM in the same mode (section 4.8).
- **Tests.** `test_speed_defaults.py` (CPU): every server command of the three benchmark docs with and without its speed switches gives the same `prepare()` arguments and dry run apart from the record; `--no-speed-defaults` and the off switches give the former command line's arguments, checked against a frozen copy of the former option mapping; the prerequisite rule, the thinking-on reply bound (mswea-xml and chat-text, keep and strip, 16 sessions at 262,144 tokens and 25 GiB), the refusals, the record and `launch.json`, and `--async-scheduling` left out and given on both command lines; mutations of each rule fail these checks. The existing launcher tests pass `--no-speed-defaults`, their former command lines.
