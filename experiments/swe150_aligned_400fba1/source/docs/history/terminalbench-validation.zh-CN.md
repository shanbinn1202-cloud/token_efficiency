# 截至 2026-11-16 的 Terminal-Bench 验证状态（冻结）

> **2026-11-16 冻结**（在 `e6d0c88`）：原来 [docs/TERMINALBENCH_BENCHMARK.zh-CN.md](../TERMINALBENCH_BENCHMARK.zh-CN.md#验证状态) 的“验证状态”一节中各次 dry run 的记述（检查清单之后的各段；清单仍留在该节），由 docs-fix1-1116 原样移到这里，只改了相对链接；不再更新。“A.x”和“B.x”指该页的各节；“Part A”是该页正式记录的配置（thinking 关闭、K = 20、25 GiB、262,144 token）。之后跑过什么、每次运行的判定见 [docs/status.zh-CN.md](../status.zh-CN.md)；从 running.md 和 reference.md 移出的作业说明见 [running-gpu-notes](running-gpu-notes.zh-CN.md) 和 [reference-gpu-notes](reference-gpu-notes.zh-CN.md)。

**`full`：修正 harness 的两项检查之后，在 65,536 token 下通过（核验器结论 `NOT_VERIFIED`）。** 作业 3399075，`full` 在 runtime commit `68d19b4` 上的 dry run，使用本文档当时的设置（65,536 token、`--kv-cache-gib 32`、`--dram-arena-gib 64`），且只开 `--decode-fastpath`（见下）：16 个 trial 全部结束，服务完成了 333 个请求，每个请求都与其 native 回执 token 级精确一致，没有任何抢占，服务从未因容量停滞。作业自己的结论是 `TB16_FAIL`，来自 harness 中两项有错的检查（bind 行的打开 session 计数，以及客户端在 agent 超时时断开的已准入请求）；修正这两项之后，存档的证据离线重新核验时通过了所有检查。runtime 没有改动。核验器存档的输出为 `NOT_VERIFIED`：它的 submission-identity 检查不通过（`ONE_JOB_SUBMITTED_NOT_QUALIFIED`），它是对着一个更新的 harness 运行的，其文件与该作业的不同，而且它重新运行检查的结果不再与作业记录的失败项一致。运行期间容量门控释放过空闲 session 的 Page；被释放的 session 都没有再回来进行下一轮，所以重新载入没有运行。

**`observation_query`：已经过 GPU 验证。** 作业 3399437（`TB16_PASS_VERIFIED`），`observation_query` 以 8,192 token 预算、在 runtime commit `68d19b4` 上按作业 3399075 的设置（见上）进行的 dry run：16 个 trial 全部结束，服务完成了 384 个请求（其中 18 个是重建），其中 238 个请求的选择生效，每个请求都与其 native 回执 token 级精确一致，没有任何抢占，服务从未因容量停滞，所有检查都通过，取回之后证据也再次通过了核验。harness 的对账脚本修复之后（它现在处理 agent 在单独 session 中进行的简短摘要调用，以及 agent 超时时没有记录下来的回复），16 个 trial 全部与其 ATIF trajectory 对上。池从未紧张，所以没有释放空闲 Page。

第一次 `full` 的 dry run，即作业 3398129，使用 runtime `0d37346`，没有开 `--release-idle-pages`，以引擎失败告终：空闲 session 的 Page 占满了注意力池，一轮在没有请求运行时被接纳，却找不到空闲 block，vLLM 抢占了它。commit `68d19b4` 让这样的一轮等待，并且现在每个服务都开 `--release-idle-pages`（A.3）。那次运行不属于验证。

**`goal_query`：`53e3b7a` 上的 dry run 已通过（2026-10-24 的状态；65,536 token，32 GiB）。** `goal_query` 的第一次 dry run，即 runtime `120bc3c` 上的作业 3429670（dry 子集的 16 个任务，`-n 16`），失败了：大约 9 分钟后服务不再响应，16 个 trial 中有 8 个触发了 900 秒的 agent 超时。原因在 Goal 特征中：每次构造 Goal 都会用上游 `dram_kv/goals/features.py` 中的引号字面量正则（`normalize_action`）规范化该 session 的上一条回复，而这个正则遇到未闭合的引号后跟反斜杠转义时会指数级回溯。卡住的那一轮之前的回复，是该次运行中唯一一条在 `max_tokens` 处被截断的回复（4,096 token，截断在一个 JSON 字符串内部）。CPython 的正则引擎在整个匹配期间持有 GIL，所以引擎进程冻结，API 服务与引擎之间 90 秒的心跳随即撤销了该服务。runtime `53e3b7a` 在服务启动时用一个线性时间、输出完全相同的实现替换这个正则；上游文件及其固定值不变（[docs/history.zh-CN.md](../history.zh-CN.md#历史)）。在 `53e3b7a` 上的重跑，即作业 3434533，是这一修复第一次在 GPU 上运行，使用 A.3 的参数，但取当时的大小（65,536 token、`--kv-cache-gib 32`、`--dram-arena-gib 64`）：`TB16_PASS_VERIFIED`。服务没有卡住，尽管 `make-doom-for-mips` 又产生了一条在 4,096 token 处截断的回复；16 个 trial 中解决 8 个，6 个触发了 900 秒的 agent 超时；按 runner 的时间跨度算，输出吞吐 177.6 tokens/s。合并计入 Terminus 2 没有记录为 ATIF 步骤、在 `max_tokens` 处截断的两条回复（一条在主循环中，一条是其上下文超限回退中的完整 summary 调用，共 8,192 token）之后，与 ATIF 轨迹的合并 16 个 trial 全部通过（`JOIN_PASS`，离线重新合并，177.63 tokens/s）（A.10）。

**优化开关。** `full` 和 `observation_query` 在 `68d19b4` 上的 dry run（作业 3399075、3399437）只开了 `--decode-fastpath`。`--decode-fastpath2`、`--decode-fastpath3` 和 `--deferred-completion-io`（A.3）在作业 3434533（`goal_query`，见上）中第一次通过了 Qwen 的 Terminal-Bench 运行；此前它们已在卡住的作业 3429670（见上）、Gemma 的作业 3433706（重新核验后为 `TB16_PASS_VERIFIED`，见下）以及 SWE-bench 作业 3428631 和 3429500（runtime `120bc3c`）中运行过。Qwen 上的解码检查（作业 3429022，runtime `120bc3c`；离线核验为 `SPD3_PARTIAL_PASS_VERIFIED`：每个 runtime 服务都通过，只是部分轮次缺少 stock 服务的测量窗口，所以是部分通过）没有发现超出运行间波动的差异：16 个并发 session 时，任何配置在两次运行之间都不是逐字节相同的（A.13）；在 prompt 逐字节相同的请求中，`--decode-fastpath3` 对照 `--decode-fastpath2` 时 76–83 % 的回复相同，`--deferred-completion-io` 开对照关时 76–80 % 相同，而同一配置只切换 step profiler 时为 81–82 %；差异集中在 8 个及以上并发 session 的轮次中，在 1 到 4 个 session 的轮次中，比较的同 prompt 回复只在两组中各有一条不同，都在一个 2 个 session 的轮次中（不开 profiler 时 `--decode-fastpath3` 对照 `--decode-fastpath2`；`observation_query` 下的 `--deferred-completion-io`）（[docs/reference.zh-CN.md 4.11 节](../reference.zh-CN.md#411-解码快速路径默认开启)）。

**262,144 token、25 GiB 下（2026-10-26 的状态）。** 作业 3461661 在 runtime `cf2b28d` 上先后运行 `goal_query` 和 `observation_query`，使用 A.3 的服务参数（`--kv-cache-gib 25 --max-model-len 262144 --dram-arena-gib 70`、三个解码快速路径和 `--deferred-completion-io`），Terminus 2 的 `max_input_tokens` 为 262144，在 dry 子集的 16 个任务上、`-n 16`：`TB16_PASS_VERIFIED`。`goal_query`：362 个请求，prompt 最多 92,354 token，16 个 trial 中解决 8 个，3 次 Goal 回退（`GOAL_FALLBACK`）。`observation_query`：390 个请求，prompt 最多 102,611 token，解决 9 个。两个服务都合并了 16 个 trial 中的 16 个，都没有容量等待、没有重建、没有释放空闲 Page、没有上下文拒绝，也没有抢占（[docs/reference.zh-CN.md 4.9 节](../reference.zh-CN.md#49-上下文上限与回复上限)）。作业 3499759（runtime `8ca8511`，2026-11-02）以 thinking 开启运行了同样的 262,144 token 服务（`--enable-thinking --thinking-history strip`，`goal_query` 和 `observation_query`），以及一个 thinking 开启的 stock 对照（每次调用都 `enable_thinking` true），结论为 `TB16_PASS_VERIFIED`；thinking 开启不属于本配置。

**Gemma 4 31B IT（A.14）：两次 dry run 都已通过（2026-10-24 的状态）。** 在 dry 子集的 16 个任务上以 `-n 16` 运行，使用 A.14 中按实际运行记录的 Gemma 参数，上下文为 65,536 token（25 GiB，K = 17，8,192 token 的前向，64 GiB 的 arena）：

- 作业 3433706，`observation_query`（runtime `9ef0d6d`）：经下文的重新核验后为 `TB16_PASS_VERIFIED`（2 个被取消的 admission）；合并通过；16 个 trial 中解决 4 个，7 个触发了 900 秒的 agent 超时。
- 作业 3434544，`goal_query`（runtime `53e3b7a`）：经下文的重新核验后为 `TB16_PASS_VERIFIED`（4 个被取消的 admission）；合并通过；16 个 trial 中解决 5 个，6 个触发了 agent 超时；Goal fallback 3 次。

两个作业自身的判定都是 FAIL，来自测试工具的几项检查：它们当时还不接受客户端在 admission 期间取消的请求（在 Harbor 的 agent 超时时取消；服务端结束了该 admission 并做了补偿）。这些检查已经修正：只有在有正面证据时（补偿成功、没有 runtime 行、引擎的取消回执或容量拒绝、匹配的断开 failure 行），这样的请求才算干净，并报告为 finding `CANCELLED_ADMISSION`；归档的证据已离线重新核验，没有在 GPU 上重跑。在 262,144 token 下尚未运行：A.14 的 Gemma 配置（`observation_query`、`random_fill`、`goal_query` 和 stock 对照）；GPU dry run 已在计划中。Gemma 的 `random_fill` 和它的 stock 对照在任何上下文下都没有在 Terminal-Bench 上运行过。`full` 不属于 Gemma 的配置（在 262,144 token 下，launcher 在 32 GiB、4,096 token 的前向时最多允许 10 个 `full` session，8,192 时最多 5 个；A.14）。此后（2026-11-15）：作业 3560498 在一次 16 个任务的 GPU dry run 中运行了这一配置，因此 Gemma 的 `random_fill` 和它的 stock 对照已在 Terminal-Bench 上运行过（`TB16_FAIL_VERIFIED`：`observation_query`、`random_fill` 和 stock 对照的服务检查通过，`goal_query` 的未通过；`goal_query` 的一个请求被以 `CAPACITY_EXCEEDED` 拒绝）。

在 GPU 上，`full` 和 `observation_query` 的 dry run 是 chat-text 协议、一个服务上 20 个同时运行的 session、`--release-idle-pages` 以及 65,536 token 下 `--dram-arena-gib 64` 的第一次测试。CUDA graph（[docs/reference.zh-CN.md 4.8 节](../reference.zh-CN.md#48-cuda-graph)）和解码快速路径（[docs/reference.zh-CN.md 4.11 节](../reference.zh-CN.md#411-解码快速路径默认开启)）此前已在 GPU 上配合 XML 协议运行过，`--language-model-only` 和 1 GiB 的 connector 池也是（作业 3379206，2026-10-16）。

尚未运行：本配置的整体（89 个任务，agent 超时从 600 到 12,000 秒），也就是本文档所配置的正式测试本身；262,144 token 下的 Gemma 在其 16 个任务的 GPU dry run 之外的部分（A.14；dry run 是作业 3560498，结果见 README 中各模型 × benchmark 的状态）；262,144 token 下的 `full`，以及 Qwen 的 `random_fill`（`random_fill` 在 Terminal-Bench 上只在这次 Gemma dry run 中运行过）；本配置下 thinking 关闭的 stock 对照。dry run 使用的是另一套 harness，其服务参数、Harbor 作业配置、隧道和关闭 session 的方式与本文档相同；`examples/terminalbench/` 中的客户端只有 CPU 测试，B.5 的 Slurm 脚本、B.2 的 agent 侧文件、B.3 的检查以及 B.7 到 B.9 的脚本都未经测试。本文档不报告任何结果。
