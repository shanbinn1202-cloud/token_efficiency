## 4.4 一个服务上的多个 session

在 GPU 上，16 个 session 跑过两次：作业 3339019（`full`、`observation_query` 和 `random_fill`，eager，runtime `afffd2b`）和作业 3343069（`observation_query`，eager 以及 `--cuda-graphs full`，runtime `613a7d5`）。都是合成会话：每个 session 6 轮、每轮 2,600 token 的 observation，prompt 最长约 14K token，24 GiB、16 token 的 Page，使用作业 3270721 的干净环境（复用）和一张 GH200。16 个 session 一起 decode，没有抢占，没有一轮等待容量；离线重放每个选页轮次，都得到与记录相同的 Page。同一负载的两次 eager 运行（两个作业里的 `observation_query`）在 96 轮中有 72 轮 token 相同：成批 decode 时，回复可能随 batch 的组成而变，而 batch 的组成取决于时序。这些上下文远低于 65,536 token 的上限，所以这两次运行没有触及下面说的那些限制。

在一块 GH200 上，16 个 `full` session 在 64K 时无法满足防死锁规则：它们需要约 67,350 个 1 MiB 的注意力 block 加上 Mamba 池，约 70.6 GiB KV，而 GPU 启动时只有 94.53 GiB 空闲（作业 3313802 的 vLLM 日志），权重占 51.1 GiB。选择性策略只在两次重建之间需要更少的 block，因为重建会回到全部驻留。16 token Page 下使用固定的 `--active-token-budget 8192` 时，15 个空闲 session 各自保留预算和上一轮的 Page，加上一轮的峰值：每轮约 7,000 token 时放得进 24 GiB，达到 16,384 token 的 observation 上限时需要 34 GiB；同样两种假设下，40 % 预算分别需要 41 和 51 GiB。请据此确定 `--kv-cache-gib` 和负载。只要正在运行的请求还能释放 block，`CAPACITY_WAIT` 就会让一轮等待。没有其他请求运行时，如果空闲 session 钉住的 Page 没给这一轮留下空间，它同样等待，直到有 session 关闭，或在 `--release-idle-pages`（4.13 节）下释放空闲 session 的 Page；所有 session 都在等待时，服务停滞。在 commit `68d19b4`（tb-capacity-fix，基于 integrate-1016；自 integrate-1018 起在 main 中）之前，门控因为没有请求在运行而放行这样的一轮：在 GPU 上它的 decode 用掉最后一个空闲 block，vLLM 抢占了它，这是致命的（Slurm 作业 3398129，runtime `0d37346`：16 个 Terminus 2 trial，`full`，32 GiB，空闲 session 钉住了 26,698 个注意力 block 中除 69 个以外的全部）。没有其他 session 钉住 block 时，这一轮照旧放行（如同单任务服务）。`--kv-cache-gib` 的最大值仍为 32：在使用 Goal rewriter 时，估计 GPU 上约有 36 GiB 可留给 KV（未测量）。

在 GPU 上（作业 3343069，runtime `613a7d5`）：24 个任务、K = 8，`observation_query` 加 `--cuda-graphs full-decode`，每个任务 6 轮、每轮 3,000 token 的 observation，24 GiB、16 token 的 Page。每个任务都打开、跑完 6 轮，并由 harness 关闭、拿到关闭回执（24 次打开、24 次关闭）；同时运行的 session 最多 8 个，没有抢占，没有一轮等待容量，离线选页重放与每个选页轮次一致，关停时两个池都回到 READY 时的基线。Mamba 池有 17 个 slot（2K + 1），由 K 而不是 24 个任务决定（见上表）。

## 6. Harness 接口

启动器的 `--protocol` 接受 `mswea-xml`（默认值）、`kv-session` 和 `chat-text`。`mswea-xml` 逐 token 复现 dram-backed-kv PoC 服务端，是 SWE-bench 实验用的协议（6.1 到 6.5 节）。`kv-session` 是 MemoryAgentBench harness 的 token 级 session 协议（6.6 节）。`chat-text` 是普通的 OpenAI chat 文本，面向 Terminal-Bench 2.0 上 Terminus 2 这样的 agent（6.7 节）。`--enable-thinking` 在 Qwen profile 上为 `mswea-xml` 和 `chat-text` 开启 thinking（需显式开启，6.8 节；未经验证：保留模式只在作业 3500604 的 `--goal-overlap` 检查中在 GPU 上运行过）。在此基础上，`--thinking-history strip` 为 `chat-text` 提供默认模板丢弃 reasoning 后的历史（需显式开启，6.9 节；作业 3493649、3500646 和 3499759 中的功能性 GPU 检查已通过，尚无完整 benchmark）。

## 6.1 Mini-SWE-Agent XML 协议

- **为什么关闭 thinking。** 本 runtime 的所有 benchmark 都关闭 thinking（开启 thinking 需显式指定，6.8 节；它在 GPU 上只跑过功能性检查：作业 3493649、3500646 和 3499759 中以 `chat-text` 加 6.9 节的历史运行，作业 3500604 的 `--goal-overlap` 检查中以保留模式在 `mswea-xml` 上运行），与 PoC 对齐：PoC 的服务端（dram-backed-kv 的 `scripts/serve_online_selector_v2.py`）以 `enable_thinking=False` 渲染，因为 LiteLLM / Mini-SWE-Agent 在发送下一个请求之前会从 assistant 内容中删去 thinking 块。开启 thinking 时，下一个请求不再延续服务端持有的 KV 前缀（前缀不稳定，KV 无法复用）；关闭 thinking 时，空的 think 块属于服务端渲染的 prompt（即上面的生成头），历史保持只追加。因此开启 thinking 的 baseline 运行与这些运行不可比。

## 6.8 开启 thinking（第一阶段，`--enable-thinking`）

`--enable-thinking`（需显式开启；Qwen3.6-27B，`--protocol mswea-xml` 或 `chat-text`）开启 thinking。**未经验证。本节的保留模式只在作业 3500604（`CMG1_PASS_VERIFIED`，runtime `c07d42a`）中在 GPU 上运行过，那是一次 `--goal-overlap` 检查：两个 `mswea-xml` 的 `goal_query` 服务，各 4 个 session、18 个脚本化请求，保留模式的检查（历史、token 切分、标记停止、追加）都通过，两者的回复逐 token 相同。开启 thinking 的其他 GPU 检查（作业 3493649、3500646 和 3499759）都以 `chat-text` 加 `--thinking-history strip` 运行（6.9 节）。没有 benchmark 结果。** 它的回复上限默认为 4,096 token（含思考内容），与 baseline 一致（4.15 节；`--max-tokens 1536` 保留以前的上限）：容量门控和 launcher 每轮预留 ceil(4096 / P) 个 Page。 不加该选项时，所有启动、startup config、证据字节和响应都不变。在 Gemma 4 profile 上它只做过 CPU 测试（gemma-thinking）：使用 Gemma 的 thinking-on 生成头 `<|turn>model\n`，强制前缀中带有模板的 `<|think|>` system 轮，回复按 vLLM 0.24.0 的 `gemma4` reasoning parser 的规则在其 channel token id 上切分（[docs/thinking-gemma/DESIGN.md](../thinking-gemma/DESIGN.md)）。kv-session 协议沿用自己的 `--kv-session-thinking`（6.6 节；在 Gemma 上 `on` 固定两个 thinking-on 生成头，只做过 CPU 测试）。背后的分析见 [docs/thinking-on/ANALYSIS.zh-CN.md](../thinking-on/ANALYSIS.zh-CN.md)。

## 6.9 开启 thinking 并丢弃 reasoning（`--thinking-history strip`）

`--thinking-history strip`（需显式开启，并配合 `--enable-thinking`；仅限 Qwen3.6-27B 的 `--protocol chat-text`）提供默认模板渲染的历史：`enable_thinking=True`、不加 `preserve_thinking`，不论客户端回传什么 reasoning，每条过往回复都只渲染其 content（即 Terminal-Bench Vanilla 基线的输入）。**功能性 GPU 检查已通过，都在 runtime `8ca8511` 上、使用 `chat-text` 服务：作业 3493649（`THG1_PASS_VERIFIED`）、3500646（`THG1B_PASS_VERIFIED`：与 stock vLLM 的 token 差异是 CUDA graph 的近似平局；另一项解读的分析尚未完成），以及 Terminal-Bench dry run 3499759（`TB16_PASS_VERIFIED`，`observation_query` 和 `goal_query`）。尚无完整 benchmark。** 不加该选项时沿用第一阶段的保留模式（6.8 节），所有启动、startup config、证据字节和响应都不变。在 `mswea-xml` 和 `kv-session` 上，（本首个版本中）与 `--gdn-device-handoff`、`--phase1-in-step` 同时使用时，以及与 `--policy recent_tools`、`akv_rule` 同时使用时被拒绝（这两个策略的回复分类无法从去掉 reasoning 的历史中读出，见第 5 节）。在 Gemma 4 profile 上（gemma-thinking，只做过 CPU 测试），transcript 一侧已经实现（每条过往回复为 `<|turn>model\n` + 其 content + `<turn|>\n`，即 stock 的 thinking-on 渲染），并拒绝与 `--async-scheduling` 同时使用；它的引擎一侧在 GPU 上保留切点处的滑动窗口（[docs/thinking-gemma/DESIGN.md](../thinking-gemma/DESIGN.md) 第 4 节）：`--window-hold-slots H`（1 到同时运行的 session 数；不给时取放得下的最大值，连一个都放不下时拒绝启动）预留 H 个 hold slot，每个为一个窗口（16-token Page 下 812.5 MiB）。一个 strip 轮次从准入到提交都占一个 hold slot（phase 1、停在 Goal 处的 goal_query 准入和冷 prefill 都算在内），因此同时在途的 strip 轮次最多 H 个，其余在容量门处等待：使用 `--admission-overlap K` 时同时在途的准入最多 min(K, H) 个，一个 Goal 批次最多 H 个调用（H = 1 时服务一次只运行一个轮次）。默认值让池 0 只剩选择性规则的最小值，所以较小的 H 能同时服务更多长上下文（设计说明 4.3 节）；H 固定为 `kv_layout.hold_slots`，dry run 会打印（`window_hold`）。尚未在 GPU 上运行。设计与决策见 [docs/thinking-cut/DESIGN.zh-CN.md](../thinking-cut/DESIGN.zh-CN.md)（方案 (a) 的形式 E）；规则在 `remote_ra_live_v2/thinking_cut.py`。
