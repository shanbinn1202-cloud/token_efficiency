> **For the Goal owner's review: `goal_query` on Terminal-Bench.** The branch tb-goal-query (merge `1d15a09`, in runtime `120bc3c` and later) added `goal_query` to the chat-text protocol (section 6.7) for Harbor 0.21.0's Terminus 2. It is a temporary implementation. Its first GPU dry run (job 3429670) stalled in the Goal features (the engine-stall note below); the rerun with the fix (job 3434533, runtime `53e3b7a`) passed (section 6.7). Terminal-Bench reaches the server through the chat-text protocol, not the XML protocol of the SWE-bench path: Terminus 2 sends its whole text history every turn, answers in JSON, and summarizes long trajectories through sub-calls of its own. The Goal's construction is unchanged (section 5); only its inputs had to be defined for this protocol. The team chose the following on 2026-10-18, to be confirmed or changed by the Goal owner (the exact rules: section 6.7, "`goal_query` inputs"):
>
> 1. After a summary, Terminus continues in the same session with its first message, so the server rebuilds the session and the Goal starts again from the original instruction as the requirement.
> 2. The observation of that hand-off turn is the summary only (the questions prompt's "Summary from Previous Agent"; the short summary, or the screen of the no-LLM hand-off).
> 3. The summarization sub-calls never call the rewriter: summary and answers keep the session's last Goal; questions and the short summary take the Goal of the requirement alone.
> 4. A turn after a parse error or a reply-length prompt carries no terminal output, so its observation is empty (the Goal update sees only the previous reply).
> 5. A timeout turn's observation is the terminal state only, without Terminus's timeout template.
>
> **Also for the Goal owner's review: batching the Goal rewriter (`--goal-rewriter-batch N`, section 4.10; it applies to `goal_query` on every protocol).** With 16 sessions the sessions' rewriter calls queue for the one Qwen3-0.6B process. With this option the calls that queue are sent together, up to N at a time, to one batched greedy `generate`. Unchanged: when the rewriter is called, what it is sent, the prompt, the JSON schema, `max_new_tokens`, the validation and the fallbacks; each call gets its own answer. Changed: batched greedy decoding is not bit-identical to one call at a time (padding changes the order of floating-point reductions), so a rewritten Goal can differ from the unbatched one. SWE-bench Verified, the first 32 tasks, 16 sessions, one run each (jobs 3404230 with N = 4 and 3404696 without; throughput definition still provisional):
>
> - Goal construction on the turns that call the rewriter, median: 41.2 s with N = 4 against 108.8 s without; output throughput 166.9 against 117.2 tokens/s; 20 against 19 of 32 resolved (within one run's spread).
> - Goal fallbacks (one run each): 59 of 362 rewriter calls with N = 4 on the first batched run (job 3404230; 9 of them GPU-memory failures seen only in the batched run: 4 CUDA out-of-memory errors, the requests of one batch of 4, and 5 cuDNN attention errors, the requests of a batch of 3 and two single calls, while the GPU was full) against 35 of 294 without batching (job 3404696). The memory fix is done (integration 120bc3c: the recovery frees GPU memory before it retries, the allocator cache is returned after every batch, and a batch is capped at 16,384 padded prompt tokens): in the batched rerun (job 3428631, N = 4) 7 batches still ran out of GPU memory and all recovered by splitting (no Goal fell back for memory), and 62 Goals fell back in 322 Goal rewrites (19.3 %): 60 of the 320 rewriter calls failed validation or generation, and 2 rewrites exceeded the request bound before a call.
> - The batched runs fell back more often than the unbatched one: "retrieval_goal.symbols must be unique" 37 of 320 calls (11.6 %) against 18 of 294 (6.1 %), Fisher exact p = 0.023; all fallbacks 62 of 322 Goal rewrites (19.3 %) against 35 of 294 (11.9 %), p = 0.015. The other reasons: unterminated JSON from the rewriter 20 (16 without batching), "files must be unique" 3, "stats exceed the compact rewrite-request bound" 2. The runs differ in runtime version and agent trajectories, so this is an association, not a controlled comparison. The controlled comparison ran later: a replay of the recorded rewriter calls one at a time and batched as recorded (job 3443061, runtime `53e3b7a`, `RWRP_PARTIAL_PASS_VERIFIED`, partial only because its timing arm was cut) found no significant difference over 557 pairs: "symbols must be unique" 53 alone against 57 batched (McNemar p = 0.50), any failure 98 against 97 (p = 1). Batched greedy decoding is not bit-identical to one call at a time; no mechanism in the batch path that creates duplicates was found.
> - Questions: is the non-bit-identical batched decoding acceptable (the SWE-bench configuration of record, "Ours (Goal)", runs `goal_query` with `--goal-rewriter-batch 4`)? Could the Goal side de-duplicate list fields (symbols, files, tests) before validation instead of rejecting the rewrite? That would remove most of these fallbacks with or without batching.
>
> **Also for the Goal owner's review: an engine stall in the Goal features (job 3429670, the Qwen Terminal-Bench `goal_query` dry run).** About 9 minutes in, the server stopped answering; 8 of the 16 trials ran into Harbor's 900 s agent timeout and the run failed. Cause: `normalize_action` in `dram_kv/goals/features.py` runs `_QUOTED_LITERAL_RE` (`(?s)(['"])(?:\\.|(?!\1).)*\1`) on the session's previous reply. A backslash can be taken either by `\\.` together with the next character or alone by `(?!\1).`, so after a quote with no closing quote the regex tries every split of the backslashes behind it, and the time doubles per escape (a cut Terminus reply with 22 escapes took 11 s on a CPU). The reply before the stalled turn was the run's only reply cut at `max_tokens` (4,096 tokens, inside a JSON string), and the match on it never finished (reproduced on CPU). CPython's regex engine holds the GIL for the whole match, so the engine process froze and the 90 s heartbeat between the API server and the engine revoked the server. The SWE-bench Goal run (job 3428631) shows the same cost at small scale: its two slowest Goals without a rewriter call took 155.9 ms and 14.7 ms (median 0.62 ms).
> - Our temporary workaround (runtime `53e3b7a`, fix-engine-stall-1022, in `cf2b28d` and later; `remote_ra_live_v2/quoted_literals.py`): `dram_kv` and its pins are unchanged. At server start the runtime replaces `_QUOTED_LITERAL_RE` of the loaded features module with a linear-time object whose `sub` returns exactly what the upstream pattern returns (checked on every text of up to 7 characters over `'`, `"`, a backslash, `a` and a newline, 97,656 texts; on 4,000 random texts of 8 to 16 characters; on reply-shaped texts and the constructor's GoalRecords); it refuses to install if the upstream pattern changes. On the GPU, the Qwen Terminal-Bench `goal_query` dry run at `53e3b7a` (job 3434533) passed without a stall, although the same task again produced a reply cut at 4,096 tokens. The Gemma dry run at `53e3b7a` (job 3434544) passed too, without a stall and with no reply cut at `max_tokens` (after the re-verification with the corrected harness checks of section 6.7).
> - Questions: could the Goal side fix this upstream, so that we can drop the replacement? For example `(?!\1)[^\\]` in place of `(?!\1).` (a lone backslash can then no longer be taken), or a length cap on the previous action before `normalize_action`. The first differs from the current pattern in edge cases (an unclosed quote that the current pattern closes at an escaped quote), the second changes the normalized action of long replies, so the choice is the Goal owner's. Three observation patterns in the same file (`_ERROR_LINE_RE`, `_RETURN_CODE_RES`, `_GENERIC_FRAME_RE`) are quadratic on whitespace-heavy text and also hold the GIL: on blank lines `_ERROR_LINE_RE` and `_RETURN_CODE_RES` take about 1 s each at 8 KB and about 4 s each at 16 KB.
