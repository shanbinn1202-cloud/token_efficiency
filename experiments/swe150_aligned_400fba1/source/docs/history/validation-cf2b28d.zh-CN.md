> **另请 Goal 负责人审阅：Goal rewriter 的批处理（`--goal-rewriter-batch N`，4.10 节；适用于所有协议上的 `goal_query`）。** 16 个 session 时，各 session 的 rewriter 调用排队等同一个 Qwen3-0.6B 进程。开启这个选项后，排队中的调用最多 N 个凑成一批，用一次批量 greedy `generate` 一起跑。没变的：什么时候调用 rewriter、发送的内容、prompt、JSON schema、`max_new_tokens`、校验和回退；每个调用拿到自己的回答。变了的：批量 greedy 解码与逐个调用不是逐位相同的（padding 改变浮点累加顺序），所以重写出的 Goal 可能与不批处理时不同。SWE-bench Verified 前 32 题、16 个 session、各跑一次（作业 3404230 用 N = 4，3404696 不批处理；吞吐的定义仍是暂定的）：
>
> - 调用 rewriter 的轮次上 Goal 构造时间的中位数：N = 4 时 41.2 s，不批处理时 108.8 s；输出吞吐 166.9 对 117.2 tokens/s；32 题解决 20 对 19（在单次运行的波动范围内）。
> - Goal 回退（各跑一次）：第一次批处理运行（作业 3404230，N = 4）362 次 rewriter 调用中回退 59 次，其中 9 次是只在批处理运行中出现的显存失败：4 次 CUDA 显存不足，即一个 4 个请求的批次中的各个请求；5 次 cuDNN attention 错误，即一个 3 个请求的批次中的各个请求和两次单独调用，都发生在 GPU 显存已满时；不批处理（作业 3404696）294 次中 35 次。显存问题已修复（集成版本 120bc3c：恢复前先释放显存，每批结束后归还分配器缓存，每批填充后的 prompt 总 token 数上限 16,384）：批处理重跑（作业 3428631，N = 4）中仍有 7 个批次显存不足，都通过拆分恢复（没有 Goal 因显存而回退）；322 次 Goal 重写中回退 62 次（19.3 %）：320 次 rewriter 调用中 60 次校验或生成失败，另有 2 次在调用之前就超出了请求上限。
> - 批处理的运行比不批处理回退得多："retrieval_goal.symbols must be unique" 320 次中 37 次（11.6 %），不批处理 294 次中 18 次（6.1 %），Fisher 精确检验 p = 0.023；全部回退 322 次 Goal 重写中 62 次（19.3 %）对 294 次中 35 次（11.9 %），p = 0.015。其他原因：rewriter 输出的 JSON 未闭合 20 次（不批处理 16 次），"files must be unique" 3 次，"stats exceed the compact rewrite-request bound" 2 次。几次运行的 runtime 版本和 agent 轨迹不同，所以这只是相关，不是受控对比。受控对比是之后做的：把记录下来的 rewriter 调用逐个重放、再按记录的方式成批重放（作业 3443061，runtime `53e3b7a`，`RWRP_PARTIAL_PASS_VERIFIED`，部分通过只是因为计时部分被截断），在 557 对调用上没有发现显著差异："symbols must be unique" 逐个 53 次、成批 57 次（McNemar p = 0.50），任意失败 98 对 97（p = 1）。批量 greedy 解码与逐个调用不是逐位相同；批处理路径里没有找到会产生重复的机制。
> - 问题：批量解码不是逐位相同，是否可以接受（SWE-bench 的正式配置 "Ours (Goal)" 跑的是带 `--goal-rewriter-batch 4` 的 `goal_query`）？能否在 Goal 一侧先对列表字段（symbols、files、tests）去重再校验，而不是拒绝这次重写？这样无论是否批处理，这类回退大多都能消掉。
>
> **另请 Goal 负责人审阅：Goal 特征提取导致的 engine 卡死（作业 3429670，Qwen Terminal-Bench `goal_query` dry run）。** 运行约 9 分钟后 server 不再响应，16 个 trial 中 8 个撞到 Harbor 的 900 s agent 超时，运行失败。原因：`dram_kv/goals/features.py` 的 `normalize_action` 对 session 的上一轮回复执行 `_QUOTED_LITERAL_RE`（`(?s)(['"])(?:\\.|(?!\1).)*\1`）。反斜杠既可以由 `\\.` 连同下一个字符匹配，也可以由 `(?!\1).` 单独匹配，所以遇到没有闭合的引号时，正则会尝试其后反斜杠的所有拆分方式，每多一个转义耗时翻倍（一条带 22 个转义的被截断 Terminus 回复在 CPU 上要 11 秒）。卡住那一轮之前的回复是整次运行中唯一被 `max_tokens` 截断的回复（4,096 token，截在 JSON 字符串内部），对它的匹配一直结束不了（已在 CPU 上复现）。CPython 的正则引擎在整个匹配期间持有 GIL，engine 进程因此整体卡住，API server 与 engine 之间 90 s 的心跳超时后，server 被撤销。SWE-bench 的 Goal 运行（作业 3428631）也有同样的开销，只是规模小：不调用 rewriter 的 Goal 中最慢的两次为 155.9 ms 和 14.7 ms（中位数 0.62 ms）。
> - 我们的临时绕行（runtime `53e3b7a`，即 fix-engine-stall-1022，包含在 `cf2b28d` 及之后；`remote_ra_live_v2/quoted_literals.py`）：`dram_kv` 及其 pin 未改。server 启动时把已加载的 features 模块的 `_QUOTED_LITERAL_RE` 换成线性时间的对象，其 `sub` 的结果与上游正则完全相同（核对过：由 `'`、`"`、反斜杠、`a` 和换行组成的、长度不超过 7 的所有文本，共 97,656 条；4,000 条长度 8 到 16 的随机文本；回复形态的文本和构造器的 GoalRecords）；上游正则一旦变化就拒绝替换。GPU 上，`53e3b7a` 上的 Qwen Terminal-Bench `goal_query` dry run（作业 3434533）没有卡住而通过，尽管同一个任务又产生了一条在 4,096 token 处截断的回复。`53e3b7a` 上 Gemma 的 dry run（作业 3434544）也通过了，没有卡住，也没有在 `max_tokens` 处截断的回复（用 6.7 节修正后的 harness 检查重新核验之后）。
> - 问题：能否在 Goal 一侧从上游修复，这样我们就可以去掉这个替换？例如把 `(?!\1).` 改成 `(?!\1)[^\\]`（单独的反斜杠不再能被匹配），或在 `normalize_action` 之前限制上一轮动作的长度。前者在边界情况下与现有正则结果不同（现有正则会在转义引号处闭合一个未闭合的引号），后者会改变长回复的归一化结果，所以由 Goal 负责人决定。同一文件中的三个 observation 正则（`_ERROR_LINE_RE`、`_RETURN_CODE_RES`、`_GENERIC_FRAME_RE`）在空白多的文本上是平方复杂度，同样持有 GIL：在空行上，`_ERROR_LINE_RE` 和 `_RETURN_CODE_RES` 在 8 KB 时各约 1 s，16 KB 时各约 4 s。

## Runtime cf2b28d（2026-11-07 之前的 main）

本节描述 runtime `cf2b28d`，即 2026-11-07 之前 `main` 的代码（integrate-1107 之前在 README 中叫“当前 runtime”）。自 2026-11-07 起 `main` 是 integrate-1107（它当时记录的状态见[历史](../history.zh-CN.md#integrate-11072026-11-07-起为-main)）；自 2026-11-15 起是 integrate-1112（见 README 的 [`main` 包含什么](../../README.zh-CN.md#main-包含什么runtime-4ebff97)）。
