## 4. Start the policies

### 4.1 One server

Each server fixes **one policy and its frozen task(s)**. A task file has exactly `instance_id` and `problem_statement`; the problem statement must appear verbatim in the task message (the first user message) of every request. The output directory must not exist yet (its parent must). Inspect the dry run first; only `--start` loads the model.

```sh
python -B serve.py --release-dir "$RELEASE" \
  --task examples/task.json --policy full --output "$RUNS/full" --port 8000
python -B serve.py --release-dir "$RELEASE" \
  --task examples/task.json --policy full --output "$RUNS/full" --port 8000 --start
```

`goal_query` needs an explicit Goal-rewriter choice: a local Qwen3-0.6B checkpoint directory (the PoC setting), or `--no-goal-rewriter` for deterministic Goal fields only. `observation_query` and `random_fill` need none; they accept `--goal-rewriter-model` but never use it (section 5). The other selector options are optional; section 5 lists them. `serve.py --help` lists every flag. For the query policies and `random_fill` we recommend 16-token pages (section 4.6):

```sh
python -B serve.py --release-dir "$RELEASE" \
  --task examples/task.json --policy goal_query --output "$RUNS/goal" --port 8000 \
  --goal-rewriter-model "$MODELS/Qwen3-0.6B-c1899de" --page-tokens 16 --kv-layout decoupled --start
```

`--start` replaces the launcher with the APIServer process, so the launcher's PID is the server PID. The server binds only `127.0.0.1:<port>` (section 6.4 for other hosts). Startup takes a few minutes: model load, KV allocation and the first Triton compilations. In the validated jobs READY came 198–231 s after the start for the first server of a job and 103–146 s for later ones; those servers ran eager (today `--no-speed-defaults`, section 4.15), and with the speed defaults' CUDA graphs the startup also captures the graphs (section 4.8).

**READY** means `<output>/ready.json` exists, parses completely, and has `native_http_ready == true`, `evidence_kind == "NATIVE_HTTP_RUNTIME"`, the requested `policy`, and `runtime_manifest == SHA256(raw <release>/runtime-manifest.json)`. Its task/config hashes must equal `startup.json`. The file is created before it is fully written, so retry on a parse error. `/v1/models` answering is not READY. `examples/slurm/server_checks.py ready <output> <policy> <release>` checks exactly this (exit 0 READY, 1 not yet, 2 mismatch).

**Stop** with `SIGTERM` to that PID only, never the process group. Wait for the process to exit with code 0, then check the cleanup receipts (section 8; `examples/slurm/server_checks.py cleanup <output>`). A killed or timed-out shutdown is not a clean shutdown.

### 4.2 The accepted run's four policies on one GPU (sequential)

One GH200 holds one server at a time. Use a fresh server and a fresh output directory for every policy (and every task). This follows the procedure of the accepted run (job 3270721) with the Quickstart task. The smoke client of section 6.2 (one first request) stands in for the harness: replace its `examples/http_client.py` line with your client. The servers run with today's speed defaults (CUDA graphs `full`, the decode fast paths, the 1-GiB connector pool and the other switches of section 4.15); job 3270721 ran eager with the 32-GiB connector pool, at runtime `509eeae`. To match its settings, add `--no-speed-defaults` to the `serve.py` line.

```sh
TASK="$REPO/examples/task.json"
OUT="$RUNS/example-array-fix"
REWRITER="$MODELS/Qwen3-0.6B-c1899de"
PORT=8000
mkdir -p "$OUT"
for POLICY in full random50 goal_query observation_query; do
  SELECTOR=""
  case "$POLICY" in goal_query) SELECTOR="--goal-rewriter-model $REWRITER";; esac
  python -B serve.py --release-dir "$RELEASE" --task "$TASK" --policy "$POLICY" $SELECTOR \
    --output "$OUT/$POLICY" --port "$PORT" --start > "$OUT/$POLICY.server.log" 2>&1 &
  SERVER=$!
  until python -B examples/slurm/server_checks.py ready "$OUT/$POLICY" "$POLICY" "$RELEASE"; do
    [ $? -eq 1 ] || { echo "READY for something else: $POLICY"; kill -TERM "$SERVER"; wait "$SERVER"; exit 1; }
    kill -0 "$SERVER" || { echo "server exited before READY: $POLICY"; exit 1; }
    sleep 5
  done
  python -B examples/http_client.py --base-url "http://127.0.0.1:$PORT/v1" \
    --messages examples/messages.json > "$OUT/$POLICY.reply.json"
  kill -TERM "$SERVER"
  wait "$SERVER" || { echo "server exit not zero: $POLICY"; exit 1; }
  python -B examples/slurm/server_checks.py cleanup "$OUT/$POLICY" || exit 1
done
```

The next server must start on an idle GPU with no leftover process. The accepted run needed about 18 minutes for four sequential servers of six turns each, up to about 33K prompt tokens.

The accepted run used 784-token pages for every policy. To follow the recommendation of section 4.6, add `--page-tokens 16 --kv-layout decoupled` to the `goal_query` and `observation_query` servers (and to `random_fill`, if you add the control to the loop). `full` produced identical tokens in both layouts in job 3321538 (1 session × 10 turns at 8 GiB, prompts up to 60,440 tokens: the same prompt tokens, replies and completion counts on every turn); the 16-token-page SWE-bench pilot nevertheless ran every server, `full` included, with the flags.

### 4.3 Several GPUs

Running one policy per GPU in parallel (`CUDA_VISIBLE_DEVICES=<n>`, a distinct `--port` and a distinct `--output` per server) follows from the one-server-per-GPU design but was **not** part of the validated runs. Never point two harnesses with the same task at one server.

### 4.4 Several sessions on one server

```sh
python -B serve.py --release-dir "$RELEASE" \
  --task /abs/path/to/tasks-g0.json --policy observation_query --kv-cache-gib 24 \
  --page-tokens 16 --kv-layout decoupled --output "$RUNS/obs-g0" --port 8000 --start
```

`--task` takes a JSON list of 1 to 32 `{instance_id, problem_statement}` objects, one session each (`max_num_seqs` = sessions; the caps and what they size: **Up to 32 sessions** below). Instance ids must be distinct and no problem statement may contain another. Each harness runs one of these tasks against the same endpoint; the server routes every request to the one session whose problem statement its task message (`messages[1]`) contains, and each session behaves as a one-task server (sections 5 and 6). A request that matches no task, or several, is rejected. Admission runs one request at a time in arrival order (unless `--admission-overlap K`, section 4.10), then decode is batched across sessions. The sessions share one GPU KV pool and nothing is preempted: a turn whose worst-case peak does not fit waits (`CAPACITY_WAIT`) until running requests free blocks.

Size `--kv-cache-gib` so that every session's resident pages plus one turn fit at the longest context you expect. Validated settings ("usable" = attention blocks − 1). At 784-token pages one page is 51,380,224 bytes and one pool holds both the attention pages and the Gated-DeltaNet states. In the decoupled layout at 16-token pages one page is 1,048,576 bytes, and the Gated-DeltaNet states have their own pool (section 4.6):

The pilots capped sessions so that the pool can never run out even when every session sits at the 65,536-token limit: N − 1 idle sessions at I = 85 blocks plus one turn's peak P = 91 blocks plus a margin of 3 must fit the usable blocks U, so N = 1 + ⌊(U − 91 − 3) / 85⌋ (the `full` footprint at 64K from our capacity analysis, used for every policy because a session rebuild re-prefills every page). That gives 1 session at 8 GiB (U = 166) and 5 at 24 GiB (U = 500). The same rule gives 3 at 16 GiB and 7 at 32 GiB; those sizes are **not part of the validated runs**.

The 16-token-page pilot applied the same rule to the attention pool: an idle session at the limit holds I = ⌈65,536 / 16⌉ + 1 = 4,097 blocks, one turn's peak is I + ⌈16,384 / 16⌉ = 5,121, and the margin is one 1,536-token reply (97 blocks) plus vLLM's 1 % watermark (229). Five sessions at 24 GiB need 4 × 4,097 + 5,121 + 326 = 21,835 of the 22,911 usable blocks; six do not fit. The Mamba pool holds 2 slots per session plus a spare (section 4.6; one per session plus a spare with `--gdn-inplace-crossing`, below). The rule again gives 1 session at 8 GiB, 3 at 16 GiB and 7 at 32 GiB (**not part of the validated runs**).

**Up to 32 sessions.** This section is the one place for the session caps and the pool sizes they imply; the other pages point here. `MAX_SESSIONS` in `remote_ra_live_v2/sessions.py` (32 since branch sessions-32-1116; 16 before, 8 before that) caps a fixed task list and the K of a session pool (below), and `MAX_PERMITS` in `remote_ra_live_v2/admission_flags.py` caps `--admission-overlap` at the same 32; up to 16 every launch is byte-identical to the 16-session cap's. A chat-text pool reads `MAX_CHAT_TEXT_RUNNING` (24) for its K instead (section 6.7). A session pool registers up to `MAX_TASKS` (256 since integrate-1117; 64 before) tasks, a chat-text pool up to `MAX_CHAT_TEXT_SLOTS` (1,024) slots. The current configuration runs 16 sessions per server ([docs/status.md](status.md#current-configuration)); more than 16 sessions on the XML and kv-session protocols, and `--gdn-inplace-crossing`, are CPU-tested only (chat-text pools ran K = 20 on the GPU; [docs/known-limits.md](known-limits.md#21-more-than-16-sessions-and---gdn-inplace-crossing-are-cpu-tested-only) 2.1; CPU tests `test_ms32.py`, `test_gdn_inplace.py`, `test_inplace_32.py`). What grows with the number of sessions S:

- The decoupled layout's Mamba pool, 1 + 3(2S + 1) blocks: 100 blocks (4.78 GiB) at S = 16, reserved before the attention pool (stock vLLM has one shared pool: [docs/known-limits.md](known-limits.md) 2.2). With `--gdn-inplace-crossing` (opt-in; Qwen, the decoupled layout; [reference.md section 4.6](reference.md#46-decoupled-kv-layout-and-16-token-pages)) a request that crosses a Mamba block keeps its one slot, so the pool holds S + 1 slots, 1 + 3(S + 1) blocks: 52, 76 and 100 blocks at S = 16, 24 and 32, which gives the attention pool 2,349, 3,523 and 4,698 more blocks at P = 16 (+2.29, +3.44 and +4.59 GiB). The launcher refuses a budget whose attention pool cannot hold one session's turn at the 65,536-token limit (⌈65,536 / P⌉ + 1 + ⌈16,384 / P⌉ + ⌈1,536 / P⌉ + 1 blocks plus the 1 % watermark). At 8 GiB that allows at most 9 sessions at 16-, 32- and 64-token pages and 8 in the decoupled 784-token mode. Every configuration of 1 to 8 sessions passes, and the shared 784-token pool, which has no Mamba pool, is not affected.
- The lifetime request bound of one server (engine lifecycle entries, request tombstones and render bindings, none ever evicted): 256 per session, the per-session request bound, and at least 1,024 (4,096 at 16; section 4.9).
- Above 16 sessions (K = 20, 24, 32 at P = 16; `serve.py` refuses what does not fit): at 25 GiB the Mamba pool takes 124, 148 and 196 blocks (5.93, 7.07 and 9.37 GiB), leaving 19,531, 18,357 and 16,008 attention blocks (312K, 294K and 256K tokens for all sessions together, against 331K at 16). At 262,144 tokens with 4,096-token replies one session's turn needs about 17,850 blocks, so 25 GiB takes K ≤ 25, 24 GiB K ≤ 20 and 32 GiB every K up to 32 (with `--gdn-inplace-crossing` 24 and 25 GiB take every K up to 32); at 65,536 and 131,072 tokens 25 GiB takes every K. Pinned host memory with the 1 GiB connector pool: 24 sessions at 65,536 tokens need 100.7 GiB, 32 need an arena (at most 122 GiB); at 131,072 and 262,144 tokens `--dram-arena-gib` is at most 123 GiB at K = 24 and 122 GiB at K = 32, and an arena of 70 GiB holds about 48K tokens per session at K = 24 (72K at 16). vLLM's capture sizes are 1, 2, 4 and multiples of 8, and it captures FULL decode graphs only for the sizes up to `max_num_seqs`: at K = 24 and 32 every decode step replays a FULL graph in `--cuda-graphs full`, while at K = 20 a step of 17 to 20 running requests is padded to 24 and replays the piecewise graph ([reference.md section 4.8](reference.md#48-cuda-graphs); [docs/known-limits.md](known-limits.md) 2.3), so prefer K = 16, 24 or 32 to K = 20 where the configuration allows it. `--admission-overlap K` up to 32 pins an admission wait of 300 + 120 (K − 1) s (3,060 s at 24, 4,020 s at 32); a client timeout must exceed it.
- Host memory: the pinned page arena (section 4.6) of up to S × 4,097 pages of 1 MiB at P = 16 and the 65,536-token limit (64 GiB at S = 16; above 16 sessions and at longer contexts, the previous item), next to the connector's CPU pool (1 GiB with the speed defaults, 32 GiB with `--no-speed-defaults`; section 4.15) and a 154 MB Gated-DeltaNet carry per session (two with `--gdn-device-handoff`, section 4.10).

Batched decode changes replies with the batch: two eager runs of the same 16-session workload (jobs 3339019 and 3343069, the table above; prompts up to about 14K tokens, far below the 65,536-token limit, so they do not reach the limits described next) gave the same tokens on 72 of 96 turns, because a reply can change with the batch composition, which depends on timing.

The never-deadlock rule cannot hold for 16 `full` sessions at 64K on one GH200. They need about 67,350 attention blocks of 1 MiB plus the Mamba pool, about 70.6 GiB of KV, while the GPU has 94.53 GiB free at start (vLLM log of job 3313802) and the weights take 51.1 GiB. The selective policies need less only between rebuilds, since a rebuild returns to full residency. With a fixed `--active-token-budget 8192` at 16-token pages, 15 idle sessions holding their budget and their last turn's pages, plus one turn's peak, fit in 24 GiB when turns are about 7,000 tokens and need 34 GiB when they reach the 16,384-token observation limit; a 40 % budget needs 41 and 51 GiB on the same two assumptions. Size `--kv-cache-gib` and the workload accordingly. `CAPACITY_WAIT` holds a turn back while running requests can still free blocks. When nothing else runs, a turn that the idle sessions' pins leave no room for waits too, until a session closes or, with `--release-idle-pages` (section 4.13), idle sessions' pages are released; once every session waits, the server stalls. (Before commit `68d19b4` the gate admitted such a turn, which could then be preempted on the GPU: [History](history.md#history).) When no other session pins blocks, the turn is admitted (as on a one-task server). The largest `--kv-cache-gib` stays 32: with the Goal rewriter, about 36 GiB of the GPU is estimated to be left for KV (not measured).

**Session pool: many tasks, at most K running (`--max-running-sessions K`).** With this option `--task` registers 1 to 256 tasks (64 before integrate-1117; pinned in `startup.json` like any task list, plus `max_running_sessions` = K), and at most K (1 to 32, at most the number of tasks) sessions are open at a time, so that one server runs, for example, 32 SWE-bench tasks with 16 concurrent agents, refilled as agents finish, or the first 150 SWE-bench Verified instances with 24 (the README's [24-session configuration](../README.md#24-session-configuration-the-groups-150-instance-runs-2026-11-17-not-yet-gpu-validated), not yet GPU-validated). Routing by the task message, per-session isolation, the turn schedule, the capacity gate and no-preemption are unchanged. What K sizes instead of the task count: `max_num_seqs` = K, the Mamba pool (2K + 1 slots, K + 1 with `--gdn-inplace-crossing`) and the launcher's attention-pool check, the never-deadlock rule above (N = K) and the pinned page arena. What the registered task count T sizes: the lifetime request bound, max(1,024, 256 × T) (8,192 at T = 32, 38,400 at T = 150, 65,536 at T = 256; section 4.9), a bound on the requests made, not a reservation. A registered task holds only its record (the task, its session id, an empty transcript), so 150 or 256 registered tasks start with the same KV pools, arena and pinned host memory as 32; a session's KV pages, Mamba slots and arena pages exist only while it is open, and its close drops its requests' host records (slim tombstones stay; CPU tests `test_ms_pool.py`, `test_tasks256.py`: a pool of K = 24 over 150 tasks).

```sh
python -B serve.py --release-dir "$RELEASE" --task /abs/path/to/tasks-pool.json --policy full \
  --max-running-sessions 16 --kv-cache-gib 24 --page-tokens 16 --kv-layout decoupled \
  --output "$RUNS/full-pool" --port 8000 --start
```

- **Open.** A session opens at its task's first request (turn 0). While K sessions are open, that request waits before admission, first come first served, until one closes; the wait is `open_wait_s` in its `runtime.jsonl` row. A request that goes away while it waits leaves its task unopened.
- **Close.** When an agent is done, the harness closes its task's session: `POST /v1/sessions/close` with `{"instance_id": "<task id>"}` (section 6.5). The engine frees everything the session holds: its resident pages and live tail on the GPU, its Gated-DeltaNet carry and pinned-arena pages on the host, its selection tables, Goal state and transcripts, and the per-request records it kept. Both pools return by exactly the session's pins, and the next waiting task opens. A closed task never reopens; later requests for it fail at once (`session ... closed by the harness`).
- **Failures.** A failed request closes its session as before, but the session keeps its open slot and engine state until the harness closes it, so the harness closes every session it started, failed or not.
- **Shutdown** closes the sessions still open, as on any server.

K sizes the Mamba pool, not the registered tasks: 24 tasks at K = 8 held 17 slots (2K + 1; job 3343069, the table above).

### 4.5 GPU job (Slurm)

`examples/slurm/serve_gh200.sh` runs one server in one Slurm job: job-local `TMPDIR` and caches, the section 3 environment, the dry run, `serve.py --start`, the READY wait, a harness, `SIGTERM` to the server PID, the exit code and the cleanup receipts. It follows the validated jobs' `job.sh` and job steps. They passed these `sbatch` options on the command line:

| Option | Validated value |
| --- | --- |
| `--partition` | a GH200 partition: the interactive partition `ghx4-interactive`, with a 2 h limit (jobs 3270721, 3299809, 3300301, and the 16-token-page pilot 3313802, 3314010, 3314319, 3314623), the batch partition `ghx4` for the 784-token-page pilots (jobs 3299922, 3300434) and the benchmark jobs (for example job 3461703) |
| `--gpus` / `--nodes` / `--ntasks` | `1` / `1` / `1` (`--gres=gpu:1` is the usual equivalent elsewhere; not part of the validated runs) |
| `--cpus-per-task` / `--mem` | `16` / `200g` in the jobs above. Since 2026-10-14 the benchmark jobs, and the command below, request `113560M`, one GH200 memory share; the MemoryAgentBench Qwen servers request two, `227120M` |
| `--time` | `00:30:00` (4 one-session servers, job 3270721), `00:45:00` (4 four-session servers: a 2-turn `full` warm-up, then `full`, `observation_query` and `goal_query`; jobs 3299809 and 3300301), `02:00:00` (2 five-session servers, jobs 3313802, 3314010, 3314319, 3314623), `03:45:00` (3 servers, job 3299922), `10:45:00` (6 servers, job 3300434) |
| `--mail-type` | `BEGIN,END,FAIL` (job 3270721 used `END,FAIL`; batch queue waits can be long) |
| `--export` | `ALL` (the script then resets `PATH`, `LD_LIBRARY_PATH`, `HOME`, caches and `TMPDIR` itself) |

The script takes its settings from the submitting shell (its header lists them). `ACCOUNT` is the Slurm account of your allocation, `PARTITION=ghx4` selects the GH200 batch partition that the benchmark jobs used (on another cluster, use its GH200 partition), and `MAIL` the address for the job mail. `RUN_ROOT` must exist before `sbatch`: Slurm writes the job's output file there, and the script creates its job directory in it. A smoke run of the Quickstart task:

```sh
ACCOUNT=your-account
PARTITION=ghx4
MAIL=you@example.org
export REPO VENV RELEASE
export TASKS="$REPO/examples/task.json" POLICY=full RUN_ROOT=/abs/short/jobs MODE=smoke
mkdir -p "$RUN_ROOT"
sbatch --account="$ACCOUNT" --partition="$PARTITION" --nodes=1 --ntasks=1 --gpus=1 \
  --cpus-per-task=16 --mem=113560M --time=00:30:00 --job-name=selective-prefix \
  --output="$RUN_ROOT/slurm-%j.out" --export=ALL --mail-type=BEGIN,END,FAIL --mail-user="$MAIL" \
  "$REPO/examples/slurm/serve_gh200.sh"
```

The job succeeded when `$RUN_ROOT/slurm-<job id>.out` ends with the lines `server exit 0, harness exit 0` and `CLEAN_SHUTDOWN` (the cleanup check of section 4.1). Its files are in `$RUN_ROOT/<job id>/`: the dry run `dry-run.json`, the server log `server.log`, the reply `smoke.json` and the server's output directory `full/`.

The smoke server pins at most about 5.2 GiB of host memory (36.2 GiB with `--no-speed-defaults`, vLLM's 32-GiB connector pool), well inside one share. One share holds a server whose pinned worst case plus about 32 GiB for the processes and a 5-GiB margin stays within 113,560 MiB, that is a pinned worst case of up to about 73.9 GiB; above that, request two shares, `--mem=227120M` ([MEMORYAGENTBENCH_BENCHMARK.md](MEMORYAGENTBENCH_BENCHMARK.md#a4-this-runtime-server-flags-and-vllm-arguments), A.4 Host memory, where the 16-session Qwen server pins 127.29 GiB). The Qwen launcher itself refuses only a pinned worst case above its 128-GiB budget (section 4.9, sized for the former 200 GiB jobs); the Gemma launcher checks one share itself, its pinned memory plus 30 GiB (section 4.14). On `ghx4` a memory share is billed like a GPU: a job of two shares is billed as two GPUs.

`RUN_ROOT` must be short: the job uses `$RUN_ROOT/<job id>/tmp` as `TMPDIR` and refuses a path over the AF_UNIX budget. `MODE=swebench` opens the reverse tunnel of section 6.4 and runs `examples/swebench/run_agents.sh` on the agent host over SSH (section 7.4). `PAGE_TOKENS=16 KV_LAYOUT=decoupled` passes `--page-tokens 16 --kv-layout decoupled` to `serve.py` (section 4.6); with both unset the server uses the default 784-token layout. The validated jobs were driven by our private controller with extra gates (environment snapshots, GPU idle checks, per-turn evidence checks); this script keeps the server-side steps only and is **not itself part of the validated runs**.

## 6. Harness interface

The launcher's `--protocol` accepts `mswea-xml` (the default), `kv-session` and `chat-text`. `mswea-xml` reproduces the dram-backed-kv PoC server token for token and is the protocol for the SWE-bench runs (sections 6.1 to 6.5). `kv-session` is the token-level session protocol of the MemoryAgentBench harness (section 6.6). `chat-text` is plain OpenAI chat text for agents such as Terminus 2 on Terminal-Bench 2.0 (section 6.7). `--enable-thinking` turns thinking on for `mswea-xml` and `chat-text` on the Qwen profile (opt-in, section 6.8). With it, `--thinking-history strip` serves `chat-text` the history of the stock default template, the reasoning dropped (opt-in, section 6.9). The current configuration turns thinking on in the keep mode of section 6.8; which runs used either option is in [docs/status.md](status.md).

### 6.1 Mini-SWE-Agent XML protocol

The PoC server's contract, used by Mini-SWE-Agent 2.4.2 with single `<mswea_bash_command>` actions:

- **Request.** `POST /v1/chat/completions` with `messages` only: the complete history as `{"role", "content"}` text. It holds the system message, the task message (which must contain the frozen issue), then the agent's assistant and user messages, and it ends with a user message (an observation with `<returncode>`, a format-error prompt, and so on). `tools` is rejected and other message keys are ignored.
- **Sampling.** The server ignores client sampling fields, as the PoC does: greedy decoding, at most the server's reply bound of new tokens (1536, the PoC's; `--max-tokens`, section 4.9), and a stop once the decoded text contains `</mswea_bash_command>` or on EOS/pad. The action marker is detected inside the engine.
- **Rendering.**
  - System and task go through the pinned chat template with `enable_thinking=false`.
  - Every later message is `<|im_start|>{role}\n{content}<|im_end|>\n`.
  - The generation header is `<|im_start|>assistant\n<think>\n\n</think>\n\n`.
  - A previous reply is replaced by the exact token IDs it was generated with, matched after `strip()`, so trimmed echoes are fine.
- **Why thinking off.** The protocol's default is thinking off (thinking on is opt-in, section 6.8; the current configuration turns it on: [docs/status.md](status.md#current-configuration)), aligned with the PoC: its server (`scripts/serve_online_selector_v2.py` of dram-backed-kv) renders with `enable_thinking=False`, because LiteLLM / Mini-SWE-Agent remove the thinking block from the assistant content before the next request. With thinking on, the next request would no longer extend the KV prefix that the server holds (prefix-unstable, so no KV reuse); with thinking off, the empty think block is part of the prompt that the server renders (the generation header above), and the history stays append-only. A baseline run with thinking on is therefore not comparable with thinking-off runs ([docs/known-limits.md](known-limits.md) 4.3).
- **Response.**
  - `choices[0].message.content` is the decoded text of every generated token, including the marker and anything the final token carries past it.
  - `finish_reason` is always `stop` and there are no tool calls.
  - The boundary `<|im_end|>\n` (`\n` after EOS) enters the server's history but is not returned.
- **Goal-query inputs.** The Goal uses the PR description inside the task message, the previous reply, the latest user message, and its `<returncode>`, as in the PoC.
- **Session.** A request that repeats the previous request, then the reply, then one new user message continues the session (section 5).
  - Any other request starts a fresh cold session, as on the PoC server. Examples are a format-error retry that drops the rejected reply (1 of 5 PoC cohort instances) and compaction.
  - A fresh session re-renders the whole request from text, releases the previous session's pages and resets the selector and Goal state. Its runtime row records `stage_b.rebuild == true`.
  - **The Goal after a dropped reply (goal-rollback-1116; the policies whose query is the Goal: `goal_query` and the marker-pages plug-in's `goal_query_markers`; Qwen and Gemma 4, thinking on or off).** A rebuild whose request is the previous request plus one user message (the client dropped the previous reply: Mini-SWE-Agent's format-error retry; with thinking on the rollback below, off the same message shape, whose prompt is still re-encoded from text) keeps the session's Goal: the constructor's state (phase tracker, drift streak, retrieval Goal) and the Goal cache stay, and the rebuild turn reuses the Goal of the turn whose reply was dropped, recorded as a `KEEP` without the rewriter (`reused_previous`, trigger `rollback`, `diagnostics` `{"kept_from_turn": …}`). That `KEEP` is synthesized by the runtime, not decided by the Goal gate (the gate does not run on that turn), so a decision histogram should count rows with trigger `rollback` (or `query.goal.carry.carried`) separately from the gate's `KEEP`s. A carried turn builds no Goal: it calls no rewriter, does not park at a Goal, and its native file has no `goal_async_ms`, `goal_construct_ms` or `goal_overlap_ms`. The next turns update it from the latest observation and the reply kept after the format error, as if the dropped reply had never been sent; their Goal turn ids go on from the kept turn's. Before, every rebuild started the Goal again from the task (an `INITIALIZE` whose observation was the format-error message, ignored as a user message: in job 3576565 all 40 rebuilds were such retries, and their Goals had no errors in 40 and no files in 30). The rebuild's runtime row adds `query.goal.carry` (`goals.jsonl`: `carry`): `carried`, `from_turn` (the request turn that built the kept Goal), `goal_turn` (its Goal turn id) and `reason` (why it did not carry: no Goal of an earlier turn, the request does not repeat the kept turn's request, or the Goal state changed since; the Goal then starts again as before). Every other rebuild (a resend, an edited history, compaction), every other policy and every other row are unchanged. The selection of the rebuild turn is unchanged (local turn 0: no candidates). Tests: `test_goal_rollback.py`.
  - With thinking on (section 6.8; branch keep-rebuild-1116) a format-error retry is a rollback: the fresh session's prompt is the previous session's exact tokens up to the rejected reply's header (every earlier reasoning and generated id kept), then the format-error message and the header. It is re-prefilled like any fresh session (`stage_b.rebuild == true`, `thinking.history == "rollback"`), and its Goal goes on (above). Before keep-rebuild-1116 it was re-rendered from the messages' content, so every earlier reasoning was gone for the rest of the session (section 6.8).

### 6.3 Errors

Treat any non-2xx status, timeout, disconnect or server exit as the end of that server's run:
1. Preserve the HTTP error body, `failures.jsonl` and the server log.
2. Stop the server with `SIGTERM`.
3. Start a fresh server for any retry.

Do not silently retry a request whose admission is uncertain, do not advance the turn, and do not reuse the session. A contract violation (6.1) is rejected with an HTTP error.

When the engine rejects a request, the HTTP 500 body is vLLM's JSON error response for an `EngineGenerateError` whose message is empty: it does not give the reason. The reason is in two places:
- the `chain` and `traceback` fields of the request's row in `failures.jsonl`;
- the server log line `REMOTE_RA_REGISTERED_ADD {"phase": "engine_rejected", ...}`.

A `CAPACITY_WAIT` refusal (section 4.4) writes the same log line, with its traceback, but it is not an error: the frontend retries the turn, and the client sees only the delay.

A server generates only for requests of its own protocol route (6.1, 6.6 or 6.7). A generate request on any other vLLM route (`POST /v1/completions`, `/v1/responses`, pooling and the like) is refused in the API server before it reaches the engine, with vLLM's error response for that route (message: "this server generates only for requests of its own protocol route; generate requests on other vLLM routes are refused"); the server and its sessions keep running. Until review-fixes-1110 one such request ended the engine and every session. Routes that do not generate (`/health`, `/metrics`, `/v1/models`) answer as before. CPU-tested only: the HTTP status vLLM gives the refusal was not checked on a running server.

Unsupported foreign prefix reuse, speculative decoding, async loading, preemption, history mutation and unknown drains are hard failures, never a silent fallback to Full.

### 6.4 Reaching the server from another host

The server listens on `127.0.0.1` only and has no authentication; never expose it beyond loopback. SWE-bench needs Docker, so in the pilots the agents ran on a separate agent host and reached the GPU job through a reverse SSH tunnel (jobs 3299922 and 3300434). Per server, in this order:

1. After READY, the GPU job opens a reverse tunnel whose far end is a **Unix socket** on the agent host:

   ```sh
   ssh -N -R "$AGENT_SOCKET:127.0.0.1:$PORT" -o ExitOnForwardFailure=yes \
     -o ServerAliveInterval=30 -o ServerAliveCountMax=3 \
     -i "$TUNNEL_KEY" -o IdentitiesOnly=yes -o BatchMode=yes -o StrictHostKeyChecking=yes \
     -o UserKnownHostsFile="$KNOWN_HOSTS" -o GlobalKnownHostsFile=/dev/null -o ConnectTimeout=20 \
     "$AGENT_HOST"
   ```

   This is the form of `examples/slurm/serve_gh200.sh`; the pilots' tunnels also passed `-o CheckHostIP=no -o UpdateHostKeys=no`. `PORT` is the server's port (8000 by default), `AGENT_HOST` is `user@agent-host`, `TUNNEL_KEY` a key that the agent host accepts, `KNOWN_HOSTS` a file that pins its host key, and `AGENT_SOCKET` a new path (one per server, at most 100 bytes) in a `0700` directory there.
2. The job checks the tunnel from the agent host: `curl -sf --unix-socket "$AGENT_SOCKET" http://localhost/v1/models` must list `selective-prefix`.
3. On the agent host, `examples/swebench/relay.py "$AGENT_SOCKET" <port>` listens on `127.0.0.1:<port>` only and relays each connection to the socket; `run_agents.sh` starts it and checks with `ss` that nothing but `127.0.0.1` listens on that port. The agents use `http://127.0.0.1:<port>/v1`.
4. After the agents finish, the job closes the tunnel, then stops the server with `SIGTERM`.

Why a Unix socket: if the agent host's sshd has `GatewayPorts yes`, every TCP remote forward binds on all interfaces whatever address the client asks for, which would expose the unauthenticated server. A Unix-socket forward has no TCP listener, and the relay binds loopback explicitly, so this form stays on loopback whatever the sshd setting. The compute node needs outbound SSH to the agent host; the pilots checked that once per job before the first server.

A simpler TCP form, **not the validated form**: `ssh -N -R 127.0.0.1:<p>:127.0.0.1:8000 <agent-host>`. It stays on loopback only if the agent host's sshd has `GatewayPorts no` (OpenSSH's default). Check with `ss -ltn` on the agent host before any agent runs; `run_agents.sh -` (no socket) performs that check and refuses a non-loopback listener.

### 6.5 Session close (session pool)

On a server started with `--max-running-sessions` (section 4.4), `POST /v1/sessions/close` with the JSON body `{"instance_id": "<startup task id>"}` closes that task's session for good. It is accepted from a loopback peer only (the server binds loopback anyway; through the tunnel of section 6.4 the peer is loopback too), like the chat route it has no HTTP authentication, and the frontend forwards it to the engine as an authenticated frame of the private channel. The response is the engine's close receipt (`"object": "session.close"`, `opened`, `turns`, the released pages and blocks, both pools' free blocks before and after, `open_sessions`); closing a closed task returns the same receipt with `"repeated": true`. Refusals: 403 (not loopback), 404 (not a startup task), 409 (`SESSION_BUSY`: the session has a request queued or in flight; retry after it ends), 400 (no session pool, or a bad body). A task that never opened still closes through the engine, which records its receipt with `"opened": false`; nothing is released, and the worker and the KV pools are not touched.

### 6.6 MemoryAgentBench kv-session protocol

`--protocol kv-session` serves the token-level session protocol of the MemoryAgentBench harness's KV-session client (method `dram_backed_kv`). The client renders the chat template and parses the replies itself; the server never renders a template. Such a server needs a session pool (`--max-running-sessions K`, section 4.4) and takes no `--task`: its registered tasks are slots, and each client session binds to the next unused slot at its first request (`--kv-session-slots N`, 1 to 64, default 64, so one server serves at most N client sessions over its lifetime). `--kv-session-thinking on|off` (default `on`) pins the generation header the client sends. On the Gemma 4 profile the default is `on` too since gemma-thinking (before, the launcher refused a Gemma kv-session server without `off`), so a thinking-off client, such as the MemoryAgentBench client's Gemma tail, must pass `--kv-session-thinking off`: otherwise its requests do not end with the pinned header and every one is refused (`HEADER_MISMATCH`). `/v1/chat/completions` and `/v1/sessions/close` are refused on such a server.

```sh
python -B serve.py --release-dir "$RELEASE" --protocol kv-session --kv-session-thinking off \
  --policy observation_query --page-tokens 16 --kv-layout decoupled --active-token-budget 32768 \
  --max-running-sessions 16 --kv-cache-gib 32 --max-tokens 4096 --max-model-len 262144 \
  --dram-arena-gib 124 --release-idle-pages --output "$RUNS/mab-obs" --port 8000 --start
```

These are the settings of the MemoryAgentBench `observation_query` server (job 3405844: thinking off, a 124-GiB arena); its exact command, with its fast-path switches, is in [MEMORYAGENTBENCH_BENCHMARK.md](MEMORYAGENTBENCH_BENCHMARK.md#a4-this-runtime-server-flags-and-vllm-arguments) (A.4). It pins up to 127.29 GiB of host memory, so its Slurm job requests two memory shares, `--mem=227120M` (section 4.5). This is the configuration of record (thinking off, a 32,768-token budget, 32 GiB of KV), now historical; the current configuration is in [docs/status.md](status.md#current-configuration).

- **`GET /v1/kv-session/info`** returns `{"method": "dram_backed_kv", "budget": <tokens or null>, "options": {...}}`: the server's attention budget (its `--active-token-budget`, else `null`) and what it runs (policy, page size, budget mode and selection-contract fields, reply bound, context limit, thinking, sessions).
- **`POST /v1/kv-session/complete`** takes exactly these fields (shortened):

```json
{"method": "dram_backed_kv", "session_id": "<32 lowercase hex>", "input_ids": [248046, 198, 248045, "..."],
 "header_tokens": 7, "prefix_tokens": 423, "boundary_tokens": 2, "budget": 32768, "max_tokens": 4096,
 "temperature": 0, "top_p": 1.0, "top_k": -1, "repetition_penalty": 1.0, "seed": 42, "messages": ["..."]}
```

  - The first request of a session sends the whole rendered prompt: `boundary_tokens` 0 and `prefix_tokens` + `header_tokens` = the number of `input_ids`.
  - Every later request sends only the new tail: the previous reply's closing delimiter (with the reply's last token in front when it was not EOS), the new messages and the next generation header. `input_ids[0]` must repeat the previous reply's last output id, `prefix_tokens` must not change, and the tail must end with the pinned header. The server's prompt is the session's stream plus `input_ids[1:]`; phase 1 computes from the last reply token to the start of the header (section 5).
  - Sampling: greedy only (`temperature` 0, `top_p` 1, `top_k` −1 or 0, `repetition_penalty` 1); `max_tokens` from 1 to the server's reply bound (`--max-tokens`), clamped to the context left. `budget` and `method` must equal the server's.
  - `messages` (the client's whole history) never makes tokens. Only the messages new since the previous request are used, for the Goal of `goal_query`: their tool and user texts are the observation, and a user message (the question that MemoryAgentBench sends with the last history chunk, or a format-error prompt) becomes the Goal's explicit requirement.
- **Response:** `text` (every generated token decoded, special tokens included), `output_ids` (the last token included), `prompt_tokens` (the prompt's length), `completion_tokens`, `cached_tokens` (`prompt_tokens` minus the number of `input_ids`), `finish_reason` (`stop` or `length`), and, named apart, `kv_slot`, `kv_turn`, `effective_max_tokens`, the waits and the turn's page counts.
- **`POST /v1/kv-session/close`** with `{"session_id": ...}` returns 200 `{"closed": true, ...}`, also for an id the server never saw or already closed (then the first answer with `"repeated": true`); 409 while the session has a request queued or in flight. A closed id is never served again.
- **Errors.** Every failure of a complete request is 400 `{"error": ..., "type": ...}`. A prompt that leaves no room for a reply is refused before any model work with exactly `"Logical RoPE context limit reached"` (`type` `CONTEXT_LIMIT`). Refusals found before admission (the body, the sampling fields, the header, the continuation token, the prefix, the boundary, the context) leave the session usable; a failure in the engine fails the session, which the client then closes. A `boundary_tokens` past what the turn geometry allows is one of these refusals (`type` `BOUNDARY_RANGE`): the boundary is the previous reply's closing delimiter (2-3 tokens), and the new messages must open at most one Page after that reply's last token. Until review-fixes-1110 such a request was refused in the engine, and that refusal ended the engine when the request's 360-s lease ran out.
- **Evidence.** Every `runtime.jsonl` row adds `kv_session`: the client session id and slot, the token geometry (`header_tokens`, `prefix_tokens`, `boundary_tokens`, `input_tokens`), the client's and the effective `max_tokens`, `finish_reason`, and the Goal's message source and explicit requirement.
- **Gemma 4 (section 4.14).** On a Gemma release the protocol uses Gemma's turn grammar with thinking off: the 7-token header after a user turn, `header_tokens` 0 after tool responses (the tail ends with `<tool_response|>`, which phase 2 computes), the new messages opening at `<|turn>` or after `<|tool_response>`, the stop ids 0, 1, 50 and 106, and the startup record's `"grammar": "gemma4"`.
- **Tests.** CPU tests (`test_kv_session_protocol.py`, which uses the pinned Qwen3.6 tokenizer when Transformers is installed: a 5-token header with thinking on, and the server's raw token stream equal, token for token, to the template's render with `preserve_thinking`; `test_kv_session_server.py`; `test_kv_session_e2e.py`, MemAgent sessions through the packaged router and the engine fakes).
- **GPU runs.** The GPU runs of this protocol, Qwen and Gemma 4, are in [docs/status.md](status.md) (MemoryAgentBench is not scored: [docs/known-limits.md](known-limits.md) 5.1); the former status text of this section is frozen in [docs/history/running-gpu-notes.md](history/running-gpu-notes.md).

The configuration of record of the MemoryAgentBench benchmark run (32 cases, 8 per ability, at most 16 at a time, thinking off, the policies `observation_query` and `goal_query`, and a stock vLLM 0.24.0 control through the harness's Vanilla transport; historical, the current configuration is in [docs/status.md](status.md#current-configuration)), the settings of the Gemma 4 31B IT end-to-end runs and the checklist for aligning baselines with it are in [docs/MEMORYAGENTBENCH_BENCHMARK.md](MEMORYAGENTBENCH_BENCHMARK.md).

### 6.7 Chat text protocol (Terminal-Bench 2.0 with Terminus 2)

`--protocol chat-text` serves plain OpenAI chat text on `/v1/chat/completions` from a server-owned token transcript, for agents that send their whole text history every turn and parse the reply themselves. The target is Harbor 0.21.0's Terminus 2 on Terminal-Bench 2.0, unchanged: JSON actions, no system message, thinking off. Such a server needs a session pool (`--max-running-sessions K`, section 4.4; 1 to 24 on a chat-text server) and takes no `--task`: its registered tasks are slots that bind lazily to client sessions (`--chat-text-slots N`, 1 to 1024, default 512). It serves the eight built-in policies of [design.md section 5](design.md#5-page-selection-for-the-query-policies) (the three plug-ins `ledger_query`, `goal_query_markers` and `observation_query_markers` serve the XML protocol only); `goal_query` serves Harbor 0.21.0's Terminus 2 only, with Goal inputs that are **provisional** (below). `/v1/sessions/close` and the kv-session routes are refused. A release of the Gemma 4 profile serves the protocol with Gemma's turns (section 4.14): everything below holds for both models except the rendering, the stop ids and the capacity figures, `goal_query`'s Goal inputs included (the same provisional rules and record; gemma-tb-goal).

```sh
python -B serve.py --release-dir "$RELEASE" --protocol chat-text --policy observation_query \
  --page-tokens 16 --kv-layout decoupled --active-token-budget 8192 \
  --max-running-sessions 20 --kv-cache-gib 25 --max-model-len 262144 --max-tokens 4096 \
  --connector-pool-gib 1 --dram-arena-gib 70 --release-idle-pages --output "$RUNS/tb-obs" --port 8000 --start
```

These are the sizes of the benchmark's Qwen servers ([TERMINALBENCH_BENCHMARK.md](TERMINALBENCH_BENCHMARK.md#a3-this-runtime-server-flags-and-vllm-arguments) A.3), the settings of job 3461661: 25 GiB of KV, the 262,144-token context and a 70-GiB arena (`--kv-cache-gib 25 --max-model-len 262144 --dram-arena-gib 70`). The first Qwen dry runs (jobs 3399075, 3399437, 3429670 and 3434533) ran at 32 GiB of KV, the default 65,536-token context and a 64-GiB arena (`--kv-cache-gib 32 --dram-arena-gib 64`). These settings are the configuration of record (thinking off); the current configuration is in [docs/status.md](status.md#current-configuration).

- **Request.** Nonstreaming, one choice, `model` `selective-prefix`. `messages`: an optional system message, then user and assistant text; the first message after the system message is a user message, and so is the last. Content must be a string; `tools`, `tool_calls` and `tool` messages are refused with 400, other message keys are ignored.
- **Sampling.** Greedy; the client's sampling fields are ignored. `max_tokens` (or `max_completion_tokens`) from 1 to the reply bound (`--max-tokens`); without one, the bound clamped to the context left. The reply stops on EOS/pad only (no marker).
- **Rendering.** The reference is the pinned template with `enable_thinking=false` and `preserve_thinking=true`. A fresh or rebuilt session renders the whole conversation through it, then the header `<|im_start|>assistant\n<think>\n\n</think>\n\n`. A continuing request appends the previous reply's exact generated ids and `<|im_end|>\n` (`\n` after EOS/pad), then the new user message as the template renders it, `<|im_start|>user\n{content.strip()}<|im_end|>\n`; startup checks these pieces against the template once. A request continues the session when it repeats the previous request, the previous reply (compared after `strip()`) and one new user message. Anything else, such as Terminus's summary hand-off, an unwound history or a resent request, rebuilds the session (`stage_b.rebuild`). When every reply re-encodes to its own ids and carries no surrounding whitespace, each prompt equals the template's render of its messages.
- **Response.** `choices[0].message.content` is the decoded reply (special tokens skipped), `finish_reason` is `stop` on EOS/pad and `length` at the bound, and `usage` has the prompt, completion and total tokens.
- **Context limit.** A request whose prompt plus requested reply exceeds the context limit (without `max_tokens`: one that leaves no room for one token) is refused with 400 and vLLM's own text, `This model's maximum context length is …`. litellm and Harbor map it to a context-length error. Nothing changes on the server; the session's next request continues normally.
- **Sessions.** A request's key is its initial segment (the system message, if any, and the first user message) and, when the client sends one, its `X-Session-ID` header (litellm also copies it into the body as `session_id`). Terminus 2 sends no header by default, and its first prompt carries the container's host name, so every trial is its own session. Under one header id, a request with another initial segment (Terminus's summary "questions" call, sent without history) is its own session (kind `aside`) and never resets the main one. A key binds to the next unused slot at its first request. A request for a key whose slot has a request queued or in flight waits up to 30 s for it, then gets 409 `SESSION_BUSY`. The key moves to a fresh slot (a rebind: the first request there renders from text, a full prefill) when its slot was failed by a request (a client disconnect or cancel, an engine failure answered with 500), was closed by the server, or reached 256 requests. A client that goes away while its request is still being admitted fails the slot as well (review-fixes-1110; before, that slot stayed live on an engine session the cancel had already retired, and the client's retry got one 500 `ENGINE_FAILURE` before the key was rebound). Slots are never reused; when all are used a new session gets 400 `SESSION_LIMIT`.
- **Closes.** On the default path no close call arrives. Failed, rebound and client-closed slots, and slots at the request bound, close at once. A live session closes only when no spare open session exists, that is when K sessions are open: while a request waits for an open session, the least recently used session idle for `--chat-text-evict-after` seconds (default 30) is closed, asides first, one per waiting request; with nobody waiting, the least recently used session idle for `--chat-text-idle-timeout` seconds (default 600) is closed, one, so that the next new session finds a spare. While a spare exists no live session is closed, however long it has been idle. A client that sends `X-Session-ID` can close: `POST /v1/chat-text/close` with `{"session_id": ...}` (or `{"key_sha256": ...}`, the SHA-256 of the canonical JSON of the initial segment) closes every session of that id. It answers 200, also for an unknown or a closed id (then the first answer with `"repeated": true`), and 409 while one of them has a request in flight; a closed id is refused afterwards. `GET /v1/chat-text/info` returns the options, the counts and the client sessions.
- **Capacity.** At most K sessions are open. For Harbor's `-n 16` the setting is K = 20: four spare sessions take the finished trials (no close call arrives) and Terminus's summary sub-calls, so a running trial in a long command is not evicted. K sizes `max_num_seqs`, the Mamba pool and the pinned page arena (section 4.4). At P = 16, K = 20 has 41 Gated-DeltaNet slots and a Mamba pool of 124 blocks (5.93 GiB, 24 blocks or 1.15 GiB more than at K = 16). That leaves 19,531 attention blocks (19,530 usable) at the benchmark's 25 GiB of KV, and 26,699 at the 32 GiB of the first dry runs (1,175 fewer than at K = 16). Under the rule of section 4.4 with 4096-token replies, 20 sessions at 262,144 tokens need 33.0 GiB with an 8192-token budget (29.8 at K = 16), 41.2 GiB with a typical last turn (36.3) and 57.0 GiB with the worst last turn (48.7); at 131,072 tokens 24.9 (21.7), 33.1 (28.2) and 48.9 GiB (40.7); at 65,536 tokens 20.8, 29.1 and 44.8 GiB. At 262,144 tokens one session at the limit holds 16,385 blocks, so 25 GiB cannot hold two such sessions at once: the benchmark relies on the capacity gate and `--release-idle-pages` (job 3461661 needed neither: no release and no capacity wait). ### 6.8 Thinking on (stage 1, `--enable-thinking`)

`--enable-thinking` (opt-in; Qwen3.6-27B with `--protocol mswea-xml` or `chat-text`) turns thinking on. The current configuration runs it (the keep mode of this section); the runs that used it are in [docs/status.md](status.md), the earlier functional checks of this section in [docs/history/running-gpu-notes.md](history/running-gpu-notes.md). Its reply bound defaults to 4,096 tokens, the reasoning included, as in the baselines (section 4.15; `--max-tokens 1536` keeps the former bound): the capacity gate and the launcher reserve ceil(4096 / P) Pages per turn. Without it every launch, startup config, evidence byte and response is unchanged. On the Gemma 4 profile (gemma-thinking): Gemma's thinking-on header `<|turn>model\n`, the template's `<|think|>` system turn in the mandatory prefix, and the reply split on its channel ids by the rules of vLLM 0.24.0's `gemma4` reasoning parser ([docs/thinking-gemma/DESIGN.md](thinking-gemma/DESIGN.md)). The kv-session protocol keeps its own `--kv-session-thinking` (section 6.6; on Gemma `on` pins the two thinking-on headers). The analysis behind it (an unreviewed report, frozen): [docs/history/thinking-on-analysis.md](history/thinking-on-analysis.md).

- **Pins.** `startup.json` and `ready.json` gain `thinking` (`remote_ra_live_v2/thinking.py`: the generation header `<|im_start|>assistant\n<think>\n`, the template arguments, the split at `</think>`, the response fields, the append rule; the dry run prints it). On chat-text the `chat_text` record's `header_text` and `template_kwargs` are the thinking-on ones (`enable_thinking=True, preserve_thinking=True`); the XML protocol renders system and task with `enable_thinking=True`. No vLLM argument changes. The pinned template's thinking-on header (and on chat-text its history render) is checked once at startup.
- **Response.** The decoded reply `R\n</think>\n\nC` is cut at its first `</think>`: `content` is C, `reasoning_content` and `reasoning` are both R, as generated (no strip). A reply without `</think>` (cut at the reply bound, or ended before it) is all reasoning, with `content` `""`. vLLM's Qwen3 reasoning parser, whose source is not in this repository, is believed to treat a thinking-on reply without an end token the same way (with a null content).
- **Action marker.** The XML protocol's stop on `</mswea_bash_command>` counts only the text after `</think>`: a draft action inside R never stops the reply. Nothing else in the server scans a reply for protocol markers.
- **History.** The routes read each assistant message's reasoning from the request body (`reasoning_content`, else `reasoning`; vLLM's request model keeps only `reasoning`). A request continues the session, and the stream keeps R's exact token ids, when it repeats the previous request's messages exactly (their reasoning included), then the previous reply with its content equal to the returned C and its reasoning equal to the returned R (both compared after `strip()`; a missing reasoning counts as empty), then one new user message. Mini-SWE-Agent 2.4.2 through litellm and Terminus 2 with `interleaved_thinking` on send R back so. Anything else takes the protocol's rebuild: chat-text renders the conversation through the template with the thinking-on arguments (R where the client sent it). A client that drops R (Terminus 2's default) therefore rebuilds every turn, unless the server runs `--thinking-history strip` (section 6.9), which cuts the last reply and re-prefills it instead.
- **History after a format error (XML protocol, keep-rebuild-1116).** Mini-SWE-Agent drops a reply without exactly one action (almost always one cut at the 4,096-token bound inside its reasoning, whose content is `""`) and sends the previous request plus a format-error message. Such a request (the previous request exactly, plus one user message) is a **rollback**: its prompt is the session's stream up to the rejected reply's generation header, token for token (every earlier R and generated id kept), then the new message and the header. The engine re-prefills it as a rebuild at local turn 0 (`stage_b.rebuild == true`; the KV of the session is not kept: that would need the Gated-DeltaNet state at the header's start, which is not held after a completion), and the next requests append to it. Several format errors in a row each roll back the same way. The `goal_query` Goal goes on across a rollback (goal-rollback-1116, section 6.1): the rollback turn reuses the Goal of the turn whose reply was dropped, and the next turn updates it from the latest observation and the kept reply's content; the offline replay of goal_query 3576565's request streams through the branch carries the Goal at all 40 of its rollbacks (5 of them the second of two in a row). Any other rebuild of the XML protocol renders system and task through the template and every later message as the template renders it with `preserve_thinking=True` (R where the client sent it, trimmed text; Gemma: the template's own render, which has no R). This also changes ordinary appends: since keep-rebuild-1116 the new user message of a thinking-on append (Qwen, XML protocol) is encoded trimmed, as the template renders it; before, it was encoded untrimmed, so an observation with leading or trailing whitespace gave that append a prompt that differed from the template render (for example one token longer for a trailing newline) and an observation span as much longer. In the five replayed runs no call before a session's first format error changed (Mini-SWE-Agent's observations carry no outer whitespace); thinking off and Gemma keep their tokens (Gemma's user piece was already trimmed); their `goal_query` Goal carries across the same retry all the same (section 6.1). A rollback or rebuild render that fails before the engine opens the new session (an abandoned render) restores the session as it was, so the retry renders against the session the engine still holds. So every prompt of a thinking-on `mswea-xml` Qwen server equals the pinned template's render of its messages with `enable_thinking=True, preserve_thinking=True` (when every reply re-encodes to its own ids); `tools/keep_render_check.py` checks a run's calls against that render. **Runs before keep-rebuild-1116 lost every earlier R at a session's first format error**: the rebuild re-encoded every later message from its content (C), and later requests appended to that. From the audit of 2026-11-16 (calls at or after a session's first format error / all calls): full 3583081 (`ba4d1ba`) 351/1,262 (27.8 %, 12 of 32 sessions, 26 format errors), recent_fill 3539242 (`60c5d21`) 683/1,613 (42.3 %), observation_query 3539260 (`60c5d21`) 640/1,548 (41.3 %), goal_query 3576565 (`ba4d1ba`) 869/1,843 (47.2 %), akv_rule 3577833 (`ba4d1ba`) 429/1,411 (30.4 %), and from the offline replay of keep-rebuild-1116 ledger_query 3611601 (`51b4085`) 519/1,548 (33.5 %, 13 of 32 sessions, 35 format errors); in 3583081 36,524 reasoning tokens of 276 replies (29.5 % of the kept replies' reasoning) left the session, and its prompts were 4.2 % shorter than the keep render. Before each session's first format error the served prompts equal the keep render (911/911 calls in 3583081). Those runs are keep runs only up to each session's first format error.
- **Reply bound.** `--max-tokens` (1536 or 4096) counts the reasoning: every generated token is a reply token for the capacity rule and the context checks, and the next prompt holds R's tokens.
- **Goal input (for the Goal owner).** With the option, the Goal's previous reply (`previous_action`) is the content C only, not R plus C.
- **Evidence.** Each `runtime.jsonl` row adds `thinking`: `reasoning_tokens` (the tokens before the one that completes the first `</think>`), `think_end_tokens` (1 or 0), `content_tokens`, `closed`, the reasoning and content lengths in characters, and `history` (`fresh`, `append`, `rollback` (XML protocol, keep-rebuild-1116), `rebuild_reasoning_dropped`, `rebuild_reasoning_differs`, `rebuild`). A `rollback` or XML rebuild row adds `kept_tokens` (prompt tokens taken from the session's own stream: all of the rejected reply's prefix on a rollback, 0 on a rebuild) and `reencoded_replies` (assistant messages encoded from their text, whose exact generated ids are not kept); `fresh` and `append` rows keep their fields. For turns that kept R and closed it, when every reply re-encodes to its own ids, the pinned template's render with `enable_thinking=True, preserve_thinking=True` and R as `reasoning_content` equals the server's prompt token for token (on the XML protocol since keep-rebuild-1116 also when an observation carries surrounding whitespace: user messages are encoded trimmed, as the template renders them; before, only when none did).

### 6.9 Thinking on with the reasoning dropped (`--thinking-history strip`)

`--thinking-history strip` (opt-in, with `--enable-thinking`; Qwen3.6-27B with `--protocol chat-text` only) serves the history the stock default template renders: `enable_thinking=True` without `preserve_thinking`, every past reply as its content only, whatever reasoning the client sends back (the Terminal-Bench Vanilla baseline's input); its GPU checks are in [docs/status.md](status.md), the earlier functional checks of this section in [docs/history/running-gpu-notes.md](history/running-gpu-notes.md). Without it stage 1's keep mode applies (section 6.8) and every launch, startup config, evidence byte and response is unchanged. Refused with `mswea-xml` and `kv-session`, (in this first version) with `--gdn-device-handoff` and `--phase1-in-step`, and with `--policy recent_tools` and `akv_rule`, whose reply classes cannot be read from a stripped history (section 5). On the Gemma 4 profile (gemma-thinking) the transcript side is in (every past reply `<|turn>model\n` + its content + `<turn|>\n`, the stock thinking-on render) and `--async-scheduling` is refused with it; its engine side holds the sliding window at the cut on the GPU ([docs/thinking-gemma/DESIGN.md](thinking-gemma/DESIGN.md) section 4): `--window-hold-slots H` (1 to the running sessions; left out, the most that fit, and the server is refused when not even one fits) reserves H hold slots of one window each (812.5 MiB at 16-token Pages). A strip turn takes a hold slot from its admission to its commit (phase 1, a goal_query admission parked at its Goal and a cold prefill included), so at most H strip turns are in flight at once and the others wait at the capacity gate: with `--admission-overlap K` at most min(K, H) admissions are in flight and a Goal batch holds at most H calls (at H = 1 the server runs one turn at a time). The default leaves pool 0 at the selective rule's minimum, so a smaller H can serve more concurrent long contexts (the design note, section 4.3); H is pinned as `kv_layout.hold_slots` and printed by the dry run (`window_hold`). Design and decisions: [docs/thinking-cut/DESIGN.md](thinking-cut/DESIGN.md) (option (a), form E); the rules are in `remote_ra_live_v2/thinking_cut.py`.

- **Commit at the cut.** Each completion commits the session at X, the start of its generation header (the end of its observation span, N - 5): the Pages up to floor(X/P) are sealed, page X/P is the tail with its valid end at X, and the Gated-DeltaNet carry is the state at X (the phase-1 state of a continuing turn; at a session's first turn its prefill ends a forward at X, after vLLM's Mamba-aligned split, and the state is captured there). The header and the reply (reasoning and content) are turn-local: no Page past the cut is sealed, copied or ranked, and the carry at the reply's end is not captured.
- **Re-prefill.** The next request's prompt is the committed stream, the reply the client sent back as the template renders it (`<|im_start|>assistant\n` + its content trimmed, after its last `</think>` if any, + `<|im_end|>\n`), the new user message and the header. Its stable end is X + 3 (the header's first three tokens, compared each turn; a mismatch refuses the request), so the turn geometry is unchanged and the re-encoded reply belongs to the next observation: phase 1 computes it with the observation, as one native forward (16,384 tokens; a longer one fails the turn as before). Every prompt therefore equals the stock template's render of its messages, also after a reply cut at its bound (its content is empty).
- **Continuing.** A request continues the session when it repeats the previous request (role and content), then the previous reply with its content equal to the returned C (after `strip()`), then one user message; anything else rebuilds from text. The responses and the Goal's previous reply are as in section 6.8.
- **Evidence.** `startup.json` and `ready.json` pin the `thinking` record with `history: strip` and the template arguments `enable_thinking=True`; the worker echoes `thinking_history`. A native file's plan names `commit_end` (X) and the seal rule `floor(X/P)`; the file adds `truncate` (the cut, and the dropped branch: its start and end, the header ids, the generated ids, the index of `</think>`) and, for a continuing turn, `reprefill` (the re-prefilled reply's start and end). In `runtime.jsonl`, `stage_b.computed_end` and `sealed_end` are the committed ends, `stage_b.phase2_end` is the reply's end (N + g - 1), and `truncate` and `thinking.cut` / `thinking.reprefill` are added. The offline Terminal-Bench verifier checks these fields request by request: it verified the dry run of job 3499759 (294 cut turns on its `observation_query` server).
- **Tests.** `test_thinking_cut.py` (the template render of a past reply with the pinned Qwen3.6 tokenizer when Transformers is installed, the transcript, the pins and refusals, chat-text sessions on the engine fakes with every completion's cut, carry, evidence and the dense recomputation of every decision, the other chat-text scenarios, the decode fast paths, `--deferred-completion-io`, `--admission-overlap`, `--release-idle-pages`, mutations; with `REMOTE_RA_TB_ATIF_DIR`, the 178 Terminal-Bench trials replayed with reasoning).
